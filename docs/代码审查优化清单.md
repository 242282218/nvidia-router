### 4. MaxBytesReader 双重写响应，破坏错误响应契约【已修复】
- **位置**：`internal/httpapi/v1/chat.go:141`、`internal/httpapi/admin/auth.go:235`
- **问题**：`http.MaxBytesReader(writer, ...)` 传入了非 nil writer，超限时 Go 内部先写纯文本 413 并提交响应头，handler 又追加 JSON 错误体，客户端收到混合体且状态码与 JSON 不一致。
- **建议**：统一改为 `http.MaxBytesReader(nil, request.Body, limit)`，让 handler 写统一 JSON 413。同仓库 `internal/protocol/audio/transcriptions.go:46` 已正确传 nil，可作为参照。
- **执行状态（2026-08-01 P0）**：`readChatBody`（chat.go）与 admin `decodeJSON`（auth.go）均改 `http.MaxBytesReader(nil, ...)`，超限由 `writeChatError`/handler 统一写 JSON 413 `request_too_large`；`writeInvalidRequest` 经 `errors.As` 保留 `*apierror.Error` 结构。新增 `TestChatRejectsOversizedBodyWithJSON413`、`TestAuthRejectsOversizedBodyWithJSON413` 断言单一 JSON 错误体与 413 状态。

### 5. xkproxy fetcher 未禁用重定向【已修复】
- **位置**：`internal/xkproxy/fetcher.go:56-59`（`http.Client` 未设置 `CheckRedirect`）
- **问题**：默认跟随最多 10 次重定向；被劫持/恶意上游的 302 可把租约地址引到攻击者服务器，后续流量被路由到攻击者。

- **执行状态（2026-08-01 P0）**：`newFetcher` 设置 `CheckRedirect: http.ErrUseLastResponse`，3xx 响应经状态码检查直接返回 `ReasonInvalidResponse`（不跟随、不解析 Location）。新增 `TestFetcherDoesNotFollowRedirects`：302 带 `Location` 指向返回有效代理地址的 `/valid` 路由，断言 Fetch 失败为 `ReasonInvalidResponse` 且 `/valid` 未被请求。

## P1 核心链路正确性

### 6. 流式请求 commit 后无读超时（stall），key 租约可被无限持有【已修复】
- **位置**：`internal/sse/proxy.go:51-116`、`internal/httpapi/v1/chat.go:122-138`
- **问题**：`ResponseHeaderTimeout` 只覆盖首字节前；一旦 `Prime` 成功、headers 已提交，主循环在 `decoder.Decode()` 阻塞读上游 body，上游僵死则客户端无限挂起，key 保持 busy 占用连接和 goroutine 无法恢复（配置的 `NonstreamTotalTimeoutMS` 对 stream 无效）。
- **建议**：给流式读加空闲超时（如 io 层包装带 deadline 的 reader 或 `SetReadDeadline` 周期性刷新），超时后走"已 commit 截断、未 commit 故障转移"的既有逻辑。9Router CHANGELOG 已修过同类 stream stall，属于应补齐的边界。
- **执行状态（2026-08-01 P1）**：`internal/sse/idle.go` 新增 `WithIdleTimeout`（空闲超时 reader：每次成功 Read 数据重置窗口，窗口过期关闭底层 body 解除阻塞，返回 `ErrStreamIdle`）；`primeSSE` 成功后统一包装 `response.Body`，chat/responses 两个端点的流式读均受保护。空闲窗口复用 `budget.FirstByteTimeout()`。新增 `TestWithIdleTimeout*` 4 个用例（stall 报告、活跃流不误杀、沉默后触发、非正 idle 原样返回）。超时后走既有逻辑：已 commit 静默截断、未 commit 500。

### 7. Responses 非流式：具名 tool_choice 形状不转换直接透传【已修复】

- **建议**：`{type,name}` 转成 `{type,function:{name}}`；或对具名 tool_choice 明确返回 `unsupported_responses_feature` 而不是制造上游 400。
- **执行状态（2026-08-01 P1）**：`mapToolChoice` 识别 `{type:"function",name}` 形状并转换为 `{type:"function",function:{name}}`；Chat 原生 `{type:"function",function:{name}}` 形状原样透传。新增 `TestToChatConvertsNamedToolChoiceShape`、`TestToChatPassesThroughChatToolChoiceShape`。

### 8. Responses 流式：delta.content 为数组时全部文本静默丢失【已修复】
- **位置**：`internal/protocol/responses/delta.go:40,70-79`
- **问题**：`decodeStringField` 只接受字符串；上游以 OpenAI 兼容数组形式流式输出 content part（`[{"type":"text","text":"..."}]`）时字段被静默丢弃，客户端收到空文本无任何报错。
- **建议**：`decodeStringField` 遇到数组时拼接其中 `text` 字段；在 stream_test 补此形状用例。
- **执行状态（2026-08-01 P1）**：`decodeStringField` 支持 content part 数组并拼接 `text` 字段；非 `text` part 忽略。新增 `TestParseChatDeltaConcatenatesContentParts`、`TestParseChatDeltaIgnoresUntextContentParts`、`TestParseChatDeltaPlainStringStillParses`。

### 9. Responses 输入：采样参数全部被静默丢弃【已修复】
- **位置**：`internal/protocol/responses/request.go:61-87`
- **问题**：`temperature`、`top_p`、`seed`、`stop`、`presence_penalty`、`frequency_penalty`、`stream_options` 等全部被丢弃（chat 路径保留未知字段，responses 路径全新构建 chat body），客户端传 `temperature: 0` 得到默认温度，生成行为被无提示改变。

- **执行状态（2026-08-01 P1）**：`mapSamplingParameters` 白名单透传 `temperature`/`top_p`/`seed`/`stop`/`presence_penalty`/`frequency_penalty`/`stream_options`，在 `ToChat` 中紧随 `max_output_tokens` 映射执行；字段缺失时全部省略（不注入默认值）。新增 `TestToChatForwardsSamplingParameters`、`TestToChatOmitsSamplingParametersWhenAbsent`。

### 10. 协议级/EOF 错误被当作连接错误，给健康 key 打瞬态冷却【已修复】
- **位置**：`internal/fault/classifier.go:175-179`、`internal/httpapi/v1/chat.go:100-104`
- **问题**：`io.EOF`/`io.ErrUnexpectedEOF` 被归为可重试连接错误；`primeSSE` 收到"200 但 body 为空/非 SSE"时返回原始 EOF，走 retryable 分支给 key 记 15s 冷却。这是**上游整体协议问题**，Attempt 循环会在所有 key 上重放，把每个 key 打上冷却，最终 `all_keys_cooling_down` 风暴。
- **建议**：prime/Validate 失败统一转换 `fault.Protocol`（不冷却 key），或让 `Classify` 对 `io.ErrUnexpectedEOF` 单独分类；补 chat prime 失败回归测试。
- **执行状态（2026-08-01 P1）**：`execute` stream 分支对 `primeSSE` 错误中的 `ErrEventTooLarge`/`io.EOF`/`io.ErrUnexpectedEOF` 统一转 `fault.Protocol`（`ScopeUpstreamGlobal`、不冷却 key）；responses 端点补 `ErrEventTooLarge` 同类处理。重写 `TestChatStreamCommentOnlyAttemptFails` 断言分类为 `fault.Fault` + `upstream_protocol_error` + `ScopeUpstreamGlobal`，新增 `TestChatRetriesProtocolFailureWithBackupKeyAndPreservesResponse` 覆盖故障转移路径。

### 11. 上游 Retry-After 未封顶，单次响应可让 key 长期不可用【已修复】
- **位置**：`internal/fault/cooldown.go:25-38`、`internal/fault/retry_after.go:15-19`、`internal/nvidiakey/repository.go:296-298`
- **问题**：429 带合法 `Retry-After` 时直接返回该值，不做 5 分钟退避上限封顶；`ParseRetryAfter` 允许最大约 292 年；冷却期间 key 不被调度也不触发恢复，管理员只能手动清库。
- **建议**：显式 RetryAfter 也做 `min(duration, maximumRateLimitCooldown)` 封顶；`Retry-After: 0` 视为无效走指数退避；补封顶测试。
- **执行状态（2026-08-01 P1）**：`CalculateCooldown` 对合法 `RetryAfter` 封顶为 `maximumRateLimitCooldown`（5 分钟）；`Retry-After: 0` 仍走指数退避。新增 `TestCooldownCapsExplicitRetryAfter`（24h→cap、精确 cap、0→0）。

### 12. 直连模式完全无连接复用，每次请求一次 TCP+TLS 握手【已修复】
- **位置**：`internal/upstream/nvidia/client.go:185-202`、`internal/upstream/nvidia/chat.go:133-148`
- **问题**：`doDirect` 每请求 `newAttemptTransport` 克隆 transport，并在 `attemptBody.Close()` 里 `CloseIdleConnections()`，keep-alive 池永远为空；代理模式（xkproxy 按超时值缓存 transport）反而有复用。
- **建议**：按 `(ConnectTimeoutMS, FirstByteTimeoutMS)` 建小型 transport 池，而不是每请求克隆+拆池。
- **执行状态（2026-08-01 P1）**：新增 `directTransportPool`（`(ConnectTimeoutMS, FirstByteTimeoutMS)` 键，LRU 上限 8，单调计数器保证 LRU 精确）；`doDirect` 从池取 transport，删除每请求克隆与 `attemptBody` 拆池。新增 `TestChatDirectTransportPoolReusesBySettings`、`TestChatDirectTransportPoolEvictsLeastRecentlyUsed`。

### 13. Prime 捕获缓冲无界增长（内存 DoS）
- **位置**：`internal/sse/prime.go:18,51-62`
- **问题**：`captureReader` 累积读到的所有字节直到第一个含 data 的事件；SSE decoder 单事件限 4MiB，但多个纯 comment/keep-alive 事件在首个 data 事件前无限累积。
- **建议**：给 capture 累计量加上限（如 4MiB），超限报 `ErrEventTooLarge`。

### 14. Responses 流式：工具参数累计无总上限
- **位置**：`internal/protocol/responses/state.go:89-111`（`stringsBuilder` 注释声称"callers bound total size at the HTTP layer"，但 HTTP 层 `internal/httpapi/v1/responses.go` 并无对应总量限制，唯一约束是 SSE 单事件 `MaxEventSize` 4 MiB）
- **问题**：`stringsBuilder` 累积所有 tool call arguments 无总量限制，恶意/异常上游可无限流式追加造成 OOM。
- **建议**：在 applyToolCall 处设置总量上限（如 16MiB），超限按流中错误处理。

### 15. 直连模式对自定义 RoundTripper 静默忽略全部超时
- **位置**：`internal/upstream/nvidia/chat.go:53-65,121-131`
- **问题**：`newAttemptTransport` 在 base 不是 `*http.Transport` 时返回 `attemptRoundTripper`，完全不应用 connect/first-byte 超时；代理模式在 `NewClient` 就拒绝了非 `*http.Transport`，直连模式却放行。
- **建议**：与代理模式一致，构造时拒绝，或对包装 RT 显式套用超时。

### 16. 已 commit 后 ErrStreamInterrupted 依赖 Prime 前置保证，耦合脆弱
- **位置**：`internal/httpapi/v1/chat.go:125-128`、`internal/sse/proxy_test.go:91-107`
- **问题**：处理层把 `ErrStreamInterrupted` 一律当作"已提交、客户端自然截断"，只有 `primeSSE` 保证 proxy 至少重放一个含 data 的事件才成立；纯 comment 流返回 ErrStreamInterrupted 且未 commit，此时客户端收到空响应。
- **建议**：在 `streamResponse` 中对 `err == ErrStreamInterrupted && !commit.Committed()` 写 502 错误体。

## P2 性能与可扩展性

### 25. 热路径上每次 /v1 请求打一次 DB 查询 + 一次同步 DB 事务写
- **位置**：`internal/httpapi/router.go:22`、`internal/httpapi/admin/auth.go:69-82`（`RequirePasswordChanged` 每请求 SELECT）、`internal/observability/http.go:76-78`（每请求同步 Record 事务 5 条语句）、`internal/database/db.go:27`（`SetMaxOpenConns(1)` 单连接）

- **建议**：将 `must_change_password` 状态缓存进 `runtimeconfig.Store`（仅在改密后失效）；观测记录批量异步写入。

### 26. 流式响应的 token 用量不采集，统计失真
- **位置**：`internal/observability/http.go:122-131,171-193`
- **问题**：`disableCaptureIfIneligible` 在 `IsStream` 时禁用响应体捕获，`parseUsage` 只在非流式路径解析；统计面板流式 chat/responses 的 token 消耗恒为 0。
- **建议**：对 SSE 流在 `[DONE]` 前的事件中解析 `usage`（chat 流式最后一个 event 带 usage）。

### 27. tryAcquireLocked 全量扫描 + 全局互斥锁
- **位置**：`internal/pool/pool.go:251-301`
- **问题**：每次 acquire/release 持全局锁并可能 O(n) 遍历全部 key；配置允许 10000 key，高并发下全局锁是唯一串行点。
- **建议**：至少做早退（发现剩余候选全 busy 提前返回）；更优做法按 ready 与否维护两级索引或分片。

### 28. 队首 waiter 因"全部冷却"被立即踢出，队列无法吸收冷却等待
- **位置**：`internal/pool/queue.go:200-222`
- **问题**：`dispatchWaitersLocked` 中 `tryAcquireLocked` 返回 `UnavailableCooling` 时直接踢出队首并投递错误，所有 key 冷却时新请求不排队而是立即 429。
- **建议**：明确设计意图——若希望队列吸收冷却，让队首 waiter 等待（用 wait 超时约束）；否则文档说明"冷却不排队"。

### 29. 非关键状态写入失败会把上游成功响应变成客户端失败
- **位置**：`internal/router/attempt.go:200-212`
- **问题**：上游返回 2xx 后 `MarkSuccess` 因 ctx 到期或 DB 错误失败时，`Run` 关闭已成功的响应并返回 504/500，一次真实的成功被吞掉。
- **建议**：状态写入失败降级为尽力而为——先返回成功响应，状态写入用独立短超时 ctx；至少把该取舍写进注释/文档。

### 30. /health/ready 每次探测做 4 次 DB 操作且可能阻塞业务
- **位置**：`internal/httpapi/health/health.go:41-56`
- **问题**：ready 依次做 Ping + VerifyMigrations + ValidateSentinel + admins 查询，单连接上与业务请求竞争。
- **建议**：Ping 一次即可，或加 100-200ms 超时并用独立只读连接。

### 31. 两个清理 worker 都在凌晨 3 点撞同一个单连接
- **位置**：`internal/observability/cleanup.go:74-81` 与 `internal/adminauth/cleanup.go:77-84`

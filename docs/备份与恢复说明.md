# 备份与恢复说明

本项目使用 SQLite 保存管理员、模型白名单、下游 Access Key 元数据和加密后的 NVIDIA Key。数据库备份不包含主密钥。恢复必须同时具备数据库备份和生成该数据库所用的原主密钥。

## 关键原则

1. 正式备份和恢复都必须停服，避免业务请求与维护操作同时修改数据库。
2. 使用容器内 CLI 的 `db backup`，该命令调用 SQLite Backup API 生成一致性快照。
3. 不要把在线复制 `router.db-wal`、`router.db-shm` 或直接复制正在运行的 `router.db` 当作正式备份方案。WAL 文件不能单独代表一致的数据库快照。
4. 数据库备份和原主密钥必须分开、受控、加密保存。备份文件本身仍包含敏感数据，不能提交仓库或放在公开目录。
5. 恢复时不能用新主密钥替代原主密钥。缺少原主密钥时，不承诺能够恢复已加密 NVIDIA Key。

## 备份前检查

确认当前 Compose 项目使用目标 named volume，并预留一个不在应用 `/data` 内的备份目录。先停服：

```bash
docker compose stop app
```

停服后确认容器没有继续运行：

```bash
docker compose ps
```

不要在服务仍运行时直接复制数据库文件。停服既是运维流程要求，也能减少备份期间仍有请求写入数据库的歧义。

## 使用 CLI 生成备份

CLI 默认从 `NVIDIA_ROUTER_DATA_DIR` 读取 `/data/router.db`。Compose 的 named volume 挂载到 `/data`，因此执行 `db backup` 时输出路径必须是容器内可写的路径。一个直接的做法是临时挂载宿主机备份目录：

```bash
mkdir -p ./backups
docker compose run --rm --no-deps \
  -v "$(pwd)/backups:/data-backups" \
  app db backup --output /data-backups/router-$(date -u +%Y%m%dT%H%M%SZ).db
```

命令实际入口为：

```text
nvidia-router db backup --output <path>
```

输出文件由临时文件写入后原子发布，权限设置为仅所有者可读写。输出路径必须与源数据库不同。备份完成后，确认文件存在且大小合理，并把备份复制到受控的独立存储；不要把 `router.db-wal` 或 `router.db-shm` 单独复制走。

备份完成后启动服务：

```bash
docker compose up -d app
```

先验证：

```bash
curl --fail http://SERVER_IP:3756/health/live
curl --fail http://SERVER_IP:3756/health/ready
```

若仍未完成首次改密，`ready` 会返回失败，这是预期的安全门禁；完成 `admin/admin` 首次登录和改密后再验证就绪。

## 恢复前准备

恢复是破坏性维护操作，先确认：

- 已停止 `app` 容器；
- 目标备份文件来自可信来源，且未被截断；
- 具备与该备份匹配的原主密钥；
- 已保留当前 named volume 的现状，必要时可先做一份当前数据库备份；
- 已安排维护窗口，恢复期间不接收 API 请求。

停止服务：

```bash
docker compose stop app
```

不要把备份文件直接覆盖一个仍被运行中的 SQLite 进程打开的数据库，也不要只恢复 WAL 文件。

## 恢复数据库

先找到 Compose named volume 挂载到宿主机的位置：

```bash
docker volume ls
docker volume inspect <COMPOSE_PROJECT>_nvidia-router-data
```

实际 volume 名称以 `docker volume ls` 和当前 Compose project name 为准。确认挂载点后，在服务停服状态下替换 `/data/router.db`。示例流程如下，`<VOLUME_MOUNTPOINT>` 必须替换成上一步检查出的真实路径：

```bash
cp <VOLUME_MOUNTPOINT>/router.db <VOLUME_MOUNTPOINT>/router.db.before-restore
install -m 600 backups/router-YYYYMMDDTHHMMSSZ.db <VOLUME_MOUNTPOINT>/router.db
rm -f <VOLUME_MOUNTPOINT>/router.db-wal <VOLUME_MOUNTPOINT>/router.db-shm
```

不要凭猜测写入 volume 路径，也不要删除整个 named volume。恢复后在 `.env` 中设置与备份匹配的原主密钥，再启动：

```bash
docker compose up -d app
```

如果使用错误主密钥，应用可能无法正常启动或 `ready` 会失败；不要通过删除 sentinel、修改 SQLite 或生成新时间戳来绕过检查。

## 恢复后验证顺序

恢复后的第一步不是调用代理 API，而是验证进程和就绪状态：

```bash
curl --fail http://SERVER_IP:3756/health/live
curl --fail http://SERVER_IP:3756/health/ready
docker compose logs --tail=100 app
```

`/health/ready` 成功表示应用能够访问数据库，迁移已完成，原主密钥可以验证加密 sentinel，管理员已完成首次改密，且服务没有进入关闭流程。之后登录管理页面，确认模型白名单、NVIDIA Key 掩码和 Access Key 元数据仍在，再进行最小范围的非敏感请求验证。

若恢复的是首次部署前或尚未改密的数据库，必须先用 `admin/admin` 登录并强制改密；在改密完成前代理 API 和敏感管理 API 会被拒绝，`ready` 也会失败。

## 密钥和保留策略

- 原主密钥是恢复 NVIDIA Key 的必要条件，必须与数据库备份分开保管并定期验证可取得。
- 数据库备份包含敏感加密数据，应限制访问、加密传输和加密静态存储。
- 备份文件不得上传到 Git、公共对象存储、Issue、聊天记录或日志。
- 废弃备份和包含主密钥的介质应按组织的凭证销毁流程处理。
- 备份恢复不能替代 HTTPS。第一轮普通 HTTP 部署仍会明文传输管理员密码、Cookie、Access Key、提示词和响应；当前版本不是安全生产部署，禁止写成安全公网部署。HTTPS 属于后续迭代。

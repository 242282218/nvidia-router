# 全模块稳定性测试方案（AI 驱动版）

> **定位**：本方案不是脚本手册，而是 **AI 测试分析师的操作手册**。所有测试由 AI 主观能动执行：AI 自主设计用例、自主调用 `vida反代` 全链路、自主分析现象、自主给出结论。禁止用硬编码脚本替代 AI 判断。
>
> **闭环**：测试 → 单维报告 → 总分析报告 → Debug/代码分析 → 修复建议 → 回归验证。测试只是输入，**总分析与代码级 Debug 才是输出**。
>
> **适用对象**：`vida反代`（`NVIDIA API 路由器`）—— OpenAI-compatible 转 NVIDIA 的调度与代理层。稳定性 = 模型能力波动 + 基础设施波动，需分层归因。
>
> **版本**：v3.0 / 2026-08-19（v1 模型 8 维 → v2 全模块 14 维 → v3 测试+分析+Debug 闭环）

---

## 0. 核心原则

1. **全链路探针**：所有请求必须走 `下游 AccessKey -> 路由器 -> 代理池(内置 XApi) -> NVIDIA`，Mock 只验协议，不算稳定。
2. **AI 主观驱动**：用例、强度、判定均由 AI 根据当前上下文动态决策，不预设固定阈值。AI 需解释"为什么这样判"。
3. **分层归因**：每次异常必须回答——是模型/路由器/代理池/Key池/认证/可观测性哪一层引入。
4. **零秘密落地**：Key、AccessKey、XApi URL 只走运行时注入，不写入文档、日志、报告正文。
5. **基础设施与模型同等重要**：代理池、Key池等模块的不稳定会放大为模型维度的偶发失败，必须独立度量。
6. **并行优先、冲突隔离**：不冲突的任务必须并发执行以压缩单次测试时间；冲突任务（压测/隔离/破坏性）严格隔离时段，避免相互污染。通过并行子代理将 70min 串行压缩至 30min，加速迭代。

## 1. 模型选型策略（AI 自主挑选）

### 1.1 挑选逻辑（AI 每次执行前重评估）

不维护静态清单。AI 每次测试前执行：

1. 读取 `GET /admin/api/models`（或 `GET /v1/models` 白名单）+ `internal/upstream/nvidia/descriptor.go:reasoningHints()` 的 hint 表，得到当前已接入模型。
2. 按四个象限打分，选 **每象限 1-2 个代表**，总数控制在 6-10 个，覆盖能力边界与稳定性风险：

| 象限 | 挑选标准 | 候选池（示例，需 AI 验证当时可用性） |
|---|---|---|
| **前沿推理** | 支持 `reasoning_effort`/`thinking`，上下文长，社区关注度高 | `deepseek-ai/deepseek-v4-flash-0731`、`deepseek-ai/deepseek-r1`、`z-ai/glm-5.2`、`minimaxai/minimax-m3`、`qwen/qwq-32b` |
| **通用 Chat 基座** | 非推理但高频使用，验证路由器基础透传 | `meta/llama-3.x-*`、`mistralai/mistral-*`、`moonshotai/kimi-k2*`（以白名单实际为准） |
| **长上下文** | 标称 32k/128k+，用于长输入稳定性 | 从白名单筛选 `supports 128k` 的模型，优先 GLM/DeepSeek/Qwen 长窗版本 |
| **特殊能力** | Vision / Tools / Embedding / Audio，用于兼容性 | `supports_vision=true` 的 Chat 模型、`embedding` 模型、`asr`/`tts`（需 `capability_verified_at` 非空） |

### 1.2 AI 选型 Prompt 模板

```text
你是 vida反代 的模型稳定性测试分析师。

任务：从以下白名单中挑选 6-10 个值得测试的前沿模型。

白名单：
{{models_json}}

挑选要求：
- 覆盖 推理/通用/长上下文/特殊能力 四象限
- 优先选 近期社区讨论度高、NVIDIA 上实际可用、有明确能力标签 的模型
- 排除 已知 410 Gone（如裸 deepseek-v4-flash）或 capability_verified_at 为空的 Audio
- 对每个入选模型说明：为什么值得测、测什么稳定性风险

输出：Markdown 表格 | 模型 | 象限 | 入选理由 | 风险点 |
```

### 1.3 采样策略

本项目为免费中转，稳定性是唯一重点，不做费用/计费评估。采样按稳定性覆盖度控制：

- 冒烟/日巡检：每模型 1-3 次轻量探针（`max_tokens=64-128`）。
- 周深度：每模型 10 次重复 + 1 次长任务。
- 月全量/Soak：10min 长任务仅对 1-2 个核心推理模型执行（见 17.2 并行编排）。
- 每次报告统计探针数与成功率，不估算费用。

## 3. D1 长任务稳定性（最详细）

### 3.1 四类长任务定义

| 类型 | 定义 | 典型水位 | 风险 |
|---|---|---|---|
| **长输入** | 单次 `messages` 携带大量上下文 | 8k / 32k / 128k tokens 三档 | 上下文截断、中间遗忘、位置偏见 |
| **长输出** | `max_tokens`/`max_output_tokens` 要求大段生成 | 4k / 8k / 16k | 提前截断、循环重复、reasoning 挤占 content、`finish_reason=length` |
| **长思考** | `reasoning_effort=high/max` 或 `thinking.budget_tokens` 大 | budget 512 / 8192 / 32768 | 首字节超时（>60s）、idle 窗口不足、流式 reasoning 丢段 |
| **长会话** | 10/20/50 轮连续对话 | 10 轮 / 20 轮 / 50 轮 | 角色遗忘、工具上下文污染、上下文窗口溢出策略 |

AI 需四类都测，不可只测其一。长会话需在同一 `conversation` 内连续调用，不开新会话。

### 3.2 AI 执行 Prompt 模板（长任务）

```text
你是长任务稳定性分析师。目标：评估 {{model}} 在四类长任务下的稳定性。

路由器：{{base_url}} / AccessKey 已注入 / 代理池内置
模型：{{model}} (kind={{kind}}, supports_reasoning={{flag}})

请自主设计 4 组探针（每类 1 组，必要时加对照）：
- 长输入：构造 8k/32k 上下文（可用重复段落+关键事实埋点），要求模型复述埋点事实
- 长输出：要求生成 4k+ 字的结构化文档（带章节），检查截断与重复
- 长思考：用 high/max 强度解一道需多步推理的题目，检查 reasoning 是否产出及占比
- 长会话：设计 10 轮递进任务（每轮依赖前轮结果），检查一致性

对每组记录：HTTP 状态、总耗时、首字节、reasoning 长度、content 长度、finish_reason、SSE [DONE]、是否循环/截断/遗忘。

最后给出：
1. 四类分别的稳定性评级（稳/波动/不稳）及证据
2. 归因：路由器 vs 上游 vs 代理池
3. 建议：超时窗口、预算分配、是否需自动适配
```

### 3.3 AI 分析要点（主观）

- **长输入**：埋点召回率是否随长度衰减？是否存在"中间丢失"（lost-in-the-middle）？路由器是否对超长请求返回结构化 413 而非 502？
- **长输出**：`finish_reason` 分布？是否出现重复句/循环段？`reasoning` + `content` 总和是否超过 `max_tokens` 导致 content 被挤占（见 GLM 实测 `max_tokens=64` 时 content=0）？
- **长思考**：同一题目 low vs high 的 reasoning 长度是否单调递增？首字节是否随强度线性增长？是否触发 `stream_first_token_timeout_ms` / `stream_idle_timeout_ms` 超时？
- **长会话**：第 10 轮是否仍记得第 1 轮的关键约束？工具调用历史是否污染后续轮次？

## 4. D2 思考强度自适应（核心）

### 4.1 测试目标

回答三个问题：

1. **能否支持思考**：模型是否在显式参数下产生 `reasoning_content`/`reasoning`，默认不带参数时是否为 0（预期行为，不算缺陷）。
2. **支持的强度**：`none/auto/minimal/low/medium/high/xhigh/max` 哪些档位真实生效，哪些被归一化或忽略。
3. **系统是否自动适配**：路由器是否需为特定模型自动注入 `chat_template_kwargs` / `thinking` 等字段，哪些模型需要、哪些不需要。

参考已验证行为（`docs/NVIDIA思考参数实测与优化方案报告.md`）：

- GLM-5.2：默认 0，显式 `reasoning_effort=high` 或 `thinking={type:enabled}` 有 reasoning。
- DeepSeek V4 Flash：`thinking:"low"` 字符串形式返回 400，对象形式 `{type:enabled}` 可用；无 kwargs 时可能挂起 90s+。

### 4.2 AI 执行 Prompt 模板（思考强度）

```text
你是思考强度自适应分析师。目标：判断 {{model}} 的思考支持度与系统适配需求。

请按以下阶梯执行，记录 reasoning 长度、content 长度、HTTP 状态、耗时：
1. 默认（不带任何 reasoning 字段）— 预期 reasoning=0
2. reasoning_effort=low / medium / high 三档
3. thinking={type:enabled} / {type:enabled,budget_tokens:512} / {type:disabled}
4. 错误形状：thinking:"low" 字符串（预期 400）
5. 如模型支持 thinking 字符串强度，尝试 reasoning/thinking 混用（预期 400 ambiguous）

对 Responses 同步验证：reasoning.effort=high 时 output 是否含 reasoning+message 双 item。

分析要求：
- 绘制 强度->reasoning长度 曲线，判断是否单调、是否区分度不足（如 low/high 长度接近则说明上游托管层未区分）
- 判断是否需要路由器自动注入：仅当 无参数挂起/400 但显式对象参数成功 时才建议注入，且必须限定模型 ID，不全局注入
- 明确区分"强度不区分"是上游托管限制还是路由器归一化问题（查 internal/compat/reasoning.go 的 nearestLevel 逻辑）
```

### 4.3 判定指引（AI 主观）

- **支持良好**：high 的 reasoning 长度显著 > low，且 `finish_reason` 正常，首字节在阈值内。
- **需适配**：无参数挂起但显式参数成功 → 建议模型级注入（参考 DeepSeek 案例，需直连+代理双路径复现）。
- **上游限制**：low/high 长度接近 → 标注"托管层强度区分度不足"，不归因于路由器。
- **协议缺陷**：字符串 thinking 返回 400 是预期拒绝，不算不稳定。

## 5. D3 输出强度稳定性

### 5.1 子项

1. **重复方差**：同一 prompt 重复 10 次，统计 content 长度 CV、reasoning 长度 CV、提前截断率。
2. **边界强度**：`max_tokens` 刚好够用 / 远超需求 / 限制过严 三档，观察 `finish_reason` 与 reasoning 挤占。
3. **流式 vs 非流式一致性**：同一模型、同一 prompt，流式与非流式的内容长度与结构是否一致。
4. **格式遵循**：`response_format: json_object` 或"Reply with exactly: ok"类指令的遵循率。

### 5.2 AI Prompt 模板

```text
你是输出强度稳定性分析师。目标：评估 {{model}} 输出的方差与边界行为。

执行：
- 选一个确定性 prompt（如"Reply with exactly: ok"或 JSON 格式要求），重复 10 次，记录长度、是否截断、是否重复句
- 用同一长输出任务分别测 max_tokens=64/512/4096，记录 finish_reason 与 content 完整性
- 同一任务分别用 stream=false/true，校验流式拼接后是否与非流式一致（含 reasoning）
- 尝试 response_format=json_object，要求输出合法 JSON，测 5 次成功率

分析：输出是否稳定（CV 大小）、是否易循环、流式是否丢尾、格式遵循是否可靠。给出"适合确定性任务/不适合"的建议。
```

## 6. D4 工具调用兼容性

### 6.1 子项

| 子项 | 探测点 | 预期 |
|---|---|---|
| **Tool 定义归一化** | Chat `tools:[{type:function,function:{name,parameters}}]` vs Responses 扁平形状 | `internal/compat/tools.go:NormalizeTools` 是否正确归一化，混用形状是否 400 |
| **tool_choice 约束** | `none/auto/required` + 指定函数名 | `required` 无 tools 时是否 400；指定不存在函数是否 400 |
| **单轮工具调用** | 1 tool + 1 call，验证 `tool_calls` 结构与 `arguments` JSON 合法性 | `arguments` 是否为合法 JSON 字符串，`compactJSON` 是否生效 |
| **多工具并发** | 3-5 个 tool 定义 + 要求模型并行调用 2+ | 是否支持 `tool_calls` 数组多项，索引是否连续 |
| **多轮工具循环** | user -> assistant tool_calls -> tool 结果 -> assistant 终答 | 第二轮是否正确携带 `tool` 角色消息，上下文是否污染 |
| **流式 tool delta** | `stream:true` + tools，观察 `delta.tool_calls` 增量 | 是否按 `index` 增量拼接，`arguments` 是否分片到达 |
| **Vision + Tools 组合** | `supports_vision && supports_tools` 模型同时传图片与 tools | 是否同时生效，还是互斥拒绝 |

### 6.2 AI Prompt 模板（工具调用）

```text
你是工具调用兼容性分析师。目标：评估 {{model}} 经 vida反代 的工具调用全链路稳定性。

请自主设计递进式探针（每步记录 HTTP 状态、tool_calls 结构、arguments 合法性、耗时）：
1. 单工具：定义 weather(city) 工具，要求模型调用它（tool_choice=auto），验证返回的 tool_calls[0].function.arguments 是否为合法 JSON
2. 多工具：定义 3 个工具，要求模型根据问题选择正确工具，测 5 次选择准确率
3. tool_choice 约束：分别测 none/auto/required/指定函数名，验证拒绝策略
4. 多轮循环：发起一轮工具调用，注入 tool 结果，再让模型生成终答，验证上下文连续性
5. 流式：同一单工具任务用 stream:true，验证 delta.tool_calls 是否按 index 增量到达且最终可拼接为完整 JSON
6. 组合（若模型支持 vision）：同时传 base64 图片 + tools，验证是否兼容

分析：
- 归一化是否正确（扁平 vs 嵌套形状）
- 是否支持并发 tool_calls（多项）
- 流式拼接是否可靠（有无丢 index 或 arguments 截断）
- 多轮是否污染（第二轮是否记得工具定义）
- 给出"工具调用可用/部分可用/不可用"的结论与规避建议
```

## 7. D5 协议与参数兼容性

### 7.1 覆盖矩阵

| 接口 | 方式 | 关键参数 | 预期 |
|---|---|---|---|
| `GET /v1/models` | — | — | 白名单过滤，不透传上游全量 |
| `POST /v1/chat/completions` | stream false/true | `messages` 角色、`reasoning_*`、`thinking`、`tools`、`tool_choice`、`response_format`、`max_tokens` | 合法透传，不兼容字段 400 |
| `POST /v1/responses` | stream false/true | `input` 字符串/数组、`instructions`、`reasoning.effort`、`max_output_tokens`、`store/conversation/previous_response_id` | 受控转换到 Chat，不支持项 400 |
| `POST /v1/embeddings` | — | `input` 字符串/数组 | 需 `kind=embedding` 模型 |
| `POST /v1/audio/*` | — | `file` + `model` / `input` + `voice` | 需 `capability_verified_at` 非空 |
| 未知 `/v1/*` | — | — | 501 `not_implemented`，不触达 NVIDIA |

### 7.2 AI Prompt 模板

```text
你是协议兼容性分析师。目标：验证 vida反代 的 OpenAI 兼容层边界。

请对 {{model}} 执行：
- Chat：system/user/assistant/tool 四角色消息各 1 次
- Chat：stream false vs true 各 1 次，验证 SSE [DONE]
- Responses：input 字符串 vs 数组，验证 output 结构；尝试 store:true / previous_response_id（预期 400）
```

#### 资源预算与隔离规则

| 规则 | 说明 |
|---|---|
| **QPS 预算** | 共享 Key/代理池时 A 组总计 ≤8 QPS（Soak 2 + 子代理 6），B 组独占时 ≤10 QPS，避免互相限流失真 |
| **模型隔离** | 主代理分配模型时，同模型不分配给 2 个以上子代理；A1/A2 若需同模型则错峰或复用结果 |
| **Key 隔离** | 管理面（M3/M4/M5）用独立 AccessKey，不与模型链路共享，避免限流互染 |
| **状态隔离** | B 组压测前主代理快照池状态（healthy_size/冷却数），B 组后对比，异常则标记污染 |
| **失败隔离** | 任一子代理 429 激增或超时>30s，立即上报主代理，主代理决定降并发或单模型重测，不让失败扩散 |

#### 主代理收敛职责

1. 汇总 Soak + A 组 6 个子代理片段，检查是否有互相限流污染（如某代理 429 激增则标记"并发干扰"并单模型重测）。
2. 串行调度 B 组，B 组期间暂停 A 组未完成请求；B 组每项前后快照池/Key 状态以检测污染。
3. 汇总全量后执行 19.2 横向对比与归因，给出"并行有效/需重测"结论。
4. 若 A 组某代理超时>30s，主代理可提前收敛已完成片段，不阻塞整体进度。

#### 快速迭代策略

| 场景 | 并行策略 | 耗时 |
|---|---|---|
| **冒烟（5min）** | 仅 A4 D5 + M6 健康 + health 检查，单代理即可，无需分组 | 5min |
| **日巡检（20min）** | Soak(可选) + A1/A2/A5 3 代理并行 → B1 抽样 | 20min |
| **周深度（30min）** | 全量 A 组 6 代理并行 → B 组串行 → C 组串行 | 30min |
| **定向诊断（5-10min）** | 仅相关维度单代理，无需并行 | 5-10min |
| **增量回归** | 仅重测变更模块相关维度（如改代理池仅跑 M1 + D6），跳过无关组 | 按需 <15min |

#### 时间收益（AI 需在报告中声明）

| 模式 | 耗时估算 | 说明 |
|---|---|---|
| 串行 | ~70 分钟 | Soak 10min + D1 10min + D2-5 各 5min + M1-M6 各 5min + D6/D7/M6 各 5min 累加 |
| 并行子代理 | ~30 分钟 | Soak 10min 与 A 组 8min 重叠，B 组 15min 串行，C 组 10min，部分重叠后 max 而非 sum |
| 日巡检并行 | ~20 分钟 | 3 代理并行 + Soak 可选 |
| 增量回归 | <15 分钟 | 仅相关维度，无需全量 |
| 加速比 | ~2× 全量 / ~3× 增量 | 单次迭代时间减半，增量更快，加快回归与问题定位 |

- 子代理数建议 4-6 个为宜，过多会因共享 Key/代理池互相限流反而失真。
- 每次并行需在报告"执行说明"中记录：分组、并发 QPS、是否观测到互相干扰。

## 21. Debug 与代码分析（AI 必做）

> **定位**：测试发现"是什么"，本章回答"为什么"和"怎么修"。AI 需像工程师一样读代码、跟链路、定根因，而非仅描述现象。每个 P0/P1 必须关联到本章的 Debug 过程。

### 21.1 Debug 方法论（AI 遵循）

```
现象 → 假设 → 证据 → 代码定位 → 复现 → 修复 → 回归

1. 现象：量化描述（成功率、耗时、错误码、状态变迁），非"好像不稳定"
2. 假设：列出 2-3 个可能根因（模型/路由器/池/认证），不单点归因
3. 证据：日志、监控、池状态、请求元数据，交叉印证（黑盒 D6 vs 白盒 M1/M2）
4. 代码定位：读关键路径源码，指向 file:line + 函数 + 逻辑分支
5. 复现：最小可复现探针（单次请求 or 并发序列），验证假设
6. 修复：给出 最小改动 + 参数调优 + 观测补充 三类方案及 trade-off
7. 回归：修复后重测相关维度，确认不引入新波动
```

## 24. 使用方式（测试→分析→Debug 闭环）

1. **测试**：AI 读取本方案 + 白名单 + 目标机状态，执行 1.2 选型 Prompt；按 17.3 冲突矩阵规划子代理分组，并发派发（A 组 6 代理与 Soak 并行，B 组独占串行）；按需选择维度 Prompt（3-16 章），子代理产出 19.1 片段。
2. **收敛**：主代理按 18 章声明并行细节，按 19.2 stitch 横向对比，汇总 19.1 片段。
3. **总分析**：主代理执行 20.1 Prompt，产出 20.2 总分析报告（含 P0/P1 归因、趋势、修复优先级）。
4. **Debug**：对每个 P0/P1 执行 21.3 Debug Prompt + 21.4 代码分析 Prompt，读 21.2 地图指向的代码，产出 21.5 Debug 报告（含 file:line 根因 + 双方案 trade-off）。
5. **交付**：总分析 + Debug 报告存 `docs/plans/` 或对话交付；修复后按增量回归（17.3 快速迭代）重测相关维度，闭环验证。

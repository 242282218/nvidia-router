## 1. 目标与非目标

### 目标

1. 把 `/system`（系统与观测）中的 **运行状态**、**请求监控** 拆成两个独立导航页面。
2. 两个新页面按 CPA 参考文档的 **布局结构、信息密度、组件层级** 重构：KPI 平铺行、三排/四层栅格、时间格健康时间线、双轴流量趋势、圆角行卡明细表、ranking/feed 列表。
3. 视觉皮肤 **保持 Warm Restraint**：全部颜色、字体、圆角、阴影走 `web/src/styles/theme.css` 既有 token，不引入 CPA 冷蓝色板。

### 非目标（方案 B 明确排除）

- 不改任何后端代码、API、数据库迁移（工作区未提交的 Codex 兼容 WIP 原样保留）。
- 不做「请求记录读取状态」卡（BufferRecorder 状态未暴露 API）。
- 不做 RPM/TPM（30 分钟窗口）KPI（无对应端点）。
- 不做 10 分钟粒度热力图（监控 series 桶粒度：24h→小时桶、7d/30d→天桶）。
- 不改实时请求流、审计日志两个 Tab 的内容。
- 部署到 hangzhou2-2 不在本轮范围，本地验证通过后另行向用户确认。

## 3. 信息架构与路由

### 3.1 路由变更（`web/src/router/index.ts`）


## 4. 运行状态页设计（`/runtime`）

参考 CPA Dashboard 文档的三排结构，全部 Warm token。

### 4.1 KPI 行（6 卡，`UiStatCard`）

| # | 标题 | 主数值 | 辅助行 | tone | icon |
|---|---|---|---|---|---|
| 1 | Key 就绪 | `ready / total` | 启用 N · 停用 N | success | key |
| 2 | 活跃请求 | `active` | （pulse 动点） | neutral | bolt |
| 3 | 队列深度 | `length / capacity` | — | neutral | boxes |
| 4 | 冷却中 | `cooling_down` | 最早结束 HH:MM（无则「无冷却」） | warning | clock |
| 5 | 渠道健康 | `healthy / total`（`model-health/status.ts` 的 displayStatus 口径：healthy/总数，辅助行列 降级 N · 不可用 N · 未检 N） | success | heartbeat |
| 6 | 服务状态 | 接收请求 / 关闭中 | （状态点 + 文本） | success/warning | server |

卡片结构：30px 图标块（tone 色 `color-mix` 10% 背景 + tone 色前景）→ 12px 标题 → `--text-display` 档主数值 → 12px 辅助行。不加 CPA 半圆装饰（Warm 原则：装饰必须解释状态）。

### 4.2 中排三卡

| 卡 | 内容 | 数据源 |
|---|---|---|
| Key 池状态分布 | 四行状态列表（就绪/冷却/失效/停用）：状态点 + 名称 + 数量 + 占比进度条（5px 圆角轨道） | `runtimeApi.getSummary().keys` |
| 渠道健康 | healthy/degraded/unavailable 计数徽章 + 状态最差的 Top 5 模型行（名称 + 成功率 + 状态点），整卡链接跳转 `/channel-status` | `modelHealthApi.getSummary('24h', 'default', 'availability')` |
| 运行参数快照 | Key-Value 只读列表：并发/流式超时、首字节超时、总超时、最大尝试、重试预算、日志保留天数 + 「调整设置」锚点滚动到设置表单 | `runtimeApi.getSettings()` |

### 4.3 运行设置

现有 `SettingsForm` 原样保留，放入可折叠收纳区（默认展开保持现状行为）。

### 4.4 数据流

- summary/settings 沿用现有 5s 轮询 + allSettled + AbortController + 部分失败保旧数据逻辑。
- model-health 摘要独立 30s 轮询，失败静默保旧值（与 summary 一致的容错策略）。
- 保留「每 5 秒自动刷新 · 更新于 HH:MM:SS」状态行与错误重试条。

## 5. 请求监控页设计（`/monitoring`）

参考 CPA 实时监控文档的四层结构。标题「请求监控」，副标题沿用现文案。

### 5.1 筛选面板（白卡两行，重构 `MonitoringFilterForm` → `MonitoringFilterPanel`）

- 行 1：时间范围 segmented（24 小时/7 天/30 天）+ 搜索框（`search` 字段，搜索 icon 右置）+ 刷新按钮（含 loading 态）+ 清空筛选按钮。
- 行 2：六个等宽筛选控件：模型 `model_id`、端点 `endpoint`、Access Key `access_key_id`、NVIDIA Key `nvidia_key_id`、结果 `outcome`、状态码 `status`。
- 筛选逻辑（apply/reset/URL 同步）沿用现有实现，仅重排布局。

### 5.2 KPI 行（8 卡，`UiStatCard`）

| # | 标题 | 主数值 | 辅助行 | tone |
|---|---|---|---|---|
| 1 | 请求数 | request_count | 总尝试 N（含换 Key 重试） | neutral |
| 2 | 成功率 | success_rate % | 成功 N · 失败 N · 取消 N | success |
| 3 | 失败数 | failure_count | 取消 N（客户端中断，不计失败） | danger |
| 4 | 平均耗时 | average_duration_ms | 平均排队 N | neutral |
| 5 | TTFT P50 | first_token_p50_ms（无则 —） | — | info |
| 6 | TTFT P95 | first_token_p95_ms（无则 —） | — | info |
| 7 | 首字节 | average_first_byte_ms | — | neutral |
| 8 | Token 总量 | prompt+completion | 输入 N · 输出 N | info |

- 此布局替代 Warm 批③在旧页的「3 主指标 + 次要指标带」（用户已确认新页面按 CPA 平铺）。
- 保留口径说明行（窗口、来源）与 stale/错误横幅的现有行为。

### 5.3 中排三卡（栅格约 `2fr : 2.2fr : 1fr`，≥1500px 三列；中屏两列；<768px 单列）

| 卡 | 内容 | 实现 |
|---|---|---|
| 流量趋势 | 新 `TrafficChart`：Token 柱（success 色低饱和）+ 请求折线（accent 色 2px）双 Y 轴；横向浅虚线网格；右上自定义小图例（小圆点 + 12px 文字）；X 轴稀疏标注（24h 每 4 小时一个、7d/30d 每天） | 数据 `snapshot.series` |
| 健康时间线 | 新 `HealthTimeline`：时间格一行（24h→24 格；7d→7 格；30d→30 格），格高约 28px、4px 间距、6px 圆角；hover title 显示 时间区间/请求/成功/取消/失败/成功率/平均延迟 | 数据 `snapshot.series` |
| 结果分布 | 三行进度列表（成功/取消/失败）：色点 + 名称 + 数量 + 百分比 + 5px 进度条；替代现有 ChartDonut 用法 | `summary` 计数 |

`HealthTimeline` 格状态判定（优先级自上而下）：

```text
bucket 起点 > now            → 空心格（surface 底 + border 虚框）
request_count === 0          → 无数据（--color-sunken）
failure_count > 0            → 失败（danger，透明度按失败率分 3 档，对齐 ChartHeatmap 档位）
canceled_count > 0           → 取消（warning，同样 3 档）
其余（有请求且无失败/取消）   → 成功（success，按请求量相对值 3 档）
```

### 5.4 下排两卡 + 明细

| 卡 | 内容 | 实现 |
|---|---|---|
| 模型成本排行 | `CostPanel` 改造为 ranking list：名次徽章（前三 accent/info/warning 浅底）+ 模型名 + 成本 + 占比进度条（第一名 accent，其余低饱和）；数据与折算逻辑不变 | `statisticsApi.getCosts()` |
| 最近失败请求 | 新 `FailureFeed`：最多 8 条，每条两行（时刻 + 模型 / 错误码 + 耗时），1px 分隔线；点击带入筛选（model_id + outcome=failure） | `statisticsApi.getLogs(range, {outcome:'failure'}, 1, 8)` |

### 5.5 请求明细表（`MonitoringLogsTable` 行卡化）

- 从 DataTable 改为 CSS Grid 圆角行卡（`RequestRowCard`），行高约 88px、行距 8px、`--radius-panel` 圆角、1px 浅分隔线。
- 核心列（Grid 12 列比例）：密钥/模型（两行）｜端点 + 流式徽章｜状态（outcome 色点 + http_status）｜耗时两行（首字 first_token_ms ?? first_byte_ms / 总耗 duration_ms；标签 12px muted + mono 数值，不引入语义色）｜Token 两行（总量 + ↑输入/↓输出）｜重试（attempt_count > 1 时 warning 徽章）｜时间两行（日期 + 时刻）。
- 行点击展开详情区：queue_ms、reasoning（requested/wire_fields/present/chars）、route_mode、request_id、upstream_request_id、error_code。
- 分页（页码/跳转/每页大小）、空态（无数据 vs 无匹配）、加载态、筛选联动全部保留现有行为。

## 7. 主题适配硬规则

1. 颜色只用 theme.css 既有 token 与 `color-mix` 派生；**不新增裸色值**（新增文本/控件配对须先过 `scripts/calc_contrast.py` 并登记对比度表）。
2. 辅助文字 ≥12px（Warm 硬规则）；CPA 的 9~10px 小字不照搬，密度通过 12px 卡间距（`--space-3`）、紧凑内边距（16px）实现。
3. 圆角：卡片 `--radius-panel`（12px）、控件 `--radius-control`（8px）、进度条 999px；不引入 >12px 卡片圆角。
4. 阴影只用 `--shadow-xs/sm`；hover 边框加深一格，无位移/缩放。
5. KPI 主数值用 `--text-display` 档；数字统一 `font-mono-data`；状态色只落在图标块、状态点、进度条、徽章等局部，不整卡染色。
6. 动效遵守现有规范：120~300ms 状态过渡，无入场飞入/数字跳动动画。

## 8. 数据流与错误处理

- 两页沿用现有模式：`AbortController` + 序列号防竞态、`Promise.allSettled` 部分失败保旧数据、后台轮询失败置 stale 标记而非闪错。
- 请求监控新增一次 `getLogs(outcome=failure)` 调用与主刷新合并（`Promise.all` 内并列，失败仅置对应卡错误态，不拖垮整页）。
- 所有新卡必须独立错误态（"获取失败 + 重试"），单卡失败不清空整页（CPA §73 原则）。
- 骨架屏沿用 `UiSkeleton`，保持各卡原高度避免布局跳动。

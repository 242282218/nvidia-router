# 星空代理池适配与 DeepSeek V4 Flash 稳定性设计

日期：2026-08-10

## 1. 背景与目标

本设计覆盖三个工作目录：

- `D:\PROJECT_ZZZZZZZZZ\nvida反代`：NVIDIA OpenAI-compatible 路由器；
- `D:\PROJECT_ZZZZZZZZZ\星空代理池`：独立 HTTP/HTTPS 正向代理池；
- `D:\PROJECT_ZZZZZZZZZ\服务器管理\hangzhou2-2`：目标服务器部署资产。

目标是修正两个服务之间的代理协议契约，针对 `deepseek-ai/deepseek-v4-flash-0731` 的慢首 token 和长流式响应完成稳定性优化，在 `hangzhou2-2` 公开部署反代与代理池，并将两套代码分别发布到 GitHub `main`。

当前两套本地基线的 Go 测试、Go vet、前端测试和前端构建均通过。反代存在大量未提交功能改动，后续必须在现状上增量修改，禁止重置。代理池是尚无首个提交和远端的 Git 仓库。

## 2. 已确认约束

1. 保持反代与代理池为两个独立服务和两个代码仓库。
2. `nvidia-router` 使用现有 GitHub 仓库并创建 `main`；`star-proxy-pool` 创建独立私有仓库和 `main`。
3. `hangzhou2-2` 的真实密钥、SSH 私钥和运行数据不上传 GitHub。
4. 反代和代理池均开放公网端口；容器内反代仍通过 Docker 内网访问代理池。
5. DeepSeek 最终执行 30 分钟真实模型测试，并发为 2。
6. 当前公网入口为 HTTP；在没有 HTTPS 网关前，认证信息不具备传输加密。

## 3. 方案选择

### 3.1 推荐：独立服务 + 标准正向代理契约

- 路由器负责 Access Key、NVIDIA Key、模型映射、请求重试和 OpenAI 协议。
- 代理池负责星空地址采集、验证、出口选择、粘滞、CONNECT 隧道和代理健康。
- 两者通过标准 HTTP 正向代理和 Basic `proxy:<secret>` 认证连接。
- 连接本身作为隐式租约，不新增专有租约 RPC。

该方案复用现有实现、故障域清晰、可独立回滚，是最小可行且正确的边界。

### 3.2 未采用方案

- 反代直接调用星空 XApi：会重复代理 TTL、测活、轮换和失败隔离逻辑。
- 把代理池嵌入反代：耦合采集任务、长连接转发、管理 UI 和发布周期，也失去被其他服务复用的能力。

## 4. 数据面设计

### 4.1 地址与认证

- 容器内地址：`http://proxy-pool:8080`。
- 公网代理地址：`http://<server>:18081`。
- 代理认证使用 `Proxy-Authorization: Basic <proxy:PROXY_AUTH_KEY>`。
- 公网实例与内部服务使用不同的强随机认证密钥。

### 4.2 每 NVIDIA Key 出口粘滞

现有实现把 `X-XK-Session` 写入 HTTPS 隧道内的 NVIDIA 请求。代理池在外层 CONNECT 建立时选出口，因此看不到该头；目标 NVIDIA 反而可能收到内部会话标识。共享 transport 还会让多个 NVIDIA Key 复用同一个 CONNECT。

修正方案：

1. 请求 handler 继续通过 context 携带 NVIDIA Key 会话。
2. `xkproxy.Manager.Acquire` 将会话加入 transport cache key，不同 Key 不共享 transport/CONNECT。
3. `http.Transport.GetProxyConnectHeader` 在外层 CONNECT 注入 `X-XK-Session`。
4. 目标 NVIDIA 请求不再包含该头。
5. 会话值使用稳定摘要标签，不暴露数据库 Key ID 或密钥内容。
6. sticky TTL 不超过出口代理 TTL；出口失效时重绑，已提交的流不迁移。

### 4.3 重试和错误归因

- 代理池的 407、502、503、504、CONNECT 拒绝、无健康出口和拨号/隧道超时统一包装成 `xkproxy.Error`。
- 下游收到 `502 upstream_proxy_unavailable`；这类错误不冷却、禁用或污染 NVIDIA Key 状态。
- NVIDIA 返回的 401、403、429、5xx 和 529 继续使用现有 fault classifier。
- 只在尚未写出请求字节的纯连接故障上做一次 transport replay。
- 请求写出或流提交后禁止跨出口重放，避免重复生成。

### 4.4 长连接

- 连接、响应头、首个 SSE data 和流间 idle 使用独立超时预算。
- 代理池 CONNECT 隧道按滚动 idle deadline 管理；持续有数据的流不会被固定总时长截断。
- 优雅停机等待活动隧道；超出 grace 后关闭。

## 5. 控制面设计

### 5.1 Readiness

- `/healthz` 仅表示进程存活。
- `/readyz` 要求存在可用出口，并反映采集器是否曾成功和是否存在需人工处理的 fatal 上游状态。
- 反代 `/health/ready` 保持本机依赖 readiness；代理不可用由业务请求明确返回，不让容器因短时代理波动频繁重启。

### 5.2 代理健康归因

- 连接/隧道失败计入出口代理失败。
- 验证目标自身异常、客户端取消和已提交响应后的下游断开不得误记为出口故障。
- 修复认证上游 CONNECT：发送 `Proxy-Authorization`，不能使用源站 `Authorization`。
- 补齐认证 HTTP/HTTPS 上游、CONNECT、sticky 和失败归因测试。

### 5.3 管理前端与配置

只做必要修复：

- 补齐 sticky/keepalive runtime 类型与表单契约；
- 替换错误但非空的管理 Key 后重新加载配置；
- 不重做现有管理 UI。

## 6. DeepSeek V4 Flash 优化

### 6.1 模型标识

- 稳定对外别名：`deepseek-v4-flash`。
- 当前 NVIDIA 上游 ID：`deepseek-ai/deepseek-v4-flash-0731`。
- 继续允许管理员配置完整上游 ID。
- bare NVIDIA ID 返回 410 时不做无界自动回退。

### 6.2 请求和预算

- 保留 `thinking` 到 `reasoning_effort` 的兼容转换。
- 稳定性探针使用短提示、流式响应、小 `max_tokens`，不额外引入随机 temperature。
- 部署初值：响应头 120 秒、首 SSE data 180 秒、流 idle 180 秒、预提交重试预算 240 秒、非流式总预算 420 秒。
- 每 NVIDIA Key 最多 2 个并发流；短请求与流式配额分离。

## 7. 可观测性与验收

### 7.1 记录范围

反代记录模型、错误类别、attempt、TTFT、总耗时和流完成状态；代理池记录选择、sticky hit/miss/rebind、CONNECT 失败、隧道时长、出口隔离和采集/验证状态。

不得记录提示词、响应正文、代理密码、Access Key 或 NVIDIA Key。

### 7.2 30 分钟真实验收

测试脚本放在 `scripts/test/`，输出机器可读结果和 Markdown 汇总：

- 请求数和成功率；
- P50/P95 TTFT；
- P50/P95 总耗时；
- HTTP 状态、断流和超时；
- sticky、重试、代理错误 metrics 增量；
- 两容器重启次数差值。

成功标准：

- 首选所有请求完成且无协议错误；
- 若真实上游偶发失败，成功率至少 95%；
- 不错误冷却 NVIDIA Key；
- 无容器重启；
- 不发生跨 Key sticky 串线；
- 所有失败必须能够归因到代理、NVIDIA 上游或客户端阶段。

## 8. 部署设计

### 8.1 拓扑

- `nvidia-router`：公网 `0.0.0.0:3756`。
- `star-proxy-pool`：公网 `0.0.0.0:18081`，容器网络别名 `proxy-pool:8080`。
- 两者加入外部 Docker 网络 `router-internal`。
- 使用非 root、只读文件系统、`cap_drop: ALL`、`no-new-privileges` 和受控 tmpfs。
- 数据目录在部署前创建并设置为容器 UID 可写。

### 8.2 安全

- Proxy/Admin/Metrics Key 分离，至少 16 字符。
- UFW 对公网代理端口启用 LIMIT；健康接口开放，ready/admin/metrics 保持鉴权。
- 明确 HTTP 明文风险，后续应通过独立 HTTPS 网关收敛公网入口。

### 8.3 发布和回滚

1. 备份反代数据卷、代理池 runtime data 和两套 `.env`。
2. 构建带不可变标签的新镜像。
3. 先升级代理池并验证，再升级反代。
4. 验证 health、ready、认证、内部和公网代理路径。
5. 执行 30 分钟 DeepSeek 实测。
6. 失败时恢复旧镜像和备份；成功后写入部署记录。

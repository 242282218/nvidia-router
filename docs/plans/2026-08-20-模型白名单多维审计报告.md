## 3. 🔴 P0 缺陷：白名单能力位错误导致思考能力被路由器拒绝

**现象**：`nvidia/nemotron-3-ultra-550b-a55b` 与 `stepfun-ai/step-3.7-flash` 携带 `reasoning_effort` 的请求被返回 **501 `not_implemented`**（89ms / 109ms，未触达上游）。

**证据链**：

1. 两个模型在 compat 阶段**稳定输出 `reasoning_content`**：nemotron 8/8 用例均有 45–209 字符思考；step 7/8 用例有 81–291 字符思考。→ 上游确实具备思考能力。
2. 白名单仍标 `supports_reasoning=false`，`internal/httpapi/v1/chat.go:454-461` 将 `ErrCapabilityUnsupported` 映射为 501 → **路由器主动拒绝**，非上游行为。
3. 修复迁移 `internal/database/migrations/038_nvidia_reasoning_capability_backfill.sql` 仅存在于本地工作区（untracked），**线上镜像 `bf409ce` 不含该迁移**。

**放大后果（本次实测到的次生失败）**：因为无法下发 `reasoning_effort=none`，step 的思考不受约束——

- output 阶段 **4/4 全部失败**，240–262s 后 502/504；
- long 阶段 `long_multi_turn_chain` 240s 超时失败；
- `long_output_stream_4k` TTFT **173 秒**，最终 `content_chars=0`、18464 字符全是思考。

即：**step 61% 的通过率里，7 个失败中有 6 个可直接追溯到这一个能力位错误**。同阶段能下发 `reasoning_effort=none` 的另外三个模型 output 阶段全部 4/4 通过。

**处置**：部署迁移 038。本地已验证 `go vet ./...` 干净，`internal/database`（含 `migration_038_test.go`）、`internal/upstream/nvidia`、`internal/router`、`internal/fault`、`internal/httpapi/...` 测试全绿。

## 4. 🟠 P1 缺陷：长文任务思考吞掉全部输出预算，返回空内容

`long_output_stream_4k`（4096 token 预算，要求 ≥2500 词技术设计文档）：

| 模型 | 思考字符 | 内容字符 | TTFT | finish | 判定 |
|---|---|---|---|---|---|
| `nvidia/nemotron-3-ultra-550b` | 236 | **14274** | 5.5s | length | 健康 |
| `z-ai/glm-5.2` | 7374 | **11118** | 20.4s | length | 正常 |
| `minimaxai/minimax-m3` | 17770 | **0** | 8.4s | length | 🔴 **空交付** |
| `stepfun-ai/step-3.7-flash` | 18464 | **0** | 173.3s | length | 🔴 **空交付** |

关键点：**m3 是在显式 `reasoning_effort=low` 下出现的**，不能用"没设 effort"解释；step 则是 §3 能力位错误的直接后果。

协议层完全合法（200 + `[DONE]` + `finish_reason=length`），但**客户端拿到的是空字符串**。这与 memory.md 中 `hy3` 的预算现象同类，但首次在 NVIDIA 渠道复现，且发生在低思考档。

**建议**：对已知会把预算耗在思考上的模型，在 descriptor 层面为 reasoning 设上限预算（`thinking.budget_tokens` 或按比例裁剪），保证内容段有剩余预算；至少在 `content_chars=0 && reasoning_chars>0 && finish=length` 时向调用方给出明确提示而非静默空串。

## 5. 🟡 P2：代理池瞬时无租约导致 8 次快速 502

- 分布：m3 ×4、glm-5.2 ×3、step ×1，全部集中在 compat 阶段（4 路并发），失败耗时 **51–135ms**（未触达上游）。
- 渠道快照：审计开始 `healthy 26/26`、结束 `healthy 19/19`，两次均 `panic_mode=0`、`upstream_overloaded=0`。
- 结论：**池未枯竭，但并发下租约瞬时耗尽**。与 memory.md 既有结论一致——`XK_EXPECTED_QTY` 即 XApi 的 `qty` 参数，当前套餐 `qty>2 → 506`，因此生产必须保持 `2`，这是**套餐物理边界，不是代码缺陷**。fail-safe 行为正确（快速失败而非静默直连）。
- 影响面：4 路并发下约 **8/104 ≈ 8%** 的请求受影响。

## 7. 思考强度（thinking，22 例）

仅 m3 与 glm-5.2 被白名单标记为支持（另两个见 §3）。两者 **各 10/10 通过**，全部 8 个档位（none/low/medium/high/minimal/xhigh/max + `thinking.budget_tokens`）均被接受。

`reasoning_chars` 随档位变化：

| 档位 | `minimax-m3` | `z-ai/glm-5.2` |
|---|---|---|
| none | **0** | **0** |
| low | 90 | 758 |
| medium | 142 | 686 |
| high | 101 | 882 |
| minimal | 144 | 1039 |
| xhigh | 135 | 655 |
| max | 92 | 941 |
| `thinking: enabled(512)` | 87 | 505 |

**结论**：`none` 与 `thinking:disabled` 的**关断是可靠的、确定性的**（两模型、两种写法全部归零）；但 low→max 之间**不单调**，实际表现为「开/关二值 + 波动」，档位粒度对上游不产生可观测的强度梯度。glm-5.2 的思考量级是 m3 的 **5–8 倍**。

## 11. 建议处置（按优先级）

1. **立即部署迁移 038**（P0）——修正两个模型的 `supports_reasoning`。预计直接消除 step 的 6/7 次失败，其通过率有望从 61% 升至 ~90%。本地验证已全绿。
2. **补预算保护**（P1）——对 `content_chars=0 && reasoning_chars>0 && finish=length` 的响应，或在 descriptor 层限制 reasoning 预算比例，避免空交付静默返回。
3. **停用或降权 OpenCodeFree 三个模型**，直到网关恢复；`opencodefree.Client.Models` 的定时禁用应覆盖整渠道宕机场景。
4. **停用 `deepseek-ai/deepseek-v4-flash-0731`**——120s 无首字节，对任何客户端超时配置都不可用。
5. **补跑未执行的 4 个阶段**（stability / concurrency / errors / responses）——本次的稳定性维度**尚无结论**，且并发维度正是 §5 的定量前提。建议在 038 部署后重跑全量，同时得到修复前后对照。
6. 文档化 glm-5.2 流式 4.3s 空档，客户端 idle 超时不应低于 10s。

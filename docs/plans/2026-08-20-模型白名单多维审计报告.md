## 3. 🔴 P0 缺陷：白名单能力位错误导致思考能力被路由器拒绝

**现象**：`nvidia/nemotron-3-ultra-550b-a55b` 与 `stepfun-ai/step-3.7-flash` 携带 `reasoning_effort` 的请求被返回 **501 `not_implemented`**（89ms / 109ms，未触达上游）。

**证据链**：

1. 两个模型在 compat 阶段**稳定输出 `reasoning_content`**：nemotron 8/8 用例均有 45–209 字符思考；step 7/8 用例有 81–291 字符思考。→ 上游确实具备思考能力。
2. 白名单仍标 `supports_reasoning=false`，`internal/httpapi/v1/chat.go:454-461` 将 `ErrCapabilityUnsupported` 映射为 501 → **路由器主动拒绝**，非上游行为。
3. 修复迁移 `internal/database/migrations/038_nvidia_reasoning_capability_backfill.sql` 仅存在于本地工作区（untracked），**线上镜像 `bf409ce` 不含该迁移**。

**放大后果（本次实测到的次生失败）**：因为无法下发 `reasoning_effort=none`，step 的思考不受约束——

- output 阶段 **4/4 全部失败**，240–262s 后 502/504；
- long 阶段 `long_multi_turn_chain` 240s 超时失败；
- `long_output_stream_4k` TTFT **173 秒**，最终 `content_chars=0`、18464 字符全是思考。

即：**step 61% 的通过率里，7 个失败中有 6 个可直接追溯到这一个能力位错误**。同阶段能下发 `reasoning_effort=none` 的另外三个模型 output 阶段全部 4/4 通过。

**处置**：部署迁移 038。本地已验证 `go vet ./...` 干净，`internal/database`（含 `migration_038_test.go`）、`internal/upstream/nvidia`、`internal/router`、`internal/fault`、`internal/httpapi/...` 测试全绿。

## 5. 🟡 P2：8 次快速 502（归因已更正）

- 分布：m3 ×4、glm-5.2 ×3、step ×1，**全部集中在 compat 一个阶段**，其余四阶段（含同为 4 并发、22 例的 thinking）零失败；三个模型在同一时间窗内一起失败、一起恢复。失败耗时 **51–135ms**（未触达上游）。
- 渠道快照：审计开始 `healthy 26/26`、结束 `healthy 19/19`，两次均 `panic_mode=0`、`upstream_overloaded=0`。

> **§5 归因更正（2026-08-20 复查）**：初版判定为「代理池瞬时无租约 / 套餐 `qty=2` 物理边界」。**该结论错误**，三条证据推翻：
> ① `attempt.go:418-422` 把 `ReasonNoHealthyProxy` 映射为 **503** +「upstream proxy **pool**…」，实测 8 次全部是 **502** + 另一条文案；
> ② NVIDIA 路径已接 `AcquireWithWait`（`client.go:432`），空池会轮询等待，首个 tick 250ms，而失败发生在 51–135ms，**根本没进入等待**；
> ③ 复现探针 25 轮 × 3 模型 = 75 次请求全部 200，447 个池采样 `healthy` 在 18–35 波动，从未接近枯竭。
>
> 真实范围收敛为 `ReasonTransportFailed`（出口拨号即死）或 `ReasonProxyRejected`（出口拒绝 CONNECT）二者之一。**当前无法区分**：两者共用 502 与完全相同的文案，`Error()` 返回常量字符串不带 reason，全链路无一处记录它。已在 `attempt.go` 补 `slog.Warn("proxy_error", reason, cause_type, key_id)`，**需部署后再次发生才能定案**。
>
> 另有一条强关联线索：§13 的 638 状态会触发 `ReportHTTPFailure(638)`，把健康出口按 HTTP 失败隔离——同一批被污染的出口很可能正是这 8 次失败的来源。
>
> 区分后的处置方向完全不同：`proxy_rejected` 在 `attempt.go:442` **短路，既不换 Key 也不换出口**，池里另外 25 个健康出口不试，那是真缺陷；`transport_failed` 已是 retryable，方向在采集/验证。

## 13. OpenCodeFree 502 根因（2026-08-20 复查，推翻 §1 判断）

### 事实：网关一直是健康的

从网关容器内、用路由器**同一把 Key** 直连（`scripts/test/opencodefree_authed_probe_remote.py`）：

| 端点 | 结果 |
|---|---|
| `/v1/models` | **200**，返回完整模型列表 |
| `/v1/chat/completions` | **200**，`deepseek-v4-flash-free` 正常回答 |

而经由路由器同一时刻探测（`opencodefree_diagnose_remote.py`）：3/3 模型 502 `upstream_error`，错误文案 **`OpenCodeFree upstream returned HTTP 638`**，候选发现 `/admin/api/models/candidates` 同样 502。

### 根因：内网网关被送去外部出口

网关地址是 Docker 内网主机名（Compose 服务别名，端口 6020），只有本机网络可达。而 `internal/upstream/opencodefree/client.go` 的 `do()` 在代理已配置且启用时，把**每一次**网关调用都送去外部 XApi 出口。出口没有到私有地址的路由，返回非标准状态 **638**，路由器按「未知 ≥300 → 502」映射成 `upstream_error`，表现得像整渠道宕机。

属 `c0cafc7`「代理池接入」引入的回归。

### 二次伤害：污染代理池

638 ≥ 500 会走到 `attemptThroughProxy` 的 `ReportHTTPFailure(638)`，把**完全健康的出口**当作 HTTP 失败隔离——一个配置层错误在持续污染代理池的质量排序。与 §5 的 8 次 502 高度可能同源。

### 修复

`NewClient` 按 base URL 主机判定 `local`：回环、私有网段、链路本地、未指定地址，以及不含点的单标签名（Compose 服务别名）→ 直连，不走代理池。代理的目的是对公网端点隐藏来源地址，对只有本机可达的地址既不可行也无意义。测试覆盖主机分类与「代理必然失败时本地网关仍能取到模型列表」。

**未部署**，线上 OCF 仍为 502。

### 附带发现：网关可用模型远多于白名单

网关 `/v1/models` 还提供 `mimo-v2.5-free`、`nemotron-3.5-lightning-free`、`laguna-s-2.1-free`，以及一批 claude / gemini 模型。

**`muse-spark-1.2-contributor-free` 实测不可用**：非流式 / 长推理 / 流式三个用例全部返回 **403 `RegionError` —「This model is not available in your country.」**，稳定复现。出站由网关自身发起、不经路由器出口池，且 XApi 出口本身即国内，换出口无效。**已决定不支持该模型。**

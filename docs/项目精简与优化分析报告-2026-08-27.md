# 项目精简与优化分析报告（2026-08-27）

## 结论先行

这个项目当前已经不是“简单 API 转发器”，而是一个把协议兼容、模型目录、能力探测、两套上游通道、Key 池、国内代理池、流式修复、请求观测、健康探测和管理前端全部放在同一进程中的控制面与数据面混合系统。复杂度本身不是唯一故障，但它制造了多处重复决策和行为漂移。

Codex 与 Cherry Studio 经常失败的直接原因可以分成三类：

1. **能力门控假阴性（本地 501）**。工具请求在到达上游前会经过模型目录能力检查；`supports_tools=false` 或 `tools_status=unknown` 会直接返回 `capability_unverified`/`not_implemented`。历史探针曾因上游不响应 `tool_choice=required` 把实际支持工具的模型记录成 unknown/unsupported，导致客户端看到“模型不支持工具”。当前版本已允许 `inferred`，但线上 NVIDIA 与 hy3 的能力状态仍不能覆盖所有工具场景。
2. **Responses 只是受控转换层，不是原生 Responses 透传**。它把 Responses 请求规范化后转换为 Chat Completions，并主动拒绝 hosted tools、持久化 response、conversation、background、prompt cache 等能力。Codex 的 function tools 普通路径可以工作，但依赖 hosted tool 或 stateful/background 语义的请求按设计返回 400。
3. **上游代理/provider 瞬态失败（502/503/超时）**。国内出口验证失败、CONNECT 被拒、上游协议异常和 provider 不可用会造成 502/503 或流被截断。这些不是路由器进程崩溃，但当前两套重试和错误映射使它们在不同协议入口表现不一致。

因此，优化重点不是继续堆兼容分支，而是收敛成“一个请求核心、一个能力权威、一个重试/错误分类层”，把探测、健康和管理功能移到数据面之外。代理池和 Responses 适配器仍应保留，它们是国内出口与 Codex 兼容的必要边界；应删除的是重复责任和不可验证的默认行为。

## 4. Codex 与 Cherry Studio 失败分析

### 4.1 Codex

已验证的历史/当前证据：

- Responses 普通流和标准 function tool 路径可以完成；混合工具请求会过滤已知 `namespace`、`web_search`，保留 function tools 后进入上游。
- `exec_command` 历史复测为 2/3 完整，1 次 `response.failed/stream_incomplete`；Chat 工具流可以完成，失败与 OpenCodeFree 提前 EOF/流截断相符，Codex 客户端重连后可继续。
- `internal/protocol/responses/validate.go:47-76` 只允许有限字段；`:94-170` 明确拒绝 stateful response、background、hosted tools 和大部分 `include`。因此 Codex 使用 hosted web search 或持久化/后台语义时，400 是当前协议边界，不是网络故障。
- 官方 Codex 兼容口径是：自定义 provider 优先使用 `wire_api=responses`；Chat Completions 兼容正在被弃用；web search 属于独立 hosted tool，custom provider 默认不拥有。路由器不能声称自己具备完整 Codex hosted tool 能力。

结论：Codex 的“经常失败”由两条链叠加：function tool 请求遇到目录假阴性时是本地 501；function 请求已经放行后，仍可能因 OCF 上游提前 EOF 产生 stream incomplete。Hosted/stateful 能力则是明确的产品边界，应在能力声明中提前告诉客户端。

### 4.2 Cherry Studio

本机 Cherry 日志出现 `The requested model capability is not implemented`、`The selected model does not support tools` 和 `AI stream error`。13:39 左右的失败链路还同时包含 Dify MCP 参数缺失、AgentBay OAuth session 失效、nowledge-mem 连接拒绝，随后模型请求因工具能力门控失败。

必须分层：

1. Cherry 的 MCP 初始化错误属于客户端配置/外部 MCP 服务问题，不能当作路由器 API 故障。
2. Cherry 发送带 tools 的请求时，路由器根据模型目录硬门控；`false/unknown` 在调用上游前就返回 501。即使上游实际能生成 tool call，客户端也看不到上游能力。
3. Cherry 模型 metadata 的 `context_window` 为空/0，客户端无法做上下文预算，也会把小预算思考耗尽误判为“模型不支持”。

结论：Cherry 的主要产品级阻断是“工具能力和上下文元数据不可用”，MCP 报错是独立噪声，应在 UI/日志中显示为不同来源。

## 6. 冗余与过度设计审计

以下是按影响和可删复杂度排序的结果。这里区分“应合并/删除的重复责任”和“虽然复杂但必须保留的业务边界”。

### 6.1 最高优先级：重复热路径

- **shrink：Chat 与 Responses 各自复制 body lease、模型 Resolve、auto-reasoning、observability 和 provider 分支。** 抽出一个统一的 `RequestExecutor`，协议包只负责产生规范化请求和响应适配器；可减少行为漂移和约 100–180 行重复控制流。涉及 `internal/httpapi/v1/chat.go:71-156`、`internal/httpapi/v1/responses.go:56-139`。
- **shrink：OCF Chat 与 OCF Responses 各自维护 retry、500ms 等待、非流式校验和状态映射。** 共享 `ProviderCall`/`TransientPolicy`，Responses 只保留转换和事件重建；预计再减少约 60–100 行重复逻辑。涉及 `internal/httpapi/v1/chat.go:222-369`、`internal/httpapi/v1/responses_opencodefree.go:21-132`。
- **yagni：provider 层同时暴露两套“重试语义”。** NVIDIA 走 `Attempt.Run`、Key pool 和 sticky session，OCF 又在 client 内使用 `proxyAttempts=3` 和自己的 transport retirement。代理池本身不能删，但重试预算、是否已写出、错误分类应由一个共享策略决定，provider 只提供一次调用函数。

### 6.2 最高优先级：能力状态没有单一权威

- **shrink：静态布尔值、数据库 `tools_status`、探针结果、请求硬门控和前端标签同时决定工具可用性。** 这使“实际支持”与“目录说不支持”容易分裂。保留一个 `CapabilitySnapshot`（来源、时间、置信级别、失败原因、过期时间），其余字段由它派生。
- **yagni：将一次探针失败等价为永久不支持。** 上游 502/503/timeout 应保持 unknown/过期，而不是覆盖已有 supported；明确 501 或合法负面响应才可写 unsupported。当前探针已部分修复，但策略需要在数据模型和 UI 中统一。
- **delete：没有证据的全局默认能力。** 不应因为候选发现或旧 migration 自动把工具、reasoning、context 当作可信事实；候选只能生成 `inferred`，不能生成 `supported`。

### 6.3 中优先级：协议边界过宽但契约过窄

- **yagni：在没有原生 Responses 上游的情况下模拟完整 Responses 能力。** 现有转换器必须保留以支持 Codex，但应明确它是“stateless function-tools subset”，不要继续为 stateful/background/hosted tools 增加伪实现。
- **shrink：统一 Responses unsupported 检查。** 现在顶层 allow-list、多个 reject 函数和转换器内的语义校验分散在两处；集中成 feature matrix 后，错误码、文档和模型能力声明可由同一表生成。
- **delete：把未知 `/v1/*` 路径伪装成可用兼容。** 当前统一 501 是正确边界，不应添加 catch-all 转发；应继续保持显式白名单，避免客户端误以为上传、批处理等能力存在。

### 6.4 中低优先级：控制面与数据面混合

- **yagni：请求进程内的多套后台写入者。** model health、capability probe、request buffer/event hub 都直接依赖同一 SQLite；模型删除竞态已在 `6d4b782` 修复，但竞态本身证明职责耦合较高。统一为一个有界 scheduler 和一个 DB writer，探测结果经队列写入。
- **shrink：将事件 Hub 与请求观测分层。** 实时 UI 订阅和长期 request_logs 不需要共享全部生命周期；事件只传摘要，数据库 writer 批量落盘，避免后台探测和用户请求互相影响。
- **native：管理前端不应成为能力真相源。** 前端只展示后端 `CapabilitySnapshot`，不再自行推断 `supports_tools`、`context_length` 或 reasoning 状态。

### 6.5 不建议删除的复杂度

- 国内 XApi 出口、CONNECT、代理轮换与坏出口 retirement 是业务前置条件，不能按“简单转发”删除。
- Key pool、sticky session、流式首字节/空闲超时是 NVIDIA 上游稳定性所需，应该统一而不是移除。
- Responses -> Chat 转换是 Codex 当前可用的兼容边界，除非产品明确放弃 Codex Responses，否则不能直接删掉。
- 鉴权、审计、临时 Key 清理、错误脱敏和 SQLite 迁移属于安全/运维边界，不能以精简为由删除。

### 6.6 Ponytail 审计摘要

- `shrink` 合并 Chat/Responses 共同执行器，保留协议适配器。[`internal/httpapi/v1/chat.go`、`internal/httpapi/v1/responses.go`]
- `shrink` 合并两套 OCF retry/status/stream 生命周期。[`internal/httpapi/v1/chat.go`、`internal/httpapi/v1/responses_opencodefree.go`]
- `yagni` 删除 provider 自行决定重试次数的自由度，统一 retry budget。[`internal/upstream/opencodefree/client.go`、`internal/router`]
- `shrink` 将静态能力、探针和请求门控收敛为一个 CapabilitySnapshot。[`internal/modelcatalog`]
- `yagni` 不为无原生上游的 Responses hosted/stateful 功能增加伪实现。[`internal/protocol/responses/validate.go`]

## 7. 推荐目标架构与方案选择

### 方案 A：一个数据面核心 + 可插拔协议/provider 适配器（推荐）

数据面固定为：

`Parse -> CapabilitySnapshot -> Normalize -> ProviderCall -> Stream/Response finalize -> Observe`

Chat 和 Responses 只实现 `RequestAdapter`/`ResponseAdapter`；NVIDIA 和 OCF 只实现 `ProviderCall`；所有重试、首字节提交、错误分类和取消语义由核心执行器统一。健康、探针、模型管理和前端保留在控制面，通过队列读写目录。

优点：

- 同一请求在 Chat/Responses 上使用同一能力门控与重试语义；
- 错误类别可以稳定映射到客户端：本地能力 4xx/501、上游协议 502、上游不可用 503、客户端取消 499；
- 可逐步替换实现，先合并 OCF retry，再合并 Chat/Responses 主链路；
- 不要求立即删除代理池或 Codex 适配器。

代价：需要一次中等规模接口重构，必须用现有 Go 单测、Responses 契约测试和远端短矩阵守住行为。

### 方案 B：保留双主链路，只做局部补丁

继续让 Chat、Responses、OCF Chat、OCF Responses 各自维护流程，仅补充能力字段、错误码和更多日志。

优点是改动小、短期风险低；缺点是重复责任继续漂移，任何一次流式修复、retry 或 reasoning 修复都要同步四处，正是当前“明明是转发却经常不适配”的结构性来源。该方案只能作为无法安排重构时的过渡，不建议作为最终架构。

## 8. 分阶段优化路线与验收标准

### P0：先恢复客户端可用性

1. **能力策略可配置且可解释**：为每个模型生成 `CapabilitySnapshot`，至少包含 `tools`、`reasoning`、`context_length`、来源、验证时间、过期时间和失败类别。请求错误中返回稳定的 capability code，管理页显示“已验证/推断/未知/明确不支持”。
2. **工具门控改为模型级策略**：保留 strict 模式给生产白名单；对 `inferred` 放行；对 unknown 提供一次性 passthrough/探测模式并记录失败，不把未知永久映射为不支持。只有明确 501 或两种探针均阴性才写 unsupported。
3. **公开协议能力矩阵**：在 `/v1/models` 或独立只读 capabilities 端点明确标记 function tools、hosted tools、Responses stateful/background、stream、reasoning wire format。Cherry/Codex 可以在发请求前选择兼容模型。
4. **清理 stale models**：对历史 410/404/unavailable 模型保持禁用并设置复核日期；StepFun 连续门控超时，不应作为默认推荐。

验收：同一模型连续 2 次基础门控 200；Cherry function tool 请求不再因错误 metadata 直接 501；Codex 普通 Responses/function tool 5/5 完整；hosted/stateful 请求稳定返回结构化 400；所有响应都能在 request metadata 中区分本地门控和上游失败。

### P1：收敛热路径和瞬态错误

1. 合并 Chat/Responses 的共同执行器和 OCF retry/status 逻辑，统一 retry budget、首字节提交规则和 stream truncation 事件。
2. 关闭全局无差别 auto-reasoning；只按模型 profile 的 wire format 和 output budget 注入，默认不注入高档思考。没有可表达 `none` 的模型只在客户端明确要求或策略允许时映射到最轻档。
3. 为所有已启用模型补录有来源的 `context_length`；未知保持 0，不从一次 8K 成功推断 32K/128K。
4. 将代理/transport/provider 错误拆成可聚合的 `upstream_proxy_unavailable`、`upstream_unavailable`、`upstream_protocol_error`、`upstream_stream_truncated`，避免把 `validation_all_failed` 当成用户请求失败。

验收：Chat 与 Responses 对同一故障返回同一错误类别；上游首字节前最多一次安全重试，首字节后不重放；流截断必有显式 error event 或可重试的 502；5 次稳定性样本中稳定模型成功率达到 90% 以上，且无 silent empty 200。

### P2：控制面拆分和功能减法

1. 将 capability probe、model health、Key health、proxy collector 统一到一个有界 scheduler；所有数据库写入经单一 writer，避免读快照与写事件产生新的竞态。
2. 将管理前端、实时事件 Hub 与数据面解耦；数据面只保留必要 metrics 和健康端点。
3. 根据实际流量关闭未使用的 embeddings/audio/speech 路由，或拆为独立可选模块；不在没有流量证据时删除。
4. 为 Responses 维护明确的“stateless function-tools subset”文档和契约测试，停止扩张未实现的 hosted/stateful 表面。

验收：关闭控制面后台任务不影响 Chat/Responses 主路径；数据面在没有管理页面访问时仍可独立通过健康、鉴权和 5 次短矩阵；SQLite 写入者数量可观测且有界。

## 10. 已修复、当前仍复现与未覆盖

### 已修复并已写入 memory 的问题

- reasoning 线格式和小预算思考饥饿：增加预算阶梯与内容保留，避免小窗口被高档思考吃光。
- 工具门控死锁：探针改为 required + auto/强提示两段式，`inferred` 可放行；历史 kimi-k3、minimax-m3、nemotron-free、x-preview 的 Agent 路径恢复。
- 已提交流静默 EOF：现在以显式 `upstream_stream_truncated`/stream error 暴露，客户端可重试。
- `proxy_rejected` 出口粘滞：被拒出口计入 retirement，避免同会话反复拨同一坏出口。
- model health 删除竞态：`6d4b782` 将过期快照的 SQLite 外键错误归类为 `ErrModelDeleted` 并跳过；其他数据库错误仍失败。
- 历史 stale 模型：410/404/unavailable 的模型已按记录禁用，不作为当前稳定矩阵结论。

### 本轮仍复现或确认的风险

- OCF Nemotron 存在流截断、工具 parallel 协议错误、JSON 不精确和稳定性 2/5 的样本。
- NVIDIA Nemotron 受代理出口影响，高档 reasoning、JSON/context、长输出会出现 502 或 100 秒超时。
- hy3 基础与 Responses 稳定，但工具能力仍被目录状态阻断；其小预算空可见内容需要按 reasoning budget 解释。
- 所有模型 `context_length=0`，客户端无法做可靠上下文规划。
- Responses hosted/stateful/background 能力仍按设计拒绝；不能宣称完整 OpenAI Responses。
- 24 小时代理池验证失败数量很高，说明出口质量仍是系统级背景噪声。

### 未完成项

- 未测出各模型真实 32K/128K 上下文安全上限，未做长时间压力测试或统计置信区间。
- 未在本轮重跑完整代理轮换/CONNECT E2E；日志与现有健康检查只能证明服务存活，不能证明每个出口可用。
- 未部署任何新的代码或配置；本报告中的架构建议需要单独立项、测试和版本化发布。

## 11. 最终建议

短期先把“能力声明可见、工具门控可解释、错误分类稳定”做成 P0；这会直接改善 Cherry 和 Codex 的可用性。随后只做一次受控重构，统一 Chat/Responses/OCF 的执行和重试责任。不要继续为每个客户端添加独立特例，也不要把上游 502/503 通过更激进的重试伪装成模型能力。

最终目标应是：客户端能在请求前知道模型支持什么；路由器只做一次明确的协议转换和一次有界的 provider 调用；代理、Key、探测和观测故障能分别定位；不支持的 Responses hosted/stateful 能力快速、稳定、可解释地拒绝。这样才能在保留国内代理与 Codex 兼容价值的同时，真正接近一个可维护的 API 转发器。

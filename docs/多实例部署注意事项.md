# 多实例部署注意事项

本文档说明当前版本在"多实例/水平扩展"场景下的边界。**结论：当前版本只支持单实例部署。** 不要在同一数据库上同时运行两个以上实例，也不要期望多实例共享限流与调度状态。

## 当前状态：进程内存态

限流和调度状态全部保存在进程内存中，没有跨进程共享，也没有持久化：

| 状态 | 所在位置 | 多实例后果 |
| --- | --- | --- |
| Access Key 限流桶（RPM/TPM/并发，固定窗口） | `internal/accesskey/limiter.go` | 每个实例各自计数，N 个实例等于 N 倍限流上限；重启清零 |
| Access Key 认证缓存 | `internal/accesskey/cache.go` | 每实例独立缓存，撤销/策略变更在不同实例生效有时间差 |
| Key 池状态（busy、冷却、流式槽位、最近错误） | `internal/pool/` | 每个实例各自调度，同一 NVIDIA Key 可被多个实例同时占用，超出 `max_concurrent` 预期 |
| 重试预算、退避与 Retry-After 节奏 | `internal/router/attempt.go` | 每实例独立计时，跨实例无法感知上游限流节奏 |
| 运行设置与代理池设置 | SQLite（DB 行） | 这是少数**持久化**的状态；DB 行一旦存在会遮蔽环境变量 |

监控统计（`request_logs`、`daily_stats`）写入 SQLite，多实例各自写同一数据库还会引入 SQLite 单写竞争。

## 为什么不能直接多实例

1. **SQLite 是单写者数据库**：本项目以 WAL + `_txlock=immediate` 单写连接模型运行。多个进程写同一个 `.db` 文件会导致锁等待、`database is locked` 和 checkpoint 抖动；如果数据库放在 NFS/共享存储上，问题会被网络延迟放大。
2. **限流语义失效**：限流的目的是保护上游，内存态桶在多实例下按实例拆分，上游看到的总流量可能远超配置值。
3. **key 槽位失效**：流式并发隔离、key busy 槽位等调度保障都是进程内的，多实例无法互相感知，可能同时把同一个 NVIDIA Key 打满。
4. **认证缓存不一致**：一个实例撤销 Access Key 后，另一个实例可能还在缓存有效期内放行该 key。

## 支持的部署拓扑

- **单实例 + 反向代理**：推荐。一个 `app` 容器 + 受信反向代理（HTTPS 终结），负载由反向代理决定，但后端始终只有一个写者。
- **多实例共享 DB（禁止）**：即使把 SQLite 放在共享卷，也会遇到单写竞争和限流失效，不属于支持范围。
- **读写分离（禁止）**：本项目没有只读副本概念，`request_logs` 的读取查询仍需要访问唯一写库。

## 未来演进方向（本轮不做）

如果确实需要水平扩展，方向是引入共享状态，而不是让多实例各自为政：

1. **Redis 共享限流与调度状态**：把 `limiter` 桶、key busy/冷却/流式槽位、认证缓存搬到 Redis，替换内存态实现。
2. **SQLite 架构演进**：`request_logs` 走独立 append-only 存储（文件或对象存储），SQLite 只保留配置与聚合；多实例写者问题转化为"配置写者唯一，指标写入外置"。
3. **编排层面的粘性**：在引入 Redis 之前，即使做多副本，也需要保证管理面（写）只有一份。

这些方向对应的接口尚未在代码中预留（例如 limiter 没有存储抽象），因此在架构演进完成前，把服务当作"一台机器的单实例"来部署和运维。

## 运维建议

- 用一个 `docker compose` 项目部署一份应用，不复制 `app` 服务。
- 备份、轮转、恢复都只针对这一份 `/data/router.db`，参见 [自动备份方案.md](自动备份方案.md)。
- 若多个服务需要共享代理池或 NVIDIA Key 配置，请让它们各自连接同一个上游（代理池），而不是共享本项目数据库。

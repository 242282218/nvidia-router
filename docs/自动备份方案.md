# 自动备份方案

本项目使用 SQLite 单文件数据库。单文件部署最大的运营风险是"数据只存在于一份磁盘上"：磁盘故障、误删、恢复演练失败都会造成不可逆损失。本文档提供基于系统 cron 的每日自动备份示例，以及可选的 Litestream 持续复制方案。

数据库备份不包含主密钥。恢复必须同时具备数据库备份和生成该数据库所用的原主密钥，详见 [备份与恢复说明.md](备份与恢复说明.md)。

## 备份一致性说明

`db backup` 命令内部使用 SQLite 的在线备份 API（`database.Backup`）生成一致性快照，输出文件由临时文件写入后原子发布，权限为仅所有者可读写。备份不会复制 `router.db-wal` / `router.db-shm` 旁车文件，快照本身就是一致的。

尽管如此，项目既定的运维原则仍是**正式备份和恢复都必须停服**：备份进程会以 `BEGIN IMMEDIATE` 打开数据库执行迁移校验，与运行中的写者存在锁竞争；双进程共享同一个 WAL 数据库时，任何一方写入都可能在极端情况下造成歧义。因此推荐的低峰期自动备份会短暂停止 `app` 容器。

## 前置条件

- 宿主机安装 Docker 与 Compose 插件；
- 项目目录可通过 `docker compose` 直接管理；
- 应用镜像已构建（`docker compose up -d --build` 成功过至少一次）。

## 一键脚本

仓库提供 `scripts/backup-cron-example.sh`：

- 默认每天 02:00 UTC 执行（配合 crontab）；
- 默认备份到宿主机的 `<项目目录>/backups`（容器内挂载为 `/data-backups`）；
- 默认保留 7 天，更早的 `router-*.db` 自动删除；
- 默认在备份前 `docker compose stop app`，备份完成后自动恢复启动；
- 可通过环境变量覆盖：`BACKUP_DIR`（宿主机目录）、`BACKUP_DIR_INSIDE`（容器内挂载点）、`KEEP_DAYS`（保留天数）、`SKIP_STOP=1`（跳过停服，使用在线备份）。

### 安装 cron

在宿主机（root 或具有 docker 权限的用户）执行：

```bash
crontab -e
```

加入以下两行：

```cron
TZ=UTC
0 2 * * * /path/to/nvida反代/scripts/backup-cron-example.sh >> /var/log/nvidia-router-backup.log 2>&1
```

`/path/to/nvida反代` 替换为实际项目绝对路径。`TZ=UTC` 确保 02:00 是 UTC 时间，与备份文件命名的时间戳一致。

### 手动验证

先手动执行一次，确认输出：

```bash
/path/to/nvida反代/scripts/backup-cron-example.sh
ls -l /path/to/nvida反代/backups
```

备份完成后用应用自身的校验入口确认快照可用（详见 [备份与恢复说明.md](备份与恢复说明.md) 的恢复与验证章节）。至少确认文件存在且大小合理：

```bash
find /path/to/nvida反代/backups -name 'router-*.db' -type f -printf '%f %s bytes\n'
```

### 保留与加密

- 备份目录权限建议收紧：`chmod 700` 备份目录，避免同机其他用户读取。
- 备份文件仍包含加密后的敏感数据（NVIDIA Key 密文、Access Key 摘要等），禁止提交仓库、上传公共对象存储或分享。
- 如需异地/加密保存，在脚本基础上增加 `gpg` / `age` 加密后再上传，或直接使用下面的 Litestream 方案（传输加密由对象存储凭证和 TLS 保证，静态加密由对象存储服务端加密负责）。

## 主密钥轮转与自动备份的关系

自动备份只解决"数据文件有副本"的问题，**不解决密钥丢失**：

- 每个备份快照只能与生成它时所用的主密钥配合恢复；换主密钥后，旧快照需要旧主密钥。
- 主密钥轮转是停服人工操作（`admin rotate-master-key`），轮转前会自行生成一份备份，不需要也**不应**被 cron 自动触发。
- 主密钥必须与数据库备份分开保管，并定期验证可取得（例如每季度恢复演练一次）。

## Litestream 集成指南（可选）

当单文件备份的 RPO（恢复点目标）不够时，可用 [Litestream](https://litestream.io/) 把 SQLite WAL 变更持续复制到对象存储（S3 兼容存储）。它不是备份脚本的替代，而是把恢复窗口从"每天一次"缩小到"最近一次 checkpoint"。

要点：

1. **运行方式**：在现有镜像内以 `-exec` 方式让 Litestream 作为父进程启动 `nvidia-router serve`，或在 Compose 中另起 sidecar 容器只负责复制 `/data/router.db`。
2. **写者唯一性**：Litestream 要求同一数据库只有一个写者。本项目是单写者应用，满足条件；不要在同一数据库上同时跑两个 Litestream 实例。
3. **与只读容器的兼容**：现有 `docker-compose.yml` 的 `app` 服务是 `read_only: true` 且没有 Litestream 二进制。需要定制镜像（Dockerfile 中 `COPY` Litestream 二进制）并为 `-exec` 模式放宽 `read_only`（至少让 Litestream 写其元数据目录）。
4. **恢复**：Litestream 的恢复是"重建数据库目录后由副本回放"，与 [备份与恢复说明.md](备份与恢复说明.md) 的手动恢复流程（直接替换 `router.db`）不同；演练时请按 Litestream 官方 restore 文档执行，并仍然校验主密钥与 sentinel。
5. **首份快照**：启用 Litestream 前先用一次 `db backup` 生成基线，避免对象存储为空时无法启动。

Litestream 是外部工具，配置、升级和运维责任在部署方；本项目内置的 `db backup` 仍作为强制备份入口保留。

## 故障排查

- **cron 不执行**：确认 crontab 中脚本路径为绝对路径，脚本有执行权限（`chmod +x`），且 `TZ=UTC` 行在 crontab 中生效。
- **`docker compose stop app` 后未恢复**：检查 `/var/log/nvidia-router-backup.log`，若脚本中途失败，EXIT trap 也会尝试 `docker compose up -d app`；极端情况下手动执行一次恢复。
- **备份文件为 0 字节或很小**：`db backup` 失败时不会发布目标文件（临时文件会被清理），若目标文件存在但异常，说明上游校验或磁盘有问题，先恢复服务再排查磁盘。
- **`SKIP_STOP=1` 时偶发 `database is locked`**：备份进程与运行中写者竞争锁，回到默认停服模式或把 cron 挪到更低峰时段。

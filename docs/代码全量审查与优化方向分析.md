## 二、必须立即处理（回归 + P1）

### R1 [P1] tests/mocknvidia 代理集成测试全挂：`proxy URL is invalid`（回归）

- **现象**：`go test ./tests/mocknvidia` 5 个测试（`TestAllEndpointsRouteThroughProxy` 等）全部失败，错误 `create app: initialize proxy service: validate environment proxy settings: proxy URL is invalid`。
- **根因**：未提交的 xkproxy 校验链中 `AllowTestAddresses` 处理不一致，共 4 处：
  1. `internal/xkproxy/service.go:59` — `NewService` 校验环境 URL 用 `ValidateURL(env.URL)`（硬编码 `allowTestAddresses=false`），**忽略 `env.AllowTestAddresses`**。测试注入的 fetch URL 是 `127.0.0.1:port`（回环），被 `validPublicHost` 拒绝 → 报错。
  2. `internal/xkproxy/manager.go:109` — `New()` 内部同样硬编码 `ValidateURL(apiURL)`，即使 `validateSettingsForManager`（service.go:207，正确传了 flag）通过，再调 `New()` 仍会拒绝测试地址。
  3. `internal/xkproxy/service.go:109` — admin `Update` 路径也硬编码 `ValidateURL(parsed)`。
  4. `internal/xkproxy/settings.go:147` — `ValidateSettings` 反方向硬编码 `validateURL(settings.URL, true)`，**无条件放行**测试/私网地址，admin 保存私网 URL 也拦不住（SSRF 语义缺位）。
- **修复方向**：把 `allowTestAddresses` 作为参数贯穿四条路径（`NewService`/`Update` 用 `settings.AllowTestAddresses`；`New()` 增加带 flag 的构造或由调用方先判定；`ValidateSettings` 用 `settings.AllowTestAddresses`）。修复后跑 `go test ./tests/mocknvidia` 验证。

### P1-1 [P1] 生产代码无 panic 恢复中间件，handler panic 直接崩掉整个进程

- **位置**：`internal/app/app.go:172-176`（中间件链仅 `shutdownMiddleware → httpapi.NewRouter(...)`）；全生产代码零 `recover()`（仅测试文件有）。
- **问题**：Go `net/http` 不捕获 handler panic。任何外部可触达的 /v1 handler（chat/responses/embeddings/audio/speech）、admin handler 或 observability 中间件内的类型断言/nil map/越界 panic 都会终止进程，连同管理端和健康检查一起挂掉。作为对外代理网关，这是可用性单点。
- **建议**：在 `shutdownMiddleware` 与路由之间加 recover 中间件，记 stack + request ID，返回 500 JSON；流式已 commit 场景写 `response.failed` 后关流。

### P1-2 [P1] body 读取租约被 handler 全程持有，16 槽信号量变相成为全局请求并发上限

- **位置**：`internal/httpapi/v1/chat.go:49-52`（`defer bodyLease.Release()` 直到 handler 结束）、`responses.go`/`embeddings.go`/`speech.go` 同模式；`internal/httpapi/v1/bodybudget.go:15-38`。
- **问题**：`bodybudget.go` 注释声称限制"body 读取并发"（慢速读者），但租约实际在**整个请求生命周期**（含 `attempts.Run` 上游重试循环和 SSE 流式转发全程）被持有：
  - 16 路并发 SSE 长连接占满 `bodyReadSemaphore` 后，**所有新 /v1 请求一律 429 `server_busy`**，正常流量被自身并发打垮（LLM 代理以流式为主，16 并发很低）。
  - chunked 上传（`ContentLength<0`）按 `reserved = limit`（JSON 32MiB）记账（bodybudget.go:56-59），2 个 chunked 请求即耗尽 64MiB 字节预算。
- **建议**：租约释放时机移到 `readBoundedBody` 完成后立即 `Release()`（读 body 本就是短操作）；"请求并发"如需限制应设独立信号量。同时 chunked 记账改为按实际读取字节或降为固定小预留。

### P1-3 [P1] Responses 流式状态机 `output_index` 错乱：文本先于工具时消息与工具共用索引、done 指向不存在的索引

- **位置**：`internal/protocol/responses/stream.go:112-133`（`openMessage` 不递增 `itemIndex`）、`143-176`（`applyToolCall` 新工具用当前 `itemIndex` 后 `++`）、`224-257`（`closeOpenMessage` 的 done 事件用当前 `itemIndex`）。
- **问题**：一条响应**先输出文本、后发起工具调用**（模型常见的"让我查一下"前缀 + tool call）时事件流为：
  - `output_item.added`(message) `output_index=0`
  - `output_item.added`(function_call) `output_index=0`（**与消息相同**，应为 1）
  - `output_text.done`/`content_part.done`/`output_item.done`(message) `output_index=1`（该索引**从未 added**）
- **影响**：Responses 协议以 `output_index` 关联 added/done 生命周期，OpenAI SDK 会项错配或报未知项。纯文本、纯工具路径正确，现有测试未覆盖"文本+工具"组合。
- **建议**：`openMessage` 时递增 `itemIndex` 并保存消息打开时的索引，done 事件引用保存值。

## 三、P2 性能与正确性

### [P2] request_logs 清理/排序用 `julianday()` 包裹列，索引失效全表扫描，且每次启动都执行一次
- **位置**：`internal/observability/repository.go:40-53`、`internal/observability/cleanup.go:52-61`、`internal/observability/stats.go:55-63`。
- **问题**：`DELETE ... WHERE julianday(created_at) < julianday(?)` 与 `ORDER BY julianday(created_at) DESC` 使 `idx_request_logs_created`（建在 TEXT 列上）完全不可用（已用同版驱动实测 `SCAN t` + `USE TEMP B-TREE`）；`CleanupWorker.Run` **启动时先执行一次**清理。高流量下 30 天全量日志的 DELETE 在单连接上持写锁，阻塞所有请求路径。
- **建议**：改 `created_at < ?` 字符串比较（写入方统一 `RFC3339Nano` UTC 'Z'，字典序即时间序，实测结果一致）；去掉启动即清理；为 `(outcome, error_code, created_at)` 补索引。

### [P2] ASR 大文件 multipart 整段进内存再多次拷贝，与"流式落盘"设计矛盾，且 tempDir 不一致
- **位置**：`internal/protocol/audio/transcriptions.go:156-205`（`EncodeUpstream` 用 `strings.Builder` 累积→`body.String()` 拷贝→`NewReplayableBody` 再落盘到硬编码 `os.TempDir()`）。
- **问题**：原始上传已落一个临时文件，重建又产生第二个临时文件 + 峰值内存约 2×文件大小（上限 25MiB/请求）；`ParseMultipart` 用配置 `TempDir`，重放体却写 `os.TempDir()`（compose 里 `/tmp` 是 64MiB tmpfs，大文件有爆盘风险）。**同一问题被调度/协议/HTTP 三个子代理独立命中**，属高置信度。
- **建议**：基于原文件体流式组装新 multipart（或让文件型重放体支持前缀复用），避免整段进内存；透传 `tempDir`。

### [P2] Responses 流式终止事件 `output_text.done`/`output_item.done` 的 text/content 恒空
- **位置**：`internal/protocol/responses/stream.go:228-250`。
- **问题**：状态机不累积文本，done 事件发 `"text": ""`、`"content": []any{}`。依赖 done 事件做最终组装的 SDK 会用空值覆盖已流式累积的 delta，最终内容为空（delta 都在但客户端组装错）。
- **建议**：在状态机累计文本（受 #14 总量上限约束），done 事件填累计值；或显式声明不兼容。

### [P2] Responses `text.format` / `response_format`（结构化输出）被静默丢弃
- **位置**：`internal/protocol/responses/request.go:61-88`（`ToChat`）、`376-382`。
- **问题**：`text: {"format": {"json_schema": ...}}` 完全不解析不映射，`rejectUnsupportedTopLevel` 也未拒绝——请求结构化输出的客户端拿到普通文本且无任何报错，输出解析必失败。
- **建议**：映射为 chat 的 `response_format`，或返回 `unsupported_responses_feature`。

### [P2] 登录限流仅按 RemoteAddr 键控，反向代理后共享桶（DoS）/ 无法按 IP 隔离
- **位置**：`internal/httpapi/admin/auth.go:103-104`；`internal/adminauth/ratelimit.go`。
- **问题**：compose 默认只绑 loopback，典型部署前端必有反向代理，所有客户端共享代理 IP → 单个用户错 5 次密码可让全站登录 429；攻击者也可多 IP 绕过。origin 校验已支持受信代理的 `X-Forwarded-*`，限流器未复用该逻辑。
- **建议**：受信代理下取 `X-Forwarded-For` 最右可信 IP（复用 `TrustedProxyCIDRs`），键为 用户名+IP。

### [P2] 队首 waiter 的 `attempted` 集合把自由 key 排除后 dispatch 整队停摆
- **位置**：`internal/pool/queue.go:211-213`、`internal/pool/pool.go:251-301`。
- **问题**：队首 W1 的 `attempted={A}`（A 已空转）、B 被长流占用时，`tryAcquireLocked` 返回 `UnavailableBusy` → `dispatchWaitersLocked` 直接 `return`，**整队停摆**：A 完全空闲却无人可用，直到 B 释放或 W1 超时（最长一个 first-byte 窗口）。与 #28（踢出）不同，这是"堵"。
- **建议**：队首 `UnavailableBusy` 时继续扫描后续 waiter，仅当整队不可服务才返回。

### [P2] `session` 鉴权每次请求写 DB（UPDATE last_seen_at），纯 GET 也产生 WAL 写放大
- **位置**：`internal/adminauth/session.go:158-163`。
- **问题**：SPA 每次路由切换/刷新调 `GET /admin/api/auth/session` 都是一次 UPDATE；与 accesskey/observability 的写全部串行在单连接上。
- **建议**：`last_seen_at` 降频（≥1 分钟才写，参照 accesskey 节流），或仅当接近过期才写。

### [P2] /v1 数据面每请求被 `RequirePasswordChanged` 门禁 + 4 次 DB 往返
- **位置**：`internal/httpapi/router.go:22`、`internal/httpapi/admin/auth.go:74-87`；`internal/observability/http.go:76-78`。
- **问题**：每个 /v1 请求（含非法流量）先 `SELECT must_change_password`（且发生在 access-key 鉴权之前），加上 accesskey RecordUse、keystate MarkSuccess/MarkFailure、observability Record，单数据面请求最多 4 次 DB 往返，全部串行在单连接上（#25 的放大确认）。
- **建议**：`must_change_password` 启动时加载、改密时失效；观测记录批量异步写入。

### [P2] 排队超时总是被 first-byte ctx 截止，`queue_timeout` 429 不可达，客户端收到 504
- **位置**：`internal/router/attempt.go:160-166`、`internal/pool/queue.go:171-184`。
- **问题**：默认 first_byte 与 queue_wait 同为 60s，但 ctx 截止在入队前创建，必然先触发 → `context.DeadlineExceeded` 被分类为 504 retryable `upstream_timeout`；池的 `queue_timeout` 429（带 Retry-After）仅在错配配置下可达。排队还蚕食 first-byte 预算。
- **建议**：排队阶段超时返回 `queue_timeout` 429（含 Retry-After），first-byte 预算从拿到租约后起算。

### [P2] Argon2 参数硬编码 + 单次验证 64MiB 内存，无参数升级路径
- **位置**：`internal/adminauth/password.go:15-20`、`:62`。
- **问题**：登录/改密并发突发时按请求数成倍占用 64MiB/次；PHC 解析严格匹配 `m=65536,t=3,p=2`，未来提高成本会拒绝全部旧哈希且无自动重哈希。
- **建议**：解析哈希自带参数；验证成功且参数落后时自动重哈希写回。

### [P2] `ApplyFailure` 用 DB 事务旧快照整体覆盖池内存，可回滚并发 admin 更新
- **位置**：`internal/pool/pool.go:215-227`。
- **问题**：`markFailure` 事务内读到的快照若晚于并发 `SetEnabled`/`UpsertKey`，`ApplyFailure` 整份覆盖回旧值（含 `Enabled`/`CooldownUntil`），池内存与 DB 不一致直到下一次收敛。
- **建议**：按字段合并（仅覆盖 cooldown/consecutive_failures/auth_invalid/block）。

### [P2] accesskey `lastRecorded`/`pending` map 永不清理
- **位置**：`internal/accesskey/service.go:33-34,101-127`（#33 的补充确认：`pending` 会删，`lastRecorded` 不删）。
- **建议**：`Revoke` 时删除对应条目或周期清理。

### [P2] observability `SetUsage` 及 token 字段是死代码，流式 token 采集管道从未接线
- **位置**：`internal/observability/context.go:65-70`、`request.go:22-23`（#26 根因补充：不仅流式不采，连注入管道都没接线）。
- **建议**：SSE 结束时从尾部 usage 事件解析并调用 `SetUsage`。

### [P2] 接近 25MiB 上限的音频请求返回 500 而非 413
- **位置**：`internal/protocol/audio/transcriptions.go:200-203`、`internal/router/replay.go:61-65`。
- **问题**：重建的上游 body 超出 `maxReplayBytes` 时返回 `errBodyTooLarge`；`router.BodyTooLarge(err)` 已定义但**无任何 HTTP 层调用**，`writeChatError` 落到 500 `internal_error`。
- **建议**：`audio.go` 用 `router.BodyTooLarge(err)` 映射 413 `request_too_large`。

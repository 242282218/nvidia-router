## 一、问题总览（按影响分层）

### 🔴 R0 级：确定的功能 Bug（立即修）

**R1. 运行设置保存链路断裂（`retry_budget_ms` vs `retry_window_ms` 契约不一致）**
- **影响**：当前"运行设置"页面无法保存任何配置
- **根因**：前端类型/表单用 `retry_budget_ms`（`web/src/features/runtime/types.ts:31`、`SettingsForm.vue:72`），后端 JSON tag 用 `retry_window_ms`（`internal/httpapi/admin/settings.go:31,48`），且后端 `decodeJSON` 开启 `DisallowUnknownFields`（`admin/auth.go:289`）
- **后果链**：GET 响应前端读不到该字段 → 表单校验失败；PATCH 整包被 400 拒收
- **为何未发现**：单测 mock 掉 API（`RuntimeView.spec.ts:26`），E2E 只断言输入框有值、从不验证保存成功（`tests/e2e/runtime.spec.ts:28-31`）

### 🟠 R1 级：高影响架构/安全风险（1-2 周内修）

**R2. 主密钥轮转"文档级离线"约束，代码不强制**
- **位置**：`internal/crypto/rotation.go:16-18` 注释 vs `internal/app/cli.go:105-159` 实现
- **风险**：双进程共享 WAL 时可能写穿版本，旧进程继续用旧 key 加密新数据 → 产生混合版本数据，恢复成本高
- **建议**：加文件锁（`flock` / named pipe）或检查 `/data/router.db-shm` 存在且非空时拒绝轮转

**R3. 会话 cookie 默认非 Secure + 默认 `0.0.0.0:3756` 无 TLS**
- **位置**：`internal/adminauth/session.go:57-67`、`internal/config/config.go:72`、`docker-compose.yml:8` 端口绑定
- **风险**：管理会话可被嗅探，完全接管管理面（含所有密钥增删改）
- **建议**：cookie 按环境开启 `Secure`；compose 默认只绑定 loopback；README 在"快速开始"第一段加醒目 TLS 警告框

**R4. 流式请求整生命周期占用 key busy 槽位**
- **位置**：`internal/router/attempt.go:277` (`keepLease=true`) + `internal/httpapi/v1/chat.go:79` (`defer result.Release()`)
- **后果**：并发流式上限 = key 池大小；一个慢生成（分钟级）可拖住整个池
- **建议**：引入"流式并发隔离"——per-key 独立流式槽位配额（如 `max_streaming_per_key=2`），短请求不受影响

**R5. 重试放大：单请求最多 10 次上游调用**
- **位置**：`internal/upstream/nvidia/client.go:178-195` （每 key 最多 2 次代理尝试）× `internal/router/budget.go:74` （最多 5 个 key）
- **加剧因素**：401/403 凭据错误默认 `Retryable:true`（`internal/fault/classifier.go:91-97`），会逐个 key 打凭据请求
- **建议**：401/403 改为"同 key 立即失败 + 标记冷却"，不跨 key 重试；每 key 代理尝试降为 1 次

**R6. 429 的 `Retry-After` 未进入重试节奏**
- **位置**：`internal/fault/cooldown.go:28-34` 只用于 key cooldown，`internal/router/attempt.go:307-336` 完全不读
- **后果**：账号级限流下换 key 立即重试照样 429，白白消耗重试预算并放大上游压力
- **建议**：`attempt.backoff` 取 `max(指数退避, min(currentFault.RetryAfter, 5min))`

**R7. 每日清理任务全表 `DELETE` 无分批，阻塞唯一写连接**
- **位置**：`internal/observability/cleanup.go:82-112` + `internal/observability/repository.go:87-100`
- **问题**：每天 UTC 03:00 对 `request_logs` 全量 DELETE（无 LIMIT），代码注释自认会 stall 所有请求写路径
- **建议**：分批删除（`DELETE ... WHERE id IN (SELECT id ... LIMIT 5000)` 循环直到 `RowsAffected() == 0`）

**R8. 无自动备份/保留策略**
- **位置**：仅手动 CLI `db backup`（`internal/app/cli.go:168-192`）和轮转前备份（`cli.go:140`）
- **影响**：单文件 SQLite 部署下这是运营空白
- **建议**：提供 cron 示例（每天 02:00 UTC 备份到 `/data-backups` + 保留 7 天）或推荐 Litestream；README 补"备份策略"章节

### 🟡 R2 级：中低影响与维护性债务（按需分批）

**R9. 明文密钥以不可清零 string 常驻内存**
- **位置**：NVIDIA key 每次请求经 `string(secret)` 进 HTTP 头（`internal/httpapi/v1/chat.go:94`、`internal/upstream/nvidia/descriptor.go:116`），代理池 key 进程级常驻（`internal/xkproxy/settings.go:373-383`、`manager.go:92-93`）
- **不一致**：与 `internal/crypto` 包的 Zero 体系声明不符（`crypto/digest.go:70-72`）
- **接受度**：个人部署可接受，但应在文档明示"密钥明文驻留内存直到 GC"

**R10. Access Key 限流为内存态固定窗口**
- **位置**：`internal/accesskey/limiter.go:70-85`
- **后果**：重启清零、多副本独立；Revoke 不清理 limiter 桶导致长期累积（`service.go:168-182`）；TPM 事后生效，窗口内可突发超限（`limiter.go:41-57`）
- **建议**：Revoke 时 `delete(l.buckets, id)`；文档明示"固定窗口、重启不保留"

**R11. 前端 Access Key 策略能力漂移**
- **位置**：后端已实现 `expires_at/rpm_limit/tpm_limit/max_concurrent` 策略 + PATCH（`internal/httpapi/admin/access_keys.go:22-33,103-127`），前端类型缺失（`web/src/features/access-keys/types.ts:1-8`）、无任何 UI
- **建议**：前端补策略编辑表单（参考 RuntimeView 布局）

**R12. 监控页 dead code**
- **位置**：`web/src/features/statistics/api.ts:12-23` 的 `getDaily`/`getRecentErrors` 与 `types.ts:3-35` 类型无人调用
- **建议**：删除或明确标记为 deprecated

**R13. 契约手写 + 守卫漏检改名**
- **位置**：类型与后端 DTO 双份手写，无单一事实来源；运行时守卫只校验"必有字段"，对字段改名（如 R1）、可选字段不设防
- **建议**：引入契约测试（Go `httptest` 快照 → 前端类型断言）或 OpenAPI codegen

**R14-R16. 其余维护性问题**
- 死代码/死表：migration 003 的 `xk_proxy_settings` 表全库零引用
- 校验三处重复：runtime settings 边界在 DB CHECK、Go `Validate`、Vue 表单各维护一份
- xkproxy 环境变量单向粘滞：DB 行一旦存在就永久遮蔽 env（`internal/xkproxy/settings.go:191-200`）
- 时间源不一致：`runtimeconfig/repository.go:53`、`xkproxy/settings.go:407` 直接用 `time.Now()`，与全局 `clock.Clock` 注入约定冲突
- access key 认证缓存全量失效：任何策略变更清空 4096 项缓存（`internal/accesskey/cache.go:71-78`）

## 四、风险与约束

### 技术风险
1. **流式并发隔离**：pool 状态机复杂度上升，需补充"流式超时释放"与"排队流式优先级"测试
2. **契约测试快照**：Go 测试生成的 JSON 快照需版本控制，后端改动必须同步更新前端类型
3. **分批删除**：SQLite `DELETE ... WHERE id IN (SELECT ...)` 在 WAL 模式下可能触发 checkpoint，需监控首次执行耗时

### 运营约束
- **主密钥轮转检测**：文件锁在 Windows 容器与某些 NFS 挂载下行为可能不一致，建议 Linux 生产环境优先验证
- **备份策略**：cron 示例脚本需运维手动配置，未来可考虑内置调度（但 MVP 不做）

### 不做清单（明确边界）
1. **多实例支持**：限流/池状态保持内存态，不引入 Redis
2. **多厂商路由**：provider 抽象只为代码整洁，不做"渠道选择"
3. **成本控制**：NVIDIA 按用量计费的预算告警留待未来（当前只做 token 统计）
4. **WebAuthn/审计日志/多租户**：明确不做，保持个人/小团队定位

## 五、与同类项目的差异化路径

基于审查报告第四节"与同类项目对比"，本轮优化后的定位：

| 维度 | 优化后状态 | 与 LiteLLM/one-api 差异 |
|---|---|---|
| **安全** | 密钥 AEAD+HKDF+轮转（加固）+ secure cookie（R1.3） | 同类 MVP 最强 |
| **调度** | 流式并发隔离 + Retry-After 节奏 + 重试收紧 | LiteLLM 更全面，但本项目单上游调度更精细 |
| **可观测** | TTFT p95 + 契约测试 | 仍弱于 LiteLLM OTel，但补上 LLM 网关核心 SLO |
| **部署** | 单二进制 + SQLite + 备份示例 | 最轻量 |

**护城河**：安全 + 单上游精细调度 + 轻量部署，不与多厂商通用网关正面竞争。

## 六、后续演进方向（本轮不做，留待第三轮）

1. **成本控制**：per-key 预算告警（NVIDIA 计费可做，对标 LiteLLM budget）
2. **限流演进**：固定窗口 → 滑动窗口 + 可选持久化（为多实例留接口）
3. **指标升级**：OTel 标准 span（auth→acquire→attempt→upstream→sse）
4. **日志分层**：`request_logs` 走独立 append-only 文件/缓冲，SQLite 只存配置和聚合
5. **管理面增强**：会话 idle 超时、audit log（谁改了哪个 key）、密码强度策略

# 第四轮优化说明：collector 验证链路与 stale 出口生命周期

更新日期：2026-08-13

## 目标

继续按四个方向迭代：① 模型反代稳定性；② 代理 IP 选择质量；③ UI 与交互；④ 审查与真实联调发现的其他高价值项。本轮以**真实工作场景端到端联调**驱动，累计修复 12 项（含 4 个严重稳定性 bug、3 个代理质量、3 个可运维性、2 个 UI/交互）。

## 一、发现路径（真实联调证据）

在测试机 `114.55.25.190`（Compose 项目 `nvidia-router`，collector 内置池模式）上做端到端验证，观察到：

1. **池「看起来满」但全死**：`/admin/api/proxy-pool/status` 显示 306 个「健康」出口，但 `last_fetch_at` 停在数小时前、`latency_samples=0`、`remaining_seconds` 接近 grace 封顶（240s）。实际这些出口全部从未通过验证，是 grace 续命的历史残留。
2. **minimax 非流式 200 但 deepseek 流式 240s 超时**：根因不是模型慢（直连 NVIDIA 测 deepseek 首 token 需 117~135s，是 reasoning 长思考的固有特性），而是池里全是死 IP，流式请求在死 IP 上反复重试耗尽时间。
3. **minimax 流式偶发 502 `upstream_proxy_unavailable`**：请求时刻池瞬时为空（所有候选都是死 IP）。

## 二、修复 1：validator 漏设 HTTP/2，代理全部验证失败（严重，根因）

**问题**：`internal/xkproxy/validator.go` 的验证 transport 未设 `ForceAttemptHTTP2 = true`。第三轮已在 `manager.go` 修复同一 h2 bug（请求路径），但漏修了验证探针。验证目标 NVIDIA 坐落在 CDN 后讲 HTTP/2，探针用 HTTP/1.1 走 CONNECT → 目标回 h2 帧 → `malformed HTTP response` → **每个抓到的代理都验证失败**，collector 持续 `validation_all_failed`，池靠 grace 无限续命 stale 出口。

**修复**：`validator.go` 的 `transportFor` 增加 `ForceAttemptHTTP2: true`，与请求路径 `manager.go`、直连模式 `chat.go` 对齐。补回归测试 `TestValidatorTransportEnablesHTTP2`。

**验证**：修复后 collector 从「306 个 stale 出口」恢复为「9 个真实验证通过、`latency_samples=1`、`last_fetch=last_success=最新`」的干净状态；minimax 流式 `[DONE]` 完整返回。

## 三、修复 2：grace 无限续命 stale 出口（严重，代理质量）

**问题**：`pool.go` 的 `Grace` 用 `cap := now.Add(maxLifetime)` 计算续命上限。但 collector 每个采集周期（5s）都调一次 `Grace`，每次 `now` 都推进 → cap 每次都被重算到「现在 + maxLifetime」，stale 出口的 `ExpiresAt` 被无限推后，**永不过期**。结果：上游持续返回死 IP 时，池「看起来满」（37 个出口）但全是死 IP，请求选到死 IP 全失败 → 502。

**修复**：cap 锚定到每个出口自己的 `ValidatedAt`（最后一次真实验证时间），不再锚定 `now`。出口在 `ValidatedAt + maxLifetime` 后停止续命，自然过期。同时跳过 `ValidatedAt` 为零（从未真实验证）的出口——没有工作证明的出口不该被续命。补回归测试 `TestPoolGraceDoesNotExtendNeverValidatedExit`、`TestPoolGraceCapAnchoredToValidatedAt`。

**验证**：修复后池从「37 个 stale（34 个从未验证）」变为「6 个真实验证过（`latency_samples=1`）」；minimax 非流式 + 流式各 3 次共 **6/6 全 200，502 消失**。

## 四、修复 3：collector 验证全败不重试、且错误地重置退避

**问题**：
- 星空代理池 IP 质量随机（实测 7 个 IP 3 死 4 活，死 IP 比例约 43%），collector 抓到死 IP 整轮 `validation_all_failed` 后，要等下一个 5s 周期才重试，浪费窗口。
- `validation_all_failed` 返回 `true`，导致 `nextInterval(true)` 把退避重置到基础间隔，5s 一次地空耗星空配额（403 限流风险）。

**修复**（`collector.go`）：
- `fetch` 内做「提取→验证」的有界重试（`validationRetryLimit=3`），一轮全败立即重新提取，利用星空 IP 的随机性在单轮内抓到好 IP。
- `validation_all_failed` 最终仍失败时返回 `false`（触发退避），不再假装成功。
- 补测试 `TestCollectorRefetchesAfterValidationAllFailed`。

**验证**：日志显示 `validation_all_failed ... attempt=1/2/3` 重试生效；`last_success_at` 保持最新，池里有真实验证过的出口。

## 五、修复 4：`latency_samples` 首次验证未累计（显示 bug）

**问题**：`validateBatch` 里新代理首次进入池时未设 `LatencySamples`，导致新代理 `latency_samples=0` 却有 `latency_ewma` 值，UI 无法区分「新鲜 EWMA」和「单样本 EWMA」。

**修复**：`collector.go` 的 `validateBatch` 首次验证后设 `LatencySamples = 1`，后续 `Merge` 再累计。

## 六、修复 5：质量选路缺相对慢速降级（代理质量）

**问题**：`orderByQuality` 只在质量分相同时用延迟做 tie-breaker，且延迟惩罚用绝对阈值（`>800ms` 才 -15 分）。星空 IP 普遍 1~3s，绝对阈值失效，导致「池内最慢的一批 IP」仍按分数（中性 50 分）排前，长尾延迟高达 20s。

**修复**（`pool.go`）：
- `orderByQuality` 增加池内相对慢速降级：用**真实请求延迟**的最快值 ×3 作为阈值，慢于阈值的出口排到最后。
- 只比较 `RequestLatencyEWMA`（真实请求），**不混入 probe latency**——probe 是快速健康检查、request 是完整 LLM 往返，量级不同，混入会让「probe 快的无样本出口」误伤「有真实成功样本但稍慢的出口」。
- 补测试 `TestPoolQualityDemotesRelativeSlowRequest`、`TestPoolQualityDoesNotDemoteByProbeOnly`。

**验证**：真实压测 12 次 minimax，`max` 从 20s 降到 3.43s，`avg` 从 3.83s 降到 1.53s，长尾被削掉。

## 七、修复 6：per-model 流式超时链路补全（可运维性）

**问题**：migration 016/022 已在 `models` 表增加并 backfill `stream_first_token_timeout_ms`/`stream_idle_timeout_ms`，handler 的 `applyModelTimeouts` 也消费它们，但**中间链路是断的**——`modelcatalog.Patch`、admin `modelDTO` 都不含这两个字段，导致：
- admin `/admin/api/models` 不返回这两个字段（之前实测 deepseek 显示 `None`，实为 DTO 未映射）；
- 管理员无法通过 API/UI 看到或调整 per-model 超时（migration 只做了 DB 侧的一半）。

**修复**：
- `modelcatalog/model.go` 的 `Patch` 增加 `StreamFirstTokenTimeoutMS`/`StreamIdleTimeoutMS` 字段。
- `modelcatalog/repository.go` 的 PATCH SQL 用 CASE 支持这两列（nil 保留、非 nil 替换），新增 `patchDerefInt`。
- `internal/httpapi/admin/models.go` 的 `modelDTO` 与 `toModelDTO` 映射这两个字段。
- 前端 `types.ts` 补字段、`ModelsView.vue` 的 `isModel` 校验补接受、`ModelTable.vue` 新增「流式超时」列（有覆盖显示 `首 Xs · 空闲 Ys`，无覆盖显示「全局默认」）。
- 补测试 `TestPatchStreamTimeoutsPersistsAndRoundsTrips`。

**验证**：部署后 API 正确返回 `deepseek: 300000/300000`、`minimax: None`；PATCH minimax 设置 `90000/120000` 后正确回显。

## 八、修复 7：请求失败时记录代理出口身份（诊断增强）

**问题**：请求路径（`client.go` 的 `doProxyAttempt`）对代理出口是完全黑盒——当某个 IP 劣质导致慢/失败时，日志里只有 `proxy_transport_retired`，看不到「这个请求走了哪个代理」，无法把「劣质 IP」和「具体请求失败」关联起来，只能去代理池页手动对照。

**修复**：
- `xkproxy.Handle` 增加 `ProxyKey()` 访问器，暴露 transport 绑定的池出口身份。
- `client.go` 在纯传输失败（`proxy_transport_error`）和 HTTP fault（`proxy_http_fault`）路径用 `observability.RequestLogger` 记录 debug 日志，带 `proxy` 字段。
- 补测试 `TestHandleProxyKeyExposesExitIdentity`。

**验证**：编译 + 全量测试通过；请求成功时无 debug 输出（符合预期），失败时日志携带具体 IP。

## 九、修复 8：冷启动用 probe 延迟兜底降级（代理质量）

**问题**：`QualityScore` 对无真实请求样本的新 IP（冷启动）统一给中性 50 分，probe latency 完全不参与。实测星空池里 probe 4.1s 的出口真实请求也 4.8s——probe 是 req 的有效先验，但冷启动期无法区分「probe 0.4s 的快 IP」和「probe 4s 的慢 IP」，导致首个请求被分配到慢 IP 付出 11s+ 的延迟。

**修复**（`pool.go`）：
- `QualityScore` 增加冷启动兜底：**仅当无 req 样本时**用 probe latency 降权（>3s 减 15、>2s 减 8、>1s 减 3）。一旦有真实 req 样本，切回 req latency，probe 不再参与——两个量级不混用。
- 补测试 `TestPoolQualityColdStartDemotesSlowProbe`、`TestPoolQualityDoesNotDemoteByProbeAfterRequestSample`。

**验证**：30 次真实请求全 200（0 失败），延迟长尾从上一轮 max 20s 降到 max 11s、avg 2.8s。剩余长尾（17% 请求 >5s）是星空共享租约出口的固有质量方差，非代码可消除。

## 十二、修复 10：transport 错误短路换 key 重试（稳定性，严重）

**问题**：`router/attempt.go` 的 `executeLease` 对 `ReasonTransportFailed`（transport 层代理失败）走 `return nil, commit, nil, executeErr`，把原始 error 作为 `resultErr` 返回。而 `Run` 里 `if err != nil { return AttemptResult{}, err }` 直接短路——**换 key 重试循环根本没机会执行**。这与 `ReasonNoHealthyProxy` 的处理不一致：后者分类成 `Retryable` fault 让 `Run` 换 key，前者却短路。

**后果**：并发场景下，一个请求在 `do` 层重试 1 次 transport 失败后直接 502 返回，`attempt.go` 的「换 key 重试」被跳过。这是并发 30 请求 5 个 502 的真正根因——不是「换 key 救不了」，而是「transport 错误根本没走到换 key 逻辑」。

**修复**：`executeLease` 对 `ReasonTransportFailed` 也分类成 `Retryable=true` 的 `ScopeUpstreamGlobal` fault（`upstream_proxy_unavailable`），与 `ReasonNoHealthyProxy` 一致，让 `Run` 的换 key 重试循环生效。

**验证**：更新 `TestAttemptDoesNotPersistProxyFailureOrSwitchKey`、`TestAttemptProxyFailureSkipsStateSyncAndModelBlockPropagation` 断言——transport 失败现在换 key 重试（`attempted >= 2`），但仍不写状态、不冷却 key。

## 十三、修复 11：metrics 端点暴露代理池健康度（可运维性）

**问题**：`/metrics` 端点暴露了 key 池和请求统计，但**完全没有代理池指标**——代理池是本项目核心，运维无法通过 Prometheus 告警「池空/panic/上游过载」，只能手动刷 admin 页面。

**修复**：
- `metrics.Handler` 增加可选 `ProxyPoolProvider`（返回 `xkproxy.PoolStatus`），`WithProxyPool` setter 保持既有调用点不变。
- 输出 4 个 gauge：`nvidia_router_proxy_pool_total`、`nvidia_router_proxy_pool_healthy`、`nvidia_router_proxy_pool_panic_mode`、`nvidia_router_proxy_pool_upstream_overloaded`。
- `app.go` 装配点接入 `proxySettings`。
- 补测试 `TestMetricsHandlerExposesProxyPoolHealth`。

**验证**：部署后 `/metrics` 正确输出 4 个代理池指标（total=6、healthy=6、panic=0、overloaded=0）。

## 十四、修复 12：`server_busy` 429 缺 Retry-After（API 一致性）

**问题**：`bodybudget.go` 的 `bodyBusyError` 返回 429 `server_busy` 但缺 `Retry-After`，而所有其他 429（queue_full/queue_timeout/access_key_rate_limited/login 限流）都带 Retry-After。客户端对 `server_busy` 无法退避重试。

**修复**：加 `RetryAfter: time.Second`（body 读取是短操作，1 秒足够释放槽位）。补测试断言 `RetryAfter > 0`。

## 十七、未做项与理由

- **`XK_EXPECTED_QTY` 接入上游 `qty` 参数**：该配置当前是死配置（存储但未参与请求构造），上游 URL 里的 `qty=2` 硬编码在 `.env`。接入需先确认星空 XApi 的 `qty` 参数语义（实测 `qty=3` 返回 506「提取数量不能大于单次提取最大数」，说明上限就是 2），改默认值无实际收益，留待上游契约确认。
- **`MaxLatency` 硬默认**：星空返回的 IP 延迟抖动大（500ms~3.5s），无真实测量依据下设硬默认可能误伤国内慢出口，保持关闭。
- **`race` 检测**：本机无 CGO 工具链，`go test -race` 不可用；并发路径沿用现有锁结构并有并发测试覆盖。

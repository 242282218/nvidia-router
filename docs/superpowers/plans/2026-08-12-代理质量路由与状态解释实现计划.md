# 代理质量路由与状态解释实现计划

> **面向 AI 代理的工作者：** 本计划在当前工作区执行。工作区已有未提交改动，必须保留；不要回退、覆盖或提交无关文件。每个行为变更遵循 TDD：先写失败测试，确认失败，再写最少生产代码。

**目标：** 将动态代理选择从单一延迟排序提升为以真实请求质量为主、延迟为辅并带有限探索的路由，同时让管理端能解释每个出口的质量依据。

**架构：** 代理池继续负责内存生命周期、熔断和选择；新增的请求级成功/失败与请求延迟统计只在真实 NVIDIA 请求路径写入，采集校验数据不再冒充真实请求质量。选择器先排除不可用出口，再按质量信号排序，默认优先稳定出口，按固定低频率探索未充分采样的出口。管理端只返回非敏感质量投影，前端用摘要 + 可读表格呈现排序依据、失败归因和数据新鲜度。

**技术栈：** Go 1.24、标准库 `sort`/`sync`/`time`、现有 xkproxy 与 admin HTTP API、Vue 3 + TypeScript + UnoCSS、Vitest。

---

## 全局约束

- 不新增数据库表或迁移；代理质量数据是运行时数据，进程重启后重新采集。
- 不记录、不返回代理用户名、密码、认证 Key 或上游 URL。
- 529 只作为上游过载信号展示，不计入出口劣化；共享 429/5xx 仍受现有多数派门控保护。
- 保留 `Get` 的既有轮转语义；质量路由只替换 `LatencyRoutingEnabled` 已启用时的选择路径。
- 不改变静态代理模式、请求重试公开错误类型和现有 HTTP/2 行为。
- UI 不使用 emoji 图标；状态必须覆盖加载、空、错误、成功、降级和刷新中；窄屏表格允许带语义的横向滚动。
- 不提交本轮改动，除非用户另行明确要求；不执行 push、reset、clean 或删除现有产物。

### 任务 1：真实请求质量指标与质量选择器

**文件：**

- [ ] **步骤 1：编写失败测试**

  增加以下行为测试：

  1. `ReportSuccess` 只增加 `RequestSuccessCount`、`RequestLatencySamples` 并更新 `RequestLatencyEWMA`。
  2. `ReportFailure` 与 `ReportHTTPFailure` 增加 `RequestFailureCount`。
  3. 一个真实成功率高但探针延迟略高的出口优先于只有探针成功、没有真实请求样本的出口。
  4. 有连续 HTTP 失败信号的出口不能排在无失败信号出口之前。
  5. 未采样出口只在低频探索机会被选中，不再与最佳出口等比例轮转。

- [ ] **步骤 2：运行红灯测试**

  运行：`go test ./internal/xkproxy -run 'TestPool(RequestQuality|Quality|RequestFailure)' -count=1`

  预期：失败原因是字段或质量选择行为尚未存在，而不是编译环境错误。

- [ ] **步骤 3：实现最少代码**

  在 `Proxy` 中新增 `RequestSuccessCount`、`RequestFailureCount`、`RequestLatencyEWMA`、`RequestLatencySamples`。保留既有 `SuccessCount`/`FailureCount` 作为兼容的观测总数。

  在 `ReportSuccess` 中写入真实请求字段；在两个失败报告中写入请求失败字段。增加不暴露凭据的质量评分函数：

  ```go
  func (p Proxy) EffectiveRequestLatency() time.Duration
  func (p Proxy) QualityScore() int
  ```

  评分只使用真实可观测字段：无请求样本时给予中性分；失败率、连续 HTTP 失败、连续传输失败分别扣分；延迟只作为有限扣分，不能覆盖严重失败信号。

  增加 `GetWithQuality(now)`：先过滤 live/未隔离出口，按评分降序、有效请求延迟升序排序；正常请求选择首位；每 8 次选择最多探索一个未充分采样且无活跃失败信号的出口。保留已有 `GetWithLatency`，仅由新路由调用方切换。

# 全量审查修复与发布收口设计

更新日期：2026-08-15

## 目标

将当前工作树中已经完成的第四轮业务改动安全收口，同时修复全量审查确认的安全、数据完整性、并发生命周期和部署可靠性问题。最终交付必须在独立分支通过本地验证与 GitHub Actions，随后才能合入并推送 `main`。

成功标准：

- 管理员登录无法通过轮换用户名绕过昂贵密码校验前的限流，限流状态有明确内存上界。
- 所有长连接和流式响应都有可执行的取消与下游写超时，慢客户端不会无限占用资源。
- 代理采集器关闭后不再存在继续刷新、访问已关闭依赖或修改池状态的任务。
- 从旧数据库升级时保留可映射的代理配置，不以删表作为迁移结果。
- 部署、备份和回滚操作使用同一数据卷与镜像标签，失败必须可见。
- Provider、代理池设置、请求体限制和管理审计的服务端行为与管理界面一致。
- GitHub 提交不包含凭据、数据库、日志、二进制、缓存或一次性远程运维脚本。
- 修复分支及合入后的 `main` 均通过仓库现有 GitHub Actions。

## 提交边界

当前工作树包含既有业务改动和本地运行产物。本次在当前目录的 `fix/audit-hardening-20260815` 分支工作，不创建基于干净 HEAD、从而丢失本地业务改动的第二工作树。

纳入提交：

- 当前已修改的产品源码、对应自动化测试、数据库迁移、前端嵌入资产和与行为一致性直接相关的文档。
- 本轮新增的回归测试、最小修复和必要的忽略规则。

排除提交：

- 数据库及 WAL/SHM、日志、覆盖率、测试结果、可执行文件、缓存和异常临时文件。
- 含运行时凭据或直接操作远程 root、重启容器、修改远程数据库的一次性脚本。
- 无法证明属于产品实现或可重复测试流程的其他未跟踪文件。

所有提交使用显式路径暂存，不使用 `git add .`。敏感信息扫描必须同时覆盖已跟踪差异、待提交内容和 Docker build context。

## 设计方案

### 1. 管理员认证与限流

在执行 Argon2 前先应用以客户端 IP 为主的限流，再保留账号维度的失败保护。未知账号继续使用等成本的伪密码校验以避免用户名枚举，但只有通过 IP 限流的请求才能进入昂贵校验。JSON 解码失败、字段缺失和普通认证失败都进入统一尝试生命周期。

限流器使用有界状态：过期桶按时间清理，并设置最大桶数；达到上限时优先移除已过期或最久未使用桶。客户端地址只使用项目现有可信代理解析规则，不新增可伪造的请求头信任。

### 2. 流式响应与慢客户端

请求预算产生的 context 必须传递到最终 Chat、Responses 和 Audio 响应写入阶段。流式写入统一遵守以下约束：

- 每次写入或 flush 都受下游写截止时间约束。
- 客户端断开或请求预算取消时，同时停止读取上游并释放响应体。
- 运行环境不支持写截止时间时，不以只能关闭上游的 watchdog 冒充下游保护；该路径应通过可取消的响应控制能力退出，或明确失败而不是无限阻塞。
- 管理员 SSE 使用同样的写超时，并限制单个客户端的缓冲与生命周期。

实现优先复用现有 `sse` 和 `http.ResponseController` 能力，不引入新的流框架。

### 3. 代理采集器生命周期

周期刷新和手工刷新使用同一生命周期计数。`Close` 先阻止新刷新，再取消公共 context，最后等待所有已经开始的刷新完成后关闭 upstream 和 validator。刷新在网络请求、验证和合并池状态前检查关闭状态，保证关闭后不再产生状态写入。

### 4. 数据库升级

Migration 023 改为保留式升级：在事务内创建新结构、复制所有能够映射的旧配置、验证复制结果，再移除被替代结构。无法映射的敏感值不得写入日志。迁移测试从包含真实旧结构和非默认配置的数据库开始，断言升级后值仍可通过当前 repository 读取。

已发布迁移文件是否允许原地修改由仓库现状决定：如果 023 尚未进入远端 `main`，直接修正 023；如果已经发布，则新增后续修复迁移，禁止改写历史迁移。

### 5. 部署、备份与回滚

Compose 是卷名、容器名、服务端口和镜像变量的唯一事实来源。部署脚本通过 Compose 查询实际资源，不维护第二套硬编码名称。备份、恢复和健康检查失败立即终止；只允许对非关键清理步骤显式容错。

镜像标签通过 Compose 环境变量实际参与镜像引用。回滚恢复同一数据卷，并只检查当前单体服务公开的健康端点，不访问已删除的独立代理池端口。

### 6. 凭据与构建上下文

删除 Dockerfile、启动文件和测试脚本中的硬编码凭据，改为运行时环境变量且在缺失时明确失败。Docker build context 排除本地启动文件、数据目录、日志、缓存、测试结果和远程运维脚本。已经暴露的凭据需要在仓库外轮换；代码提交不能代替轮换。

### 7. Provider 行为

本轮不实现未经契约和真实联调验证的 OpenAI-compatible 请求路由。服务端允许保存用于后续配置的 Provider 草稿，但拒绝启用非 NVIDIA Provider，也拒绝把可用模型绑定到运行时不支持的 Provider，避免管理端显示成功而 `/v1` 静默走 NVIDIA。

Base URL 即使处于草稿状态也必须在服务端解析和校验：只允许明确支持的 HTTP(S) 协议，拒绝 userinfo、query、fragment、空 host 和非法端口。Provider upsert 使用 `RETURNING` 或唯一键回查，不依赖冲突更新后的 `LastInsertId()`。

### 8. 代理池设置与管理界面

PATCH 在服务端验证状态码、正数超时、并发数、期望数量、最大延迟及字段关系。可清空字段使用显式 nullable 语义，区分“未提供”和“清除”。

前端加载完整配置并只提交用户实际编辑后的完整一致状态，不能用未回填的默认值覆盖数据库。`ExpectedQty` 进入采集请求的数量约束；其值同时受上游已知最大值和服务端校验限制。若当前上游实现不支持该参数，则服务端拒绝非默认值，不保留无效果配置。

### 9. 请求体、审计和管理事件流

请求体限制读取至 `limit+1`，以区分精确达到上限和仍有尾部数据；超过上限统一返回现有错误合同。管理操作完成后的审计写入使用脱离客户端取消、但带独立短超时的 context，保留请求标识且不无限等待。

管理员事件流为每个连接设置写截止时间和有界发送队列；慢客户端被主动断开，发布方和其他订阅者不受影响。

### 10. 运维一致性

Litestream、Compose、文档统一使用 CLI 当前支持的 `db backup --output <path>` 形式。`baseline` 只执行其命名对应的基线生成/上传动作，不能调用 restore。删除已经被配置入口明确拒绝的旧配置加载死代码。数据库离线维护不再仅凭 `-shm` 文件大小判定服务是否运行；脚本优先通过 Compose 服务状态和数据库锁尝试确认空闲。

## 测试策略

每个行为修复按 TDD 完成：先添加能够稳定复现问题的最小测试并确认失败，再写最小实现使其通过。

本地验证至少包括：

- 受影响 Go 包的定向测试和 `go test ./...`。
- `go vet ./...`，以及本地可用时的 golangci-lint。
- 前端定向 Vitest、全量测试、lint、typecheck 和生产构建。
- Migration 旧库升级测试、部署脚本自测、secret scan、`git diff --check`。
- Docker build 与 Compose acceptance；本地条件不足的 Linux race、E2E 由 GitHub Actions 执行。

GitHub Actions 的 `verify` 与 `e2e` 必须全部成功。分支 CI 失败时只针对证据定位根因并追加修复提交，不跳过检查。合入 `main` 后再次等待 push 触发的完整 CI 成功。

## 提交与合并

提交按可独立验证的职责拆分：现有第四轮业务改动、认证与输入安全、流式与生命周期、迁移与设置一致性、部署与凭据收口。每次只暂存对应文件，并在提交前检查 staged diff。

修复分支推送 GitHub 后，以 Actions 结果作为远端验证记录。全部检查通过且完成最终代码复审后，将分支快进或常规合入本地 `main`，再推送 `origin/main`。禁止 force push、跳过 hook、重写已有远端提交或把失败 CI 合入主分支。

## 非目标与外部动作

- 本轮不新增完整多 Provider 运行时架构。
- 本轮不把一次性远程联调脚本产品化。
- 凭据轮换需要在对应供应商和部署环境执行，仓库修复只负责停止继续泄露。
- 真实星空代理联调不替代自动化测试；只有本地与 GitHub 验证通过后才考虑运行，且不会为完成代码提交而写入凭据。

## 回退

功能修复按独立提交组织，可通过普通 revert 回退。数据库迁移在合入前必须证明旧配置保留；一旦生产执行，回退依赖升级前备份，不使用破坏性 Git 或数据库命令。部署脚本在执行任何恢复前先验证备份存在且目标卷与 Compose 一致。

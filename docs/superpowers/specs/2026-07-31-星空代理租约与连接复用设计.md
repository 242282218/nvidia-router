# 星空代理租约与连接复用设计

- 日期：2026-07-31
- 状态：设计已确认，实现尚未开始
- 适用项目：NVIDIA API 路由器单实例部署
- 目标代理：星空代理 HTTP/HTTPS 3 分钟计量 IP

## 1. 决策摘要

第一版采用“全局粘性单 IP 租约 + 租约级长连接池”：

1. 仅在首个 NVIDIA 上游请求到达时懒提取 `qty=1` 的代理 IP。
2. 同一代理 IP 在 180 秒物理租期内复用，租期最后 15 秒不再接收新请求。
3. 所有 NVIDIA Key、Chat、Responses、Embeddings、Models、ASR 和 TTS 共享当前代理 IP。
4. 每个代理租约拥有可复用的 `http.Transport`，不再按请求克隆 Transport 或在响应结束时清空连接池。
5. 代理获取、拨号或 CONNECT 故障属于代理故障，不得冷却、停用或污染 NVIDIA Key 状态。
6. 代理路径在请求尚未成功写入 NVIDIA 前发生可归因的拨号、CONNECT、TLS 或写入故障时，废弃当前代理、提取新 IP，并使用同一 NVIDIA Key 重放一次。
7. 代理模式下不允许静默回退直连。
8. 第一版不实现每 Key 独立 IP、多 IP 自适应池、管理页面、数据库持久化或多代理供应商抽象。

## 2. 背景与现状

### 2.1 现有 NVIDIA Key 调度

项目已具备：

- 健康 NVIDIA Key 的 Round Robin 调度。
- 每 Key 最大并发固定为 1。
- 忙碌、冷却、鉴权失效和模型禁用过滤。
- 在尚未向下游提交响应时换 Key 重试。
- 流式响应在首个有效事件后禁止重放。
- 请求级连接、首字节和非流式总超时预算。

代理必须复用这条调度链路，不得建立第二套 Key 选择或重试逻辑。

### 2.2 现有 HTTP 传输问题

`internal/upstream/nvidia/chat.go` 的现有实现会为每次尝试克隆 `http.Transport`，并在响应 Body 关闭时调用 `CloseIdleConnections`。Audio 和 Embeddings 沿用同一逻辑。

这保证了每次尝试的动态超时，但导致不同请求无法复用：

- 与代理服务器的 TCP 连接。
- HTTPS CONNECT 隧道。
- 与 NVIDIA 的 TLS 会话。
- NVIDIA 支持时的 HTTP/2 多路复用连接。

因此，仅加 `Transport.Proxy` 能改变出口 IP，却不能实现本需求的传输性能目标。实现必须同时调整 Transport 生命周期。

### 2.3 星空代理契约

已知契约：

- 套餐为 3 分钟计量 IP。
- 提取数量范围为 1 至 200，本项目固定 `qty=1`。
- 当前生成链接使用 TXT 返回格式，成功正文预期为单行 `IP:PORT`。
- HTTP/HTTPS 代理通过 HTTP 代理协议提供，访问 NVIDIA HTTPS 端点时由 Go 发起 CONNECT。
- 官方 API 文档未给出可依赖的错误码表和结构化到期字段。
- 2026-07-31 实测 `api1.xkdaili.com` 和 `api2.xkdaili.com` 的 HTTPS 握手失败，HTTP 端点返回 200 且不跳转 HTTPS。

因为无法从当前 TXT 响应稳定获取到期时间，第一版以部署配置中的 3 分钟 TTL 为准，不猜测 `fmt=6` 的未知输出形式。

## 3. 目标与非目标

### 3.1 功能目标

1. 配置星空代理后，所有 NVIDIA 上游流量必须通过当前代理租约。
2. 无流量时不提取 IP，不产生空闲计量消耗。
3. 只要当前租约可分配，后续请求必须复用它。
4. 同一时刻最多只有一个星空 API 提取请求在执行。
5. 新请求不得获取剩余可分配时间小于等于 15 秒的租约。
6. 已开始的请求必须持有租约引用，直到响应 Body 关闭或请求失败。
7. 代理故障不得改变 NVIDIA Key 的成功、冷却、失效或模型禁用状态。
8. 现有的客户端取消、总超时、首字节超时和首字节后禁止重放语义必须保持。

### 3.2 成本目标

1. 连续有流量时，每个 165 秒可分配窗口最多成功提取 1 个 IP。
2. 进程启动、配置读取和空闲定时任务不得提取 IP。
3. 并发首次请求不得造成多次重复提取。
4. 已开始退役的租约不再提供新请求，但不为了回收连接而强制终止正在进行的请求。

### 3.3 性能目标

1. 同一租约和相同超时配置下，顺序请求必须共享 `http.Transport` 和其连接池。
2. 默认允许每个 NVIDIA 目标保留至少 32 个空闲连接，避免 Go 默认的低 `MaxIdleConnsPerHost` 限制。
3. 支持 NVIDIA 和代理链路时保留 HTTP/2 协商能力。
4. 连接池不得跨代理 IP 租约复用。
5. 生产启用前必须在测试机输出直连、代理冷连接和代理热连接的 P50/P95 首字节时间、成功率和完整响应耗时。

### 3.4 非目标

本轮不实现：

- 每个 NVIDIA Key 固定绑定一个代理 IP。
- 多代理 IP 并发池或根据负载自动扩容。
- SOCKS5 协议。
- 其他代理供应商的通用插件、工厂或接口层。
- 代理配置的 Web 管理页面。
- 代理 IP、租约或统计数据的 SQLite 持久化。
- 周期性后台预取或健康巡检。
- 首字节已提交后切换代理或重放请求。
- 将一条流式连接从已到期代理无缝迁移到新代理。

## 4. 配置契约

### 4.1 环境变量

| 变量 | 默认值 | 含义 |
|---|---|---|
| `NVIDIA_ROUTER_XK_PROXY_API_URL` | 空 | 星空提取 URL；空表示保持直连，非空表示代理必选 |
| `NVIDIA_ROUTER_XK_PROXY_TTL` | `3m` | 一个提取 IP 的物理租期 |
| `NVIDIA_ROUTER_XK_PROXY_RENEW_BEFORE` | `15s` | 物理到期前禁止分配新请求的安全窗口 |

### 4.2 加载与校验

`config.LoadFromEnv` 必须执行以下校验：

1. API URL 为空时，TTL 和 `renew_before` 不启用，应用保持现有直连行为。
2. API URL 非空时，必须是包含 host 的绝对 `http` 或 `https` URL。
3. API URL 不得包含 fragment 或 userinfo。鉴权参数保留在 query 中。
4. URL 中 `qty` 必须且只能为 `1`。程序不自动改写 URL，避免破坏供应商参数契约。
5. TTL 必须在 30 秒至 30 分钟之间。
6. `renew_before` 必须大于 0，且小于 TTL。
7. 所有配置错误只返回环境变量名和固定原因，不得包含 URL 原文、query、`apikey` 或 `sign`。

### 4.3 Docker 配置

`docker-compose.yml` 以可选环境变量传递三个值。`.env.example` 只写占位符，不得写入本次对话或截图中出现的任何真实值。

删除 `NVIDIA_ROUTER_XK_PROXY_API_URL` 并重启进程是唯一的代理功能回滚操作，不需要数据库回滚。

## 5. 组件与责任边界

### 5.1 `internal/xkproxy` 包

新增供应商专用包 `internal/xkproxy`，不新增通用 Provider 工厂。包内部分为两个职责：

- `fetcher.go`：直连星空 API，限制响应大小，解析和验证单个 `IP:PORT`。
- `manager.go`：管理租约状态、并发刷新、引用计数、Transport 缓存、故障退役和进程关闭。

不为第一版建立只有一个实现的公共接口。NVIDIA 上游包可以直接依赖 `*xkproxy.Manager`；未配置时传入 `nil`。

### 5.2 Fetcher 契约

Fetcher 使用专用 `http.Client`：

- 总超时固定为 5 秒。
- Transport 从 `http.DefaultTransport` 克隆，但 `Proxy` 必须置为 `nil`，防止已失效的星空代理或进程环境代理阻断新 IP 提取。
- 只接受 HTTP 2xx。
- 响应 Body 最多读取 4 KiB；超限视为协议错误。
- 去除首尾空白和 CRLF 后，正文必须仅包含一个非空行。
- 使用 `net/netip.ParseAddrPort` 解析，只接受有效 IP 和 1 至 65535 端口。
- 解析成功后构造内存中的 `http://IP:PORT` 代理 URL。
- 任何非 IP 错误文本、多行结果、空响应或 HTML 都必须拒绝。

Fetcher 的对外错误必须是固定的安全错误，不得暴露请求 URL、返回正文、代理 IP 或底层 `url.Error`。

### 5.3 Manager 契约

Manager 持有：

- 时钟依赖，测试使用现有 `internal/clock`。
- TTL 和 `renew_before`。
- 当前可分配租约。
- 已退役但仍有活跃请求的租约集合。
- 一个互斥锁和一个代表当前提取操作的等待 channel。
- 最近一次提取失败的 1 秒负缓存截止时间。
- 进程内递增租约 ID，只用于脱敏日志和测试断言。

Manager 的并发保证：

1. 当可分配租约存在时，获取路径只持锁读取状态、增加引用计数并返回。
2. 当需要提取 IP 且已有其他 goroutine 正在提取时，当前请求等待同一个 channel，不再发起 API 请求。
3. 等待必须同时监听请求 `context` 和 Manager 关闭信号。
4. 网络提取不得在 Manager 互斥锁内执行。
5. 提取成功后原子替换当前租约，并同时唤醒全部等待者。
6. 提取失败后唤醒全部等待者；1 秒内的新请求直接获取同类型安全错误，防止供应商故障时被高并发连续请求。
7. Manager 关闭后不得启动新提取，所有等待者立即返回安全错误。

#### 5.3.1 建议方法契约

生产代码使用具体类型，不为单个供应商创建公共接口：

```go
func New(
	apiURL *url.URL,
	ttl time.Duration,
	renewBefore time.Duration,
	base *http.Transport,
	source clock.Clock,
	logger *slog.Logger,
) (*Manager, error)

func (m *Manager) Acquire(
	ctx context.Context,
	snapshot runtimeconfig.Snapshot,
) (*Handle, error)

func (m *Manager) Close()

func (h *Handle) Transport() http.RoundTripper
func (h *Handle) Retire(reason RetireReason)
func (h *Handle) Release()
```

`Handle` 是单次 NVIDIA HTTP 发送持有的引用，内部指向租约和对应超时组合的 Transport。`Retire` 和 `Release` 都必须幂等：

- `Retire` 最多将底层租约从 `active` 改为 `retiring` 一次。
- `Release` 最多将租约活跃引用数减一次。
- 先 `Retire` 后 `Release`、只 `Release`、以及响应 Body 多次 `Close` 都不得产生负引用计数或 panic。

测试所需的 Fetcher 注入使用包内非导出构造器或函数字段，不扩大生产 API。

`base` 来自当前 NVIDIA `http.Client.Transport`。如果 Client 的 Transport 为 `nil`，App 传入 `http.DefaultTransport.(*http.Transport)`。代理已启用但现有 Transport 不是 `*http.Transport` 时，应用在启动阶段返回安全配置错误，不在运行时静默丢失自定义 TLS/拨号设置。

### 5.4 租约模型

每个内存租约包含：

- 脱敏递增 ID。
- 代理 URL，仅供 Transport 配置使用。
- `acquired_at`。
- `expires_at = acquired_at + ttl`。
- `usable_until = expires_at - renew_before`。
- 活跃请求引用数。
- 已服务请求数和复用命中数。
- 退役原因枚举。
- 按超时组合缓存的 Transport。

代理 URL 和 IP 不得出现在 `String()`、JSON、日志、统计、错误或管理 API 中。

### 5.5 NVIDIA Client 集成

`internal/upstream/nvidia.Client` 继续作为所有 NVIDIA 端点的唯一传输入口。新增的共享发送逻辑必须同时被以下方法复用：

- `Models`
- `ValidateCredential`
- `Chat`
- `Embeddings`
- `AudioTranscriptions`
- `AudioSpeech`

禁止只在 Chat 或只在业务请求中使用代理，否则 Key 导入、手工测试和模型发现会泄漏直连出口并产生不一致结果。

NVIDIA Client 必须接收当前 `runtimeconfig.Provider`，使没有 Attempt Budget 的 Models 和 Key 验证请求也能使用当前连接和首字节超时。处于 Attempt 链路的请求优先使用请求上下文中的预算快照。

#### 5.5.1 Client 构造契约

`NewClient` 使用显式依赖，不增加全局变量或隐式环境变量读取：

```go
func NewClient(
	httpClient *http.Client,
	descriptor Descriptor,
	settings runtimeconfig.Provider,
	proxy *xkproxy.Manager,
) (*Client, error)
```

- `httpClient` 继续用于直连模式和测试注入。
- `settings` 必填，App 传入现有 `runtimeconfig.Store`；测试使用固定 Provider。
- `proxy == nil` 表示直连，必须保持现有行为。
- `proxy != nil` 表示代理必选，任何端点不得绕过 Manager。

#### 5.5.2 共享发送器

Client 内部新增一个非导出共享方法，所有端点只负责提供可重建请求的 factory：

```go
type requestFactory func(context.Context) (*http.Request, error)

func (c *Client) do(
	ctx context.Context,
	snapshot runtimeconfig.Snapshot,
	build requestFactory,
) (*http.Response, error)
```

`do` 的语义固定为：

1. 直连模式使用现有超时 Transport 路径，不改变故障分类。
2. 代理模式从 Manager 获取 Handle，每次发送前调用 factory 构造全新 request 和 Body。
3. 代理模式为每次发送注入 `httptrace.ClientTrace.WroteRequest`，用同步安全布尔值记录请求是否已经成功写入上游。
4. 收到 response 后将 Body 包装为幂等 release body，关闭 Body 时释放 Handle。
5. `RoundTrip` 返回 error 后先检查 `ctx.Err()`。原 context 已取消或超时时只释放 Handle，不退役代理、不提取新 IP、不重放。
6. 原 context 仍有效、`RoundTrip` 返回 error、response 为 `nil`，且 `WroteRequest` 未成功时，先退役和释放 Handle，再获取新租约并调用 factory 重放一次。
7. 原 context 仍有效但 `WroteRequest` 已成功时，只释放 Handle，不退役或刷新代理，将错误交回现有 Attempt/Fault 链路。
8. 第二个代理仍在 `WroteRequest` 成功前发生传输错误时，退役和释放第二个 Handle，返回 `xkproxy.Error`，不尝试第三次。
9. factory 构造失败是本地/NVIDIA 请求构造错误，只释放 Handle，不退役健康代理。
10. response 非 `nil` 时，不论 HTTP 状态码为何，都不由 `do` 刷新代理。

Models 和 `ValidateCredential` 调用 `c.settings.Snapshot()`。Chat、Responses、Embeddings、ASR 和 TTS 使用 Attempt Budget 快照。

## 6. 租约状态机

### 6.1 状态

| 状态 | 含义 | 是否可分配新请求 |
|---|---|---|
| `empty` | 尚未提取或旧租约已移除 | 否 |
| `fetching` | 一个 goroutine 正在提取 IP | 否，其他请求等待 |
| `active` | 当前时间早于 `usable_until` | 是 |
| `retiring` | 进入安全窗口、传输故障或被新租约替换 | 否 |
| `closed` | 应用正在关闭 | 否 |

### 6.2 转移规则

1. `empty -> fetching`：首个需要 NVIDIA 上游的请求发起懒提取。
2. `fetching -> active`：提取和解析成功。
3. `fetching -> empty`：提取失败，同时启动 1 秒负缓存。
4. `active -> retiring`：当前时间大于等于 `usable_until`。
5. `active -> retiring`：请求在成功写入 NVIDIA 之前发生可归因的代理路径传输错误。
6. `retiring -> removed`：活跃引用数归零，关闭其全部空闲连接并移除租约。
7. `active/retiring/empty/fetching -> closed`：应用关闭。

不使用独立定时 goroutine 在 `usable_until` 到达时切换状态。每次新获取都用时钟懒判断，避免空闲时预取和定时器生命周期复杂性。

## 7. Transport 与连接复用

### 7.1 Transport 键

同一租约内，Transport 按以下稳定组合缓存：

```text
(connect_timeout_ms, first_byte_timeout_ms)
```

代理 URL 不需要出现在键中，因为 Transport 不跨租约共享。

`snapshotFromBudget` 不再使用每次调用时略有波动的“剩余毫秒数”作为 Transport 配置，而是使用 Attempt Budget 中稳定的连接超时和单次首字节超时。实际的首字节截止时间仍由现有 Budget 与 SSE/Audio Prime 上下文控制，换代理或换 Key 不得重置客户端总超时。

### 7.2 Transport 配置

每个新 Transport 从 Manager 构造时接收的 NVIDIA base Transport 调用 `Clone()` 创建，然后设置：

| 字段 | 值 |
|---|---|
| `Proxy` | `http.ProxyURL(leaseProxyURL)` |
| `DialContext` | 使用当前 Transport 键中的连接超时 |
| `ResponseHeaderTimeout` | 使用当前 Transport 键中的首字节超时 |
| `MaxIdleConns` | `64` |
| `MaxIdleConnsPerHost` | `32` |
| `IdleConnTimeout` | `60s` |
| `ForceAttemptHTTP2` | `true` |

其他 TLS、Root CA、KeepAlive、Expect-Continue 和压缩行为保留现有 NVIDIA base Transport 语义。生产默认 base 来自 Go 默认 Transport。不禁用 TLS 证书验证，不信任代理服务器提供的中间人证书。

### 7.3 Transport 生命周期

1. Transport 在首次使用对应超时组合时懒创建。
2. 同一租约与超时组合下的后续请求共享 Transport。
3. 正常响应 Body 关闭时只释放租约引用，不调用 `CloseIdleConnections`。
4. Transport 错误且没有收到 HTTP 响应时，立即标记租约退役并调用其 Transport 的 `CloseIdleConnections`。该操作不会中断正在使用的连接。
5. 租约最后一个引用释放时，再次关闭全部空闲连接并删除 Transport 缓存。
6. 应用关闭时停止新分配，关闭所有空闲连接；现有 App 的优雅关闭截止时间仍负责终止超时活跃请求。

## 8. 请求数据流

### 8.1 正常请求

1. 下游请求进入现有 HTTP handler。
2. Attempt 从现有 Key Pool 获取 NVIDIA Key 租约。
3. NVIDIA Client 获取当前代理租约。
4. Manager 增加租约活跃引用，返回对应超时组合的共享 Transport。
5. NVIDIA Client 构造可重放的上游请求并通过 Transport 发送。
6. 一旦收到 NVIDIA HTTP 响应，代理路径视为成功；HTTP 401、403、429 或 5xx 由现有 NVIDIA Fault 分类器处理。
7. 响应 Body 被包装，确保关闭时恰好释放一次代理租约引用。
8. Attempt 和 handler 按现有流程验证、Prime、提交并转发响应。

### 8.2 首次懒提取

1. Manager 发现没有可分配租约。
2. 首个 goroutine 成为提取者，其他 goroutine 等待。
3. Fetcher 通过不使用代理的专用 Client 调用星空 API。
4. 提取成功后创建租约，第一个请求计入“首用”，后续等待者计入“复用命中”。
5. 所有等待者共享同一租约。

### 8.3 到期刷新

1. 新请求发现 `now >= usable_until`。
2. 旧租约进入 `retiring`，不再接收新请求。
3. 已经持有旧租约的流式或非流式请求不被主动中断。
4. 当前新请求触发一次同步懒提取，提取耗时计入该请求现有超时预算。
5. 新租约成功后原子替换当前租约。

不做提前后台预取。这会让刷新边界的首个请求增加一次提取延迟，但避免在流量突然停止时浪费新 IP。

### 8.4 代理故障重试

1. NVIDIA Client 通过 `net/http/httptrace.ClientTrace.WroteRequest` 记录请求是否已经成功写入上游。回调与 RoundTrip 可能并发，状态使用 `atomic.Bool` 或等价同步保护。
2. 当前上游请求发生传输错误，且 `WroteRequest` 尚未以 `err == nil` 完成。该条件覆盖代理拨号、CONNECT、上游 TLS 握手和请求写入失败。
3. NVIDIA Client 关闭该请求使用的任何局部资源，并释放租约引用。
4. Manager 将当前租约标记为 `transport_error` 退役，不再将它分配给新请求。
5. 在原请求 context 和预算内懒提取一个新 IP。
6. 使用新租约和同一 NVIDIA Key 重建请求 Body，重放一次。
7. 重放成功则正常返回，不增加 NVIDIA Key Attempt 次数，不改变 Key 状态。
8. 新代理仍在成功写入请求前失败时，不提取第三个 IP，返回稳定代理错误。

如果 `WroteRequest` 已以 `err == nil` 完成，之后发生的响应头超时、EOF 或连接中断属于“请求已写入后的上游路径故障”。该错误不退役代理、不提取新 IP，继续交给现有 Attempt/Fault 逻辑。这避免把 NVIDIA 处理慢误判为坏代理，也避免无依据地重复执行已写入的 POST 请求。

所有 POST 请求体在当前实现中均已经缓存为字节或可重建的 multipart 内容。实现时必须通过 `http.NewRequestWithContext` 和 `bytes.Reader`/新 reader 为每次发送创建新 Body，不得重用已读取的 `io.ReadCloser`。

## 9. 故障归因与错误契约

### 9.1 代理故障

以下错误归属代理基础设施：

- 星空 API 超时、DNS、连接或非 2xx。
- 星空 API 正文超限或不是唯一合法 `IP:PORT`。
- 连接代理 IP 失败。
- HTTP CONNECT 失败。
- 在 `WroteRequest` 成功前发生的 TLS、EOF、连接重置、超时或写入错误。

这些错误必须使用可被 `errors.As` 识别的 `xkproxy.Error`。其 `Error()` 只返回固定安全文本，内部 reason 使用有限枚举：

- `fetch_failed`
- `invalid_response`
- `transport_failed`
- `manager_closed`

`xkproxy.Error` 可以通过 `Unwrap()` 保留底层 cause 供 `errors.Is/As` 和测试使用，但其自身 `Error()` 必须固定返回 `upstream proxy unavailable`。日志和 HTTP 层禁止单独打印 `Unwrap()` 后的 cause。

### 9.2 NVIDIA 故障

只要成功建立 CONNECT/TLS 并收到 NVIDIA HTTP 响应，其状态码和正文验证结果继续交给现有 `fault.Classify`：

- 401/403 Key 整体鉴权错误。
- 模型级权限错误。
- 429 限流。
- 5xx 上游故障。
- 响应协议错误。

收到 HTTP 响应后不得因状态码或 NVIDIA 正文而更换代理 IP。

### 9.3 Router 行为

`router.Attempt.executeLease` 在识别到 `xkproxy.Error` 时必须：

1. 关闭任何响应资源。
2. 释放当前 NVIDIA Key 租约。
3. 不调用 `MarkFailure`。
4. 不把当前 Key 写入持久化冷却或模型 block。
5. 不切换下一个 NVIDIA Key，因为全局代理故障与 Key 无关。
6. 向下游返回 HTTP 502，稳定错误码为 `upstream_proxy_unavailable`，稳定消息为 `The upstream proxy is temporarily unavailable.`。

管理端 Models、Key 验证和模型验证使用现有端点的安全错误响应，但必须保留“临时不可用”语义，不得把 Key 标记为无效。

### 9.4 Key 导入与手工验证

Key 导入和手工测试不经过 `router.Attempt`，必须单独处理代理错误。

`nvidia.ValidationState` 新增明确状态：

```go
ValidationProxyUnavailable
```

`Client.ValidateCredential` 在共享发送器最终返回 `xkproxy.Error` 时，生成：

```go
ValidationResult{
	State:     ValidationProxyUnavailable,
	SafeError: "upstream proxy unavailable",
	Fault:     nil,
}
```

该状态的业务语义：

1. `nvidiakey.Service.Import` 将其映射为 `ImportStatusTemporarilyUnavailable` 和固定 reason `proxy_temporarily_unavailable`，不保存新 Key。
2. `nvidiakey.Service.Test` 返回 `status=temporarily_unavailable` 和 `reason=proxy_temporarily_unavailable`。
3. `nvidiakey.Service.Test` 对该状态不调用 `MarkFailure`，不调用 `MarkSuccess`，返回零值 Snapshot，因此 admin handler 不同步任何 Key Pool 状态。
4. 现有 `ValidationTemporarilyUnavailable` 继续表示已到达 NVIDIA 且可能需要冷却 Key 的 429/5xx 等故障，不得与代理状态合并。
5. 现有“失败结果必须带 Fault”的防御检查仅适用于需要写 Key 状态的失败；`ValidationProxyUnavailable` 是唯一允许 `Fault == nil` 的明确失败状态。

### 9.5 模型发现与手工模型验证

`modelcatalog.Service` 必须保留代理错误的类型：

1. `DiscoverCandidates` 不吞掉 `xkproxy.Error`，admin 端映射为 502 `upstream_proxy_unavailable`。
2. `testTargetModel` 在 tester 返回 `xkproxy.Error` 时原样向上传递，不将其转换成 `ErrManualTestRequired`。
3. 代理错误时不写 `capability_verified_at`，不清除 Key-model block，不修改 NVIDIA Key 状态。
4. 非代理的 NVIDIA HTTP/协议失败继续使用现有 `ErrManualTestRequired` 行为。

admin 错误 writer 对任何链路中的 `xkproxy.Error` 统一返回 502 和固定公开消息，不返回底层 cause。

### 9.6 直连回退

当 `NVIDIA_ROUTER_XK_PROXY_API_URL` 已配置时，以下行为均禁止：

- 提取 API 失败后直连 NVIDIA。
- 代理拨号失败后直连 NVIDIA。
- 代理到期但新 IP 尚未获得时直连 NVIDIA。
- 仅 Models 或 Key 验证直连，业务请求走代理。

未配置 API URL 时，应用不创建 Manager，并完全保持当前直连行为。

## 10. 超时、取消与重放边界

1. 星空 API 提取耗时必须包含在原上游请求 context 中，不得为刷新代理创建与客户端无关的后台 context。
2. Fetcher 的 5 秒超时是上限；客户端或 Attempt Budget 更早取消时立即返回。
3. 等待其他 goroutine 提取 IP 时，客户端取消必须立即退出等待。
4. 代理内部重放使用原 Attempt Budget，不重置连接、首字节或非流式总超时。
5. 只有“原 context 仍有效、未收到 HTTP 响应，且 `WroteRequest` 未成功”的可归因代理路径错误允许代理内部重放。
6. 收到 HTTP 响应头后，即使首个 SSE 事件或音频字节尚未到达，也不通过代理层自动重放；现有 Prime 和 Attempt 逻辑决定是否换 NVIDIA Key。
7. 已向下游提交任何响应字节后，代理层、NVIDIA Client 和 Attempt 均不得重放。

## 11. 流式请求特别约束

1. SSE 和 TTS 在响应 Body 关闭前持有代理租约引用。
2. 进入 `renew_before` 窗口仅阻止新请求，不主动关闭旧请求。
3. 3 分钟代理是物理限制。如果供应商在 TTL 到达时断开已建立 CONNECT，持续超过 3 分钟的流无法通过软件切换 IP 保持连续。
4. 实现不得用缓冲整个 SSE/TTS 响应的方式规避这一限制。
5. 生产真实测试如果证明已建立连接在 180 秒处被稳定中断，长流场景必须改用更长 TTL 套餐，而不是增加重试代码。

## 12. 安全与脱敏

### 12.1 提取凭据

`NVIDIA_ROUTER_XK_PROXY_API_URL` 同时包含 `apikey` 和 `sign`，按完整密钥处理：

- 仅从环境变量加载。
- 不写入 SQLite。
- 不通过管理 API 返回。
- 不打印配置值或 URL。
- 不将底层包含 URL 的错误原文包装成可见错误。
- 不把真实值放入 `.env.example`、Compose、测试 fixture、文档、截图或脚本。

实现前必须在星空后台更换本次对话已暴露的凭据，并启用服务器出口 IP 白名单。

### 12.2 HTTP 提取风险

当前星空 API 只能通过 HTTP 成功访问，因此 API URL 和凭据在运输层不加密。代码无法消除该供应商限制。部署门禁为：

1. 必须开启星空账户的提取来源 IP 白名单。
2. 提取凭据只用于该套餐，不与其他系统共用。
3. 凭据定期轮换，并在提取量异常时立即废弃。
4. 如果供应商后续提供经验证的 HTTPS 端点，仅替换环境变量 URL，不需要修改 Manager。

### 12.3 上游 TLS

星空 HTTP 代理使用 CONNECT 转发 NVIDIA HTTPS 流量。NVIDIA API Key、请求正文和响应正文仍由 NVIDIA TLS 保护。实现必须保留 Go 默认证书校验，代理无法提供受信任中间人证书。

### 12.4 Secret Scan

`scripts/check-secrets.sh` 需要覆盖以下 tracked 文本风险：

- `api[0-9].xkdaili.com/tools/XApi.ashx` 且同时存在非占位的 `apikey`/`sign`。
- `NVIDIA_ROUTER_XK_PROXY_API_URL` 后跟非占位真实 URL。

占位符、测试中的 `invalid` 值和本设计文档的变量名不得误报。

## 13. 日志与可观测性

第一版不增加数据库表或管理页面。Manager 仅在租约级别输出结构化日志，不为每个请求增加日志噪音。

### 13.1 允许字段

- `lease_id`：进程内递增整数。
- `fetch_duration_ms`。
- `usable_duration_ms`。
- `served_requests`。
- `reuse_hits`。
- `active_requests`。
- `retire_reason`：`renew_window`、`transport_error`、`shutdown`。
- `error_reason`：安全枚举，不是原始 error。

### 13.2 禁止字段

- 代理 IP 和端口。
- 星空 API URL、host、query、`apikey` 和 `sign`。
- NVIDIA API Key。
- NVIDIA 请求或响应正文。
- 可能包含 URL 的底层网络错误原文。

### 13.3 必要事件

1. `proxy_lease_acquired`：新租约创建成功。
2. `proxy_lease_retired`：租约退役，记录服务请求数、复用命中和原因。
3. `proxy_fetch_failed`：提取失败，只记录安全 reason。
4. `proxy_manager_closed`：关闭时记录累计提取数和退役数。

通过 `proxy_lease_retired.served_requests` 即可计算每个计量 IP 的价值，无需持久化代理 IP。

## 14. 关闭与资源回收

1. `app.App` 持有 Manager，且只在代理已配置时创建。
2. App 开始关闭时先禁止新下游请求，再调用 Manager 关闭。
3. Manager 关闭后唤醒所有等待提取的 goroutine。
4. Manager 对所有 Transport 调用 `CloseIdleConnections`。
5. 正在执行的请求由 App 现有 root context 和 shutdown grace 控制，Manager 不创建脱离 App 生命周期的 goroutine。
6. Manager `Close` 必须幂等，重复调用不 panic、不重复关闭 channel。

### 16.2 Fetcher 单元测试

- CRLF 和首尾空白被安全去除。
- 空正文、多行 IP、非 IP host、端口越界、HTML 和中文错误正文失败。
- 非 2xx 失败。

- 实际请求不使用进程 `HTTP_PROXY`/`HTTPS_PROXY`。

### 16.3 Manager 状态和并发测试

使用 fake clock 和可计数 Fetcher 覆盖：

- 构造 Manager 不提取 IP。
- 首次获取只提取一次。
- 50 个同时首次获取只产生一次 Fetcher 调用，且全部获得同一租约 ID。
- `now < usable_until` 始终复用。
- `now == usable_until` 立即退役并提取一次新 IP。
- 旧租约有活跃引用时可与新租约并存。
- 旧租约引用归零后关闭 Transport。
- 提取失败唤醒全部等待者。
- 1 秒负缓存期内不再调用 Fetcher，边界到达后允许一次新提取。
- 等待 context 取消时不泄漏 goroutine。
- `Close` 幂等，并唤醒全部等待者。
- `go test -race` 不报告租约、Transport 缓存或关闭竞态。

### 16.4 Transport 复用测试

在 `_test.go` 中实现最小 HTTP CONNECT 代理，不增加生产依赖。覆盖：

- NVIDIA HTTPS 请求实际经过 CONNECT 代理。
- 代理模式下 fake NVIDIA 直连通道被禁止时请求仍成功。
- 同一租约、同一超时组合的 Transport 指针相同。
- 不同超时组合使用不同 Transport，但仍属于同一租约。
- 不同租约不共享 Transport。
- 自定义 base Transport 的 Root CA 和 TLS 设置在代理 Transport 中保留。
- 代理已启用但 base RoundTripper 不是 `*http.Transport` 时，构造阶段安全失败。
- 连续 20 个顺序请求的 CONNECT/TCP/TLS 新建次数明显小于请求数；在支持 KeepAlive/HTTP2 的 fixture 中目标为不超过 2 次。
- 普通 Body 关闭不会关闭租约 Transport 空闲池。
- 租约退役后不再复用旧连接。
- 连接、响应头和 SSE/Audio Prime 超时保持现有语义。

### 16.5 故障归因集成测试

覆盖：

- 首个代理拨号失败，第二个代理使用同一 NVIDIA Key 成功。
- 代理内部重试恰好一次，不提取第三个 IP。
- 两个代理都失败时返回 502 `upstream_proxy_unavailable`。
- 代理已成功建立且 `WroteRequest` 成功后发生 `ResponseHeaderTimeout` 时，不刷新代理，现有 Attempt 仍可按原规则换 Key。
- `WroteRequest` 成功后的 EOF/连接中断不计为代理提取失败，不额外消耗 IP。
- 代理获取失败时 fake NVIDIA 接收到 0 个直连请求。
- 代理错误前后 NVIDIA Key 的 `auth_invalid`、`cooldown_until`、`consecutive_failures`、`last_error_code` 和模型 block 不变。
- Key 导入遇到代理错误时返回 `temporarily_unavailable/proxy_temporarily_unavailable`，且不创建 Key 记录。
- 已存在 Key 的手工测试遇到代理错误时返回零值 Snapshot，不调用 `MarkFailure`。
- 模型发现和手工模型验证遇到代理错误时返回脱敏 502，不写验证时间、不清 block。
- NVIDIA 401、429、5xx 仍按现有规则改变 Key 状态，且不刷新代理。
- 客户端取消或原 Attempt Budget 到期不退役健康代理，不触发额外提取或重放。
- 首字节已提交后连接中断不刷新代理、不换 Key、不重放。

## 17. 真实环境验证

### 17.1 脚本

新增 `scripts/test/live-xkproxy.sh`，要求：

- 必须显式设置真实测试开关才允许运行。
- API URL、NVIDIA Key 和管理密码只从运行时环境变量读取。
- 脚本不回显、不写文件、不写 shell trace 的敏感值。
- 输出仅包含 case 名、PASS/FAIL、HTTP 状态、耗时统计、提取次数和每租约请求数。
- 不输出代理 IP、上游 request ID、请求正文或响应正文。
- 任何临时文件权限为 0600，退出时必须清理。

### 17.2 测试机步骤

1. 确认服务、端口、Docker 和磁盘状态，不与现有进程冲突。
2. 使用同一个 NVIDIA Key、模型、请求正文和并发度运行直连基线。
3. 启用代理，运行首个冷连接请求。
4. 在同一租约内运行至少 20 个顺序请求和一组不超过健康 Key 数的并发请求。
5. 持续到 165 秒边界，验证只发生一次正常刷新。
6. 运行一条持续跨越 180 秒的 SSE 流，记录供应商是否中断已建立连接。
7. 注入一个可控失败代理 fixture 验证故障归因；不用破坏真实星空账户或生产流量的方式制造失败。
8. 测试后删除临时容器、进程、访问 Key 和测试数据，保留脱敏结果。

### 17.3 性能准入门槛

功能正确不等于网络加速。生产默认启用前必须同时满足：

1. 代理热连接成功率不低于 99%。
2. 代理热连接 P95 首字节时间不高于直连基线的 120%。
3. 代理热连接成功请求吞吐不低于直连基线的 90%。
4. 代理热连接 P50 首字节时间必须优于代理冷连接；否则说明连接复用未生效。
5. 165 秒可分配窗口内的正常提取次数恰好为 1。

任一门槛不满足时，不得宣称“提高传输速率”。应优先调整星空地区节点或套餐，而不是无证据增加代码并发和预取复杂度。

## 18. CI 与验证命令

轻量、无真实凭据的验证进入 GitHub Actions：

```bash
go test ./internal/config ./internal/xkproxy ./internal/upstream/nvidia ./internal/router ./tests/mocknvidia
go test -race ./internal/xkproxy ./internal/upstream/nvidia ./internal/router ./tests/mocknvidia
go vet ./...
bash scripts/check-secrets.sh
bash -n scripts/test/live-xkproxy.sh
```

完整回归在提交前执行：

```bash
go test ./...
golangci-lint run --fix ./...
```

如果当前环境没有 `golangci-lint`，实现者必须明确记录该缺口，不得用 `go vet` 声称代替了 golangci-lint。

真实星空与 NVIDIA 联调只在测试机上通过显式开关运行，不在 CI 中传入真实凭据。

## 19. 验收标准

实现只有在以下条件全部满足时才能验收：

### 19.1 代理获取与成本

- 无业务流量不提取 IP。
- 50 个并发首次请求只调用一次星空 API。
- 当前租约在 165 秒内不因正常请求额外刷新。
- 到达 165 秒边界后第一个新请求恰好提取一次。
- 并发刷新不重复消耗 IP。

### 19.2 路由与安全

- 配置代理后，所有 NVIDIA 端点都通过代理。
- 代理失败不发生直连回退。
- 代理故障不改变任何 NVIDIA Key 状态。
- API URL、凭据和代理 IP 不出现在日志、错误、HTTP 响应、数据库或 Git tracked 文件中。
- 进程启动时的错误不包含完整配置 URL。

### 19.3 传输与重试

- 同一租约内 Transport 和空闲连接可复用。
- 响应 Body 关闭不会每次清空连接池。
- `WroteRequest` 成功前的可归因代理传输失败仅使用同一 NVIDIA Key 重放一次。
- `WroteRequest` 成功后的上游超时或中断不刷新代理。
- 代理内部重放不重置请求总预算。
- 首字节提交后不重放。
- 现有连接超时、响应头超时、SSE Prime、Audio Prime 和客户端取消测试全部通过。

### 19.4 工程质量

- 无新的生产第三方依赖。
- 无数据库 migration。
- 无与本功能无关的重构。
- 所有新错误用 `%w` 保留内部原因时，必须确保最终可见文本不暴露 URL 或凭据。
- 所有新的并发逻辑通过 race 测试。
- 目标 Go 测试、全量 Go 测试、secret scan 和脚本语法检查通过。
- 真实性能结果使用明确 PASS/FAIL 结论，不用“看起来更快”代替指标。

## 20. 发布、回滚与后续升级条件

### 20.1 发布顺序

1. 在星空后台轮换已暴露的凭据。
2. 启用测试机出口 IP 白名单。
3. 运行 CI 单元、集成、race、secret scan 和构建。
4. 使用测试机执行真实星空 + NVIDIA 功能和性能验证。
5. 只有功能、安全和性能门槛都通过后，才在生产配置 API URL。
6. 发布后观察租约退役日志中的每 IP 请求数、运输故障刷新比例和提取延迟。

### 20.2 回滚

1. 删除 `NVIDIA_ROUTER_XK_PROXY_API_URL`。
2. 重启单实例应用。
3. 验证 NVIDIA 直连主路径。

回滚不涉及数据库、管理配置或代理状态清理。

### 20.3 升级为多 IP 池的条件

只有以下任一证据持续出现，才开始设计多 IP 池或每 Key 亲和性：

- 确认星空单 IP 存在低于当前健康 Key 数的并发上限。
- 代理热连接已复用，但吞吐仍显著低于直连。
- NVIDIA 经实测存在来源 IP 级而非 Key 级限流。
- 单 IP 故障域导致不可接受的全局成功率。

升级设计必须使用本轮日志与真实测试数据确定池容量，不提前在第一版中加入未使用的扩展点。

# 数据面执行核心收敛设计

## 背景

Chat 和 Responses 入口都完成模型解析、reasoning 处理、provider 分流和观测；NVIDIA 与 OpenCodeFree 又分别维护不同的重试、空响应、非流式校验和流式提交逻辑。当前行为可以工作，但重复责任造成错误码、重试边界和资源释放容易漂移，正是 Codex/Cherry 遇到瞬态错误时难以判断的原因之一。

## 目标

第一阶段只收敛数据面调用生命周期，不改变公开端点、数据库结构、模型能力门控或 Responses 的支持边界：

1. Chat 与 Responses 继续各自解析协议，但 provider 调用、请求上下文、一次性重试边界和错误映射使用同一套核心策略。
2. OpenCodeFree Chat 与 Responses 共用状态码读取、瞬态判断、500ms 等待和“首字节后不重放”规则。
3. 保持现有安全语义：请求已写出或已提交上游后不重放；敏感上游正文只保留现有受限错误信息；代理错误仍映射为 `upstream_proxy_unavailable`。
4. 通过单元测试锁定空响应、协议错误、429、404、5xx、流式首字节前重试和首字节后禁止重试。

## 非目标

- 不新增或修改 migration，不改变 `tools_status` 的 strict/inferred/unknown 语义。
- 不放宽或扩展 Responses hosted tools、stateful response、background、conversation 和 prompt cache 能力。
- 不调整线上模型白名单、代理池、Key 池、provider 凭据或 runtime settings。
- 不在本阶段拆分控制面，不修改前端或内嵌 dist。

## 设计

### 1. 统一的 provider 调用策略

在 `internal/httpapi/v1` 增加一个仅面向 HTTP handler 的小型执行组件。它接收一次 provider call 函数、请求 context、是否 stream 和提交回调，不了解 Chat/Responses payload，也不持有模型目录状态。

执行规则固定为：

- provider 返回 transport error 或空 response：调用方负责把错误映射为现有 public error；不得在已写客户端数据后重试。
- 非 2xx：读取最多 8 KiB、错误消息最多 512 字节；404 映射 `upstream_model_not_found`；429 不自动重放；5xx 和 436 仅在第一次且客户端尚未写出时重试一次，等待 500ms。
- 2xx stream：由协议专属 callback 负责 prime/转换和终止事件；除非 callback 明确证明客户端尚未写出，否则不重试流内协议错误；首字节后只写显式 stream error，不重放。第一阶段保持现有 stream callback 的提交语义。
- 2xx non-stream：先执行统一的 Chat 响应校验，再由协议 callback 完成原始 Chat 或 Responses 转换；空响应和协议错误只在第一次调用时重试一次。
- 每个 attempt 都独立创建带转发头和 `openCodeFreeRequestTimeout` 的 context，并在 attempt 结束关闭 body、取消 context。

### 2. 适配器边界

- `Chat` 适配器只提供 Chat 流式写入和 Chat 非流式响应写入 callback。
- `Responses` 适配器只提供 Responses SSE 重建和 Chat→Responses 非流式转换 callback。
- `OpenCodeFreeChat` 接口保持不变，现有 `firstWriteTracker` 继续作为唯一提交状态来源；两个旧的未导出 OCF 循环和状态映射函数在迁移后删除，避免保留第二套生命周期实现。
- NVIDIA 的 `AttemptRunner` 保持不变。共享组件首先服务 OCF 直连路径；NVIDIA 的 Key 池重试仍由 `router.Attempt` 控制，但其错误分类和协议校验测试必须与 OCF 使用同一组语义断言。

### 3. 可观测性

现有 `error_code` 不改名。新增的共享测试只断言 `upstream_unavailable`、`upstream_model_not_found`、`upstream_protocol_error`、`upstream_empty_response`、`upstream_stream_truncated` 和 `upstream_proxy_unavailable` 等安全标量，不记录响应正文。

## 测试策略

1. 先为共享状态分类、重试门控和 response body 关闭行为写失败测试。
2. 运行 `go test ./internal/httpapi/v1` 确认测试先失败，再实现最小共享组件。
3. 运行 `go test ./internal/httpapi/v1 ./internal/router ./internal/upstream/opencodefree`，确保 Chat、Responses、Attempt 和 OCF transport 语义不回归。
4. 最后运行 `go test ./...`、`go vet ./...`、`git diff --check`。
5. 不做线上部署；若本地通过，下一阶段再在国内环境用稳定模型门控和短 Responses/Chat 矩阵验证。

## 回滚

本阶段代码只在 `codex/optimize-executor-20260828` 分支；回滚为删除共享组件并恢复两个 OCF handler 的薄包装即可，不涉及数据库或远端状态。

## 第二阶段：请求准备核心

在第一阶段 OCF 生命周期收敛后，Chat 与 Responses 入口仍然各自重复以下步骤：设置模型/stream 观测、读取 requested reasoning、调用 `ModelResolver.Resolve`、记录能力错误、执行 `MarshalForWithOptions`、提取有效 reasoning wire 字段并设置观测来源。

第二阶段增加同包内部的 `prepareModelRequest`，接受两个协议 Request 都满足的最小接口，返回已解析模型、上游 Chat body、stream、reasoning 观测所需的不可变结果。它不负责解析原始 JSON、不负责 Responses 事件转换、不改变任何错误映射；Chat/Responses handler 只保留协议专属的 body lease、响应写入和 provider 分支。

准备器必须保持以下顺序：先设置请求模型观测，再 Resolve；Resolve 失败要记录 capability error code；Marshal 成功后再设置 effective reasoning 和 source。任何失败都不应调用 provider。通过 Chat 与 Responses 各一个集成回归测试确认相同的模型 Resolve、reasoning source 和 provider body。

# vibe 场景模型优化设计

## 目标

根据 docs/plans/2026-08-24-vibe场景多维复测报告.md，把“基础请求成功”升级为按模型、按能力、按错误类型可解释且可验收的 vibe-coding 运行链路，重点解决代理瞬态失败、流式截断、工具能力元数据漂移和上下文窗口缺少可信声明的问题。

## 已确认的证据

- 10 个启用 Chat 模型完成基础请求，7 个有效 HTTP 200，3 个 NVIDIA 请求返回 502 upstream_proxy_unavailable。
- OpenCodeFree 深测覆盖思考、thinking 开关、工具、流式、长输入和重复稳定性；x-preview 出现一次流式 503。
- 综合矩阵中 x-preview 完成双工具及 follow-up；Nemotron、StepFun、Hy3 的工具请求返回 501 not_implemented。
- 当前探针已经能保存 reasoning 的状态和 wire format，但 supports_tools 只有布尔值，无法区分“已验证支持”“候选推断”“明确不支持”和“本次探测暂时失败”。
- context_length 已有 operator-owned 字段和管理端编辑能力，但真实目录仍不能据长输入成功推断 32K/128K 上限。

## 约束与不做事项

- 真实联调、部署和运行态验收只在 hangzhou2-2 执行。
- 密码、Access Key、provider 凭据和完整响应只在运行时使用，不进入代码、报告、日志或记忆。
- 不自动删除或永久禁用模型；能力探测只更新能力状态，模型是否启用仍由管理员决定。
- 不根据一次长输入成功猜测上下文窗口；没有可信证据的 context_length 保持 0。
- 不引入新的 provider、全局 overlay、外部重试库或独立代理池服务。

## 设计

### 1. 统一请求错误和重试语义

NVIDIA 的 Attempt 继续作为唯一的 Key/代理重试入口。ReasonNoHealthyProxy 保持为可重试的 503；ReasonTransportFailed 保持为可切换出口重试的 502；ReasonProxyRejected 不重试。上游 4xx、模型不存在、能力不支持和 501 不进入代理切换。只有请求尚未提交时允许重放，已提交的流不能回放。

Chat、Responses 和 OpenCodeFree 共享同一组错误码约定。已提交但在 [DONE] 前结束的 Chat 流发送 upstream_stream_truncated 与 [DONE]；Responses 流发送 response.failed 终态与 [DONE]；两者都将 stream_done 保持为 false。只有真实的 upstream/pool Retry-After 才透传，未知恢复时间不伪造 header。

### 2. 能力状态从布尔值升级为可解释状态

在 models 表增加 tools_status 和 tools_verified_at：

| 状态 | 含义 | 是否允许带 tools 的请求 |
|---|---|---|
| unknown | 没有可靠探测结果 | 否，返回能力未验证 |
| inferred | 来自候选发现或人工声明 | 否，先完成探测 |
| supported | 探测得到合法 tool call 和 JSON 参数 | 是 |
| unsupported | 上游明确拒绝工具能力 | 否，返回能力不支持 |

supports_tools 继续作为有效能力布尔值，但只有 tools_status=supported 才能满足请求的 tools requirement。普通文本请求不受影响。候选保存和手工修改只能产生 inferred，不能伪造 supported；探测遇到 502/503、代理耗尽或超时不覆盖已有状态。

reasoning 继续复用现有 reasoning_status、wire format 和档位字段。只有明确成功的 reasoning 探测才更新 wire format；自动 reasoning 只从模型声明的有效档位中选择，不向上游注入 none、auto 或不存在的档位。

### 3. 评测脚本输出能力门禁，而不是原始响应

vibe_eval_remote.py 保持 stdin 注入管理员密码和临时 Key 的方式，改为可配置的脱敏矩阵：基础请求、reasoning、双工具闭环、流式工具、JSON、context needle、长输出和稳定性重复。输出只保留状态码、错误码、TTFT、最大流间隔、完成标记、长度统计、needle 是否命中和工具参数是否为合法 JSON，不保留响应文本或凭据。

每个模型单独出具维度结果：普通 Chat、reasoning、tools、stream、context 和 stability。工具不支持的模型应标记为“能力不支持”，不能与代理 502 合并；transient 失败需要单独计数和重试。评测脚本不直接修改模型目录，目录更新由管理员探测和人工证据驱动。

### 4. 发布与验收

本地先完成 Go、前端和脚本门禁；发布使用唯一版本号和 scripts/deploy/deploy_remote.py。国内机切换后核验版本化镜像、Release、数据库备份、容器健康、关键端口和匿名鉴权边界，再运行脱敏真实矩阵。任意未达到门禁阈值的维度都按部分通过报告，不能宣称完整 vibe/E2E 通过。

## 验收标准

- 代理池为空、代理传输失败和代理拒绝三类错误分别得到稳定的状态码、错误码和重试行为。
- Chat 与 Responses 的 committed EOF 都能被客户端识别为失败，不再产生“HTTP 200 空响应即成功”的假阳性。
- tools 状态只在明确探测结果下更新；unknown/inferred/unsupported 模型不会被误认为 Agent 可用。
- 评测脚本在不暴露完整响应的前提下，能输出每模型每维度的成功率和失败分类。
- 未声明上下文窗口的模型不被自动填入猜测值；有证据的值通过现有管理端 Patch 持久化并出现在 /v1/models。
- 本地测试、构建、静态资源闭包和国内部署健康检查全部通过；真实矩阵的失败项被逐项记录。

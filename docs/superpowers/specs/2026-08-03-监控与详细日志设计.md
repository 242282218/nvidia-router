# 监控与详细日志设计

## 目标

在现有 SQLite 观测链上补齐可长期参考的内置监控能力：保存至少 30 天的请求元数据，提供请求量、成功率、失败、耗时、排队、重试、Token 趋势，以及可筛选的请求级明细。

## 范围

### 包含

- 沿用 `request_logs` 保存请求级元数据，默认保留 30 天，支持管理员配置 30–365 天。
- 沿用 `daily_stats` 保存轻量日聚合。
- 增加监控汇总、趋势序列、请求明细和安全错误查询。
- 将现有统计页面升级为密集型监控页，支持 24 小时、7 天、30 天切换、筛选和分页。
- 通过数据库索引和查询上限控制明细查询成本。

### 不包含

- 不保存请求正文、响应正文、请求头、Cookie、Authorization、代理认证信息或任何密钥明文。
- 不引入 Prometheus、Loki、Grafana 或其他外部服务。
- 不增加费用估算、缓存命中率等当前请求链路无法可靠提供的指标。
- 不重构与观测无关的路由、代理池或密钥管理代码。

## 已确认的安全边界

`RequestRecord` 及其持久化表只能包含请求元数据。Access Key 和 NVIDIA Key 通过内部 ID 关联；管理页面只显示脱敏标识或 ID，不读取密文。日志和 API 错误响应不得包含请求正文、响应正文、密钥、Cookie 或代理认证信息。

## 现有链路

请求进入 `observability.HTTPMiddleware` 后创建 `RequestState`，业务处理器写入模型、Access Key、NVIDIA Key、重试和错误等元数据。中间件在响应结束时补齐状态码、总耗时、首字节耗时和 Token 使用量，将 `RequestRecord` 放入已有 `BufferRecorder`。后台批量写入 `request_logs`，并在同一事务中更新 `daily_stats`。

本设计只扩展记录的查询面和索引面，保留缓冲写入路径，避免监控功能增加请求热路径的数据库写入次数。

## 数据与保留策略

### 请求明细

继续使用 `request_logs` 的现有字段：

- `request_id`、`created_at`、`endpoint`、`model_id`
- `access_key_id`、`nvidia_key_id`
- `http_status`、`outcome`、`error_code`
- `is_stream`、`queue_ms`、`first_byte_ms`、`duration_ms`、`attempt_count`
- `prompt_tokens`、`completion_tokens`、`upstream_request_id`

Token 不可用时继续保存 `NULL`，不能把未知值伪装成 0。已有错误分类由 `apierror.Error.Write` 写入观测状态；没有分类的非 2xx 请求使用安全的状态类兜底分类，确保失败列表不会静默遗漏。

### 聚合

保留 `daily_stats` 现有的 global、model、nvidia_key、access_key 四个维度，并增加首字节耗时总和及有效样本数。监控趋势在无接口筛选时优先读取日聚合；24 小时的小时桶从请求明细按索引范围聚合，避免新增第二张高频聚合表。

7 天和 30 天使用日聚合时，平均首字节耗时由 `total_first_byte_ms / first_byte_count` 计算；没有首字节样本时返回 0。接口筛选无法由现有日维度表达，带 `endpoint` 筛选的汇总回退到 `request_logs` 的有界时间查询。这样普通监控不扫描明细，精确筛选仍能得到正确结果。

### 保留期限

- `request_log_retention_days` 默认值为 30，合法范围改为 30–365。
- 运行设置 API、后端校验、SQLite 约束和前端输入校验必须保持一致。
- 清理任务继续每日 03:00 UTC 执行，并使用当前运行设置快照计算截止时间。
- 清理失败只记录服务端错误，不影响请求处理；下一次计划周期继续重试。
- `daily_stats` 是低基数聚合数据，不在本次功能中删除，以保留趋势参考并避免清理任务扩大事务范围。

## 后端接口设计

### 汇总与趋势

新增 `GET /admin/api/monitoring/summary`。

查询参数：

- `range`：`24h`、`7d`、`30d`，默认 `24h`。
- `model_id`、`endpoint`、`outcome`：可选精确筛选。
- `access_key_id`、`nvidia_key_id`：可选正整数筛选。

响应结构：

```json
{
  "data": {
    "range": "24h",
    "from": "2026-08-02T12:00:00Z",
    "to": "2026-08-03T12:00:00Z",
    "summary": {
      "request_count": 6200,
      "success_count": 6192,
      "failure_count": 8,
      "success_rate": 99.87,
      "average_duration_ms": 921.4,
      "average_first_byte_ms": 779.2,
      "average_queue_ms": 13.5,
      "total_attempts": 6350,
      "prompt_tokens": 955700000,
      "completion_tokens": 3200000
    },
    "series": [
      {
        "bucket": "2026-08-03T11:00:00Z",
        "request_count": 522,
        "success_count": 520,
        "failure_count": 2,
        "average_duration_ms": 840.0,
        "average_first_byte_ms": 702.0,
        "average_queue_ms": 9.0,
        "total_attempts": 530,
        "prompt_tokens": 80000000,
        "completion_tokens": 280000
      }
    ]
  }
}
```

`24h` 使用小时桶；`7d` 和 `30d` 使用 UTC 日桶。缺少数据的桶由服务端补零，前端可以直接绘制连续趋势。平均值在无请求时为 0；Token 总量只有有值的记录才累加。

### 请求明细

新增 `GET /admin/api/monitoring/logs`。

查询参数：

- `range`：`24h`、`7d`、`30d`，默认 `24h`。
- `page`：从 1 开始，默认 1。
- `page_size`：默认 50，最大 100。
- `search`：匹配请求 ID、模型、接口、错误码和上游请求 ID，限制长度 128。
- `model_id`、`endpoint`、`outcome`、`status`：可选筛选。
- `access_key_id`、`nvidia_key_id`：可选正整数筛选。

响应返回 `items`、`page`、`page_size`、`total` 和 `has_more`。列表字段只使用安全元数据，并以固定 `created_at DESC, request_id DESC` 排序，保证同一毫秒内翻页稳定。

查询实现使用固定 SQL 片段和参数绑定，不拼接用户输入；过滤字段使用白名单。`page_size`、搜索长度和时间范围在 handler 层拒绝越界输入。

新增 SQLite 迁移为 `request_logs` 增加按时间、状态、模型和 Key 维度的查询索引，并为 `daily_stats` 增加首字节聚合字段。迁移保持已有数据可用，历史首字节聚合值按 0 处理，不回填未知数据。

### 兼容接口

保留现有：

- `GET /admin/api/stats?days=...`
- `GET /admin/api/errors?limit=...`

原接口的响应字段和范围限制不变。新监控页只依赖 `/monitoring/summary` 和 `/monitoring/logs`，这样已有客户端不会因页面升级破坏。

## 前端监控页设计

将现有 `StatisticsView` 升级为“监控”页面，但保留原路由 `/statistics`，避免导航和书签失效。

### 布局

1. 顶部工具栏：时间范围按钮（24 小时、7 天、30 天）、刷新、当前数据时间。
2. KPI 卡片：请求数、成功率、失败数、平均耗时、首字节、排队、Token、重试。
3. 趋势面板：请求/失败曲线、平均耗时曲线、输入/输出 Token；使用原生 SVG，提供图例、数值标签和等价数据表。
4. 筛选栏：搜索、模型、接口、结果状态、Access Key、NVIDIA Key。
5. 请求明细表：桌面端表格，移动端卡片；宽表容器允许横向滚动，不破坏页面宽度。
6. 错误信息：加载失败、空数据、筛选无结果和刷新状态就地显示。

页面采用当前深色主题和现有颜色变量。状态不只用颜色区分，同时展示文字和 HTTP 状态码；按钮有可见焦点态，支持键盘操作和 `prefers-reduced-motion`。

### 加载与刷新

- 首次加载汇总和明细并行请求。
- 切换范围或筛选时取消旧请求，避免旧响应覆盖新条件。
- 手动刷新保留当前筛选。
- 不做高频自动刷新；页面刷新间隔由用户控制，避免 SQLite 被持续查询。

## 错误处理与边界

- 数据库查询失败返回现有统一 `internal_error`，服务端记录带上下文的错误。
- 非法范围、页码、筛选 ID、搜索长度返回 `invalid_request_error`，不执行查询。
- 明细没有结果返回空数组和 `total: 0`，不是 404。
- 统计范围内没有请求时返回全零 summary 和完整零值 series。
- 监控 API 继续走现有管理员会话和 No-Store 中间件。
- 记录器缓冲区满时沿用现有丢弃计数和错误日志机制；监控页不把“尚未落库的极短延迟”伪装成实时完整数据。

## 测试设计

### Go

- 仓储：汇总、小时/日趋势、零值补桶、明细分页、稳定排序、所有筛选组合、搜索特殊字符、空/NULL Token。
- API：默认值、范围边界、非法参数、最大页大小、错误映射和响应 JSON。
- 保留：30 天允许、29 天拒绝、365 天允许、366 天拒绝；清理截止时间使用运行设置。
- 安全：请求正文/响应正文/Authorization 等字段不会进入 `RequestRecord` 或 SQLite；错误列表只返回白名单字段。
- 回归：现有 `/stats`、`/errors`、记录缓冲和迁移测试保持通过。

### Vue

- API 解码器拒绝缺字段、负数、无穷数和错误的数据类型。
- 范围切换、筛选、翻页、刷新取消和组件卸载取消请求。
- KPI、趋势、空状态、错误状态和明细表的关键 `data-testid`。
- `pnpm run typecheck`、`pnpm test`、`pnpm run lint`、`pnpm run build`。

## 交付判定

- 管理员可以在监控页查看 24 小时、7 天、30 天趋势。
- 可以按关键词、模型、接口、状态和 Key 维度定位请求，并翻页查看请求级元数据。
- 新安装默认至少保存 30 天请求明细；设置页不能保存小于 30 天的值。
- 监控查询不会返回正文或任何密钥明文。
- Go 和前端验证命令全部通过，且不覆盖工作区中已有的无关改动。
